# 14: A steer the hub drew always ends, and is always kept

**What to build:** Close the open edges ticket 13 reported around the moment between the hub drawing steered messages at the cut and the agent starting their turn. One invariant covers three of them: **every key the hub drew ends exactly once, and every message it drew is in the stored line**, whichever way the gathering step is left. User's request (2026-11-17): fix the open items.

The gathering step can be left five ways today, and each must hold the invariant:
1. **Stop while the agent gathers** two or more drawn steers. The hub returned none (they were drawn), and the turn had not started. Today nothing is kept, so the drawn messages are gone on reload. Ticket 13 already decided what happens: a drawn message is not returned, and it is kept as stopped. The reload shows the messages and no answer, as for any stopped turn.
2. **Stop before a lone steer's turn starts.** Same window, same outcome as (1).
3. **The merged turn fails to set up.** Today only the first steer is answered with the error and the others are logged as dropped. The hub keeps their places until a stop, so the topic's queue stalls. Every drawn key must end: the error is answered once, as for a failed turn. Every message is stored, marked failed, so Retry can take it.
4. **A drawn steer never reaches the agent** (`Unsteer` false / `EndUnheardAsync`: its emit was not heard after it was drawn). Today the agent waits for it until the next message, a stop or the group's end. The hub is the side that knows, so the fix goes there. Use the existing handed-back path if it can carry the signal before adding a wire field; any new field is optional both ways. No agent-side timeout, since it would flake under load.
5. **A drawn steer reaches the agent after the stop.** It is stored as stopped and never starts a turn ("nothing may run after the stop", ticket 08).

**Retry after a failed merged turn.** Ticket 13 read this in the code but never ran it: the page's Retry sends the last message alone, and `FailedTail.RetriedBy` compares every message of the failed tail, so the retry is appended after the failed turn instead of replacing it. Reproduce it red first; if it does not reproduce, drop the item and say so in the notes. The expected behaviour follows the reroll precedent: a retry of a failed merged turn replaces it, and its one answer covers every message of it.

**Not in scope:**
- **Mixed agent/hub versions.** That is deploy order (agent before hub), not code.
- **A steer the agent refused after the hub drew it together**, whose error lands in the middle of the answer. Where that error should be drawn is the user's call. Leave it open unless it falls out of this change unchanged in what the page shows.

**Notes from the implementation:**
- One commit per item: the stop exits (`2905a01a0`, with this ticket), the cancel's drawn/returned rows (`ce71dba7a`), the failed setup (`c19bbac5f`), the unheard steer (`4ddb269cf`), Retry (`b234a0320`), the reload pins (`e286f2ec2`), `channels.md` (`0bcfb6ff7`); then, from a review, Retry bounded to the last failed turn (`42d4c97ab`) and the row for a stop while the gathering waits (`aec402e6c`).
- **The theory** is `ChatMonitorSteeringTests.EveryDrawnSteer_EndsOnce_AndIsInTheStoredLine_HoweverTheGatheringIsLeft`, one row per way out of the step between the cut and the steers' turn, each placed by a deterministic hold (a recall hook that holds or fails one message's setup, a held reply for the cut turn's end, a wrapper that holds a run before it reaches the agent; the group having heard the stop is read off the thread resolver letting its context go): two steers stopped while their turn sets up; two drawn together, stopped while the group waits for the second, not arrived yet (the first is kept); a lone steer stopped as its turn sets up; two steers stopped once their turn was handed over but before its run reached the history; a steer the group takes only after it heard the stop; two steers whose turn fails to set up; and two steers pressed of which the hub drew only the first, the second's emit unheard. Each asserts the stored tail (stopped, failed, or answered), how often each drawn key ends, the model calls, and the reload. Exits 1 and 2 are three of the rows: the setup window and the window before the run reaches the history are both "the turn had not started".
- **Drawn or returned: no new wire field.** Since ticket 12 a hub's stop hands back every steer it has not drawn and names each in `ChannelCancelNotification.ReturnedTurnKeys`, always as a list (empty when nothing went back). So a cancel that names a list accounts for every steer: one the agent was sent and the cancel does not name was drawn. The pump records each steer it admits (`_admittedSteers`) and, at a cancel naming a list, takes those it does not name as drawn (`_drawnAtStop`); a steer arriving after the cancel (a later stream's, landing in the dying group) is never among them. A cancel naming nothing (a hub from before 12, or a topic's delete) leaves the old drop. A drawn steer always reaches the pump before the stop's cancel: the hub sends the steer before drawing it, and the cancel after, in one inbox, in order (`InAgentOrderAsync`). That is how exit 5 reads: "after the stop" is the group taking the steer (from its pending turns or the teardown drain) after it heard the cancel; it is kept and never run.
- **Keeping.** The group collects every turn the stop left unrun (gathered, set up, taken, or still pending) and, as it ends, keeps the drawn ones as one stopped turn with no answer, in the order they came, through `DisposableAgent.KeepUnansweredAsync` (`McpAgent` → `RedisChatMessageStore.KeepUnansweredAsync`: appended under the store's lock, each with a name of its own). The messages are built as a turn builds them, less the preload and recall (`ConversationGroup.PersonsMessage`, now shared with `BuildUserMessageAsync`), so a reload says whose each is. A turn whose run started is kept by the history as any stopped turn is; the history now settles every turn it decides about (`TurnSteering.IsSettled`, set in `InvokedCoreAsync`, a handed-back turn included), and the group keeps only a cancelled turn it never settled, so nothing is kept twice. Only steers: a queued head or a person's own first send stopped before its turn started is still dropped (see below).
- **A failed setup** (`EndUnsetUpAsync`, in all three setup catches): the first message is answered as before; every other key is ended with a `StreamComplete` of its own, which the hub counts and does not draw (`RunningQueue.Joined`), so the queue goes on; and the steers are kept, each marked failed, then what the person was told, as a failed run is kept. A lone steer is kept too (it was drawn); a turn that is not a steer still keeps nothing. Kept only when the first message was answered: an agent its household does not have answers only an attach-only channel, so a WebChat steer there is neither answered nor kept, as any WebChat message there is not.
- **The unheard steer is fixed at the hub, with no wire field and no agent timeout.** The emit is synchronous but outside the stream lock, so the running turn's end could draw a steer between `Steer` and the answer to its emit; drawn and unheard, the agent was told it went in with the others and waited for it. `StartSteers` now draws only a steer heard (`WaitingSteer.Heard`, set by `StreamService.SteerHeard` after the emit) or already answered, and stops at one still being sent (always the last: a steer is sent before the next is taken). Heard later, it is drawn where the turn ended; unheard, `Unsteer` puts it back at the head, and the place it held is given up so the queue goes on. When the end drew nothing, `RunningQueue.EndedUnheard` says nothing runs until one of those. So `Unsteer` can no longer lose to a draw, and `SteerQueued` no longer ends an unheard steer's turn "not live" (`EndUnheardAsync` is left to a queued turn's emit). The receipt's `steeredTogether` never names a steer nobody heard, which is the agent's half: the merged turn starts with what arrived.
- **Retry reproduced red** (the retry was appended after the failed turn: `…, error, and in red, Both answered`). `FailedTail.RetriedBy` now takes a request saying the tail's last messages (a suffix of what its person said, as the page's Retry sends the last message alone): the earlier messages are read by the model again (unmarked, after the line it reads) and kept again ahead of the retry under their own names, the retry's messages take the names of those they replace, and the tail is dropped, so the line is both messages once, then the one answer. Failing again, all are kept failed again. The failed tail is the last failed turn alone (its person's messages and what they were told): read as every trailing failed message, two failed turns in a row made the second's retry hand the model the first's message and unmark it (found in review, red first: `FailedTurnHistoryTests.ARetryOfTheSecondOfTwoFailedTurns_TakesItsPlaceAlone`). The page's half (Retry sends the last message, the first stays drawn above it) was already so and is pinned (`SendMessageEffectTests`). The same words sent fresh after a failed turn are still taken for its retry, as they were for a turn of one.

**Still open:**
- Read, not run: the loop taking a turn the reader handed over after the stop (`unstarted.Add(x)`). Which of that and the teardown drain a steer leaves by is the channel reader's timing; the drain is the pinned one, and both keep the same way.
- `KeepUnansweredAsync` appends without the check `KeepStoppedAsync` makes that the line is still the one the turn read (`StillTheLineReadAsync`), so a topic deleted inside a stop's teardown could have the line written again under its key.
- A queued head the hub dispatched, or a person's own send that opened the stream, stopped before the agent started its turn: drawn, and still dropped (the drop is the decided rule for a non-steer turn behind a cancel; the invariant here covers steers).
- A steer heard by an inbox subscriber that then went away before taking it: drawn, and the group may wait for it until the next message, a stop or its end. The hub cannot tell; an agent timeout would flake.
- After a stop, a cancelled turn still sends its own stream ends; the hub, whose stream is gone, draws nothing of them (unchanged for any stopped turn).
- Out of scope, unchanged: mixed versions (deploy the agent before the hub; a hub from before this ticket can still draw an unheard steer), and a steer the agent refused after the hub drew it together, whose error is drawn in the middle of the answer (the hub draws an answered steer as before).
