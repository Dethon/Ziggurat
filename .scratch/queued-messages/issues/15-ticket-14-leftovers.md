# 15: What ticket 14 left open

**What to build:** Close the edges ticket 14 left open, so that no message the page has drawn as sent is ever lost to a stop, and no turn waits on a message that will not come. User's request (2026-11-17): fix the open items instead of reporting them.

1. **Every drawn message survives a stop, not only steers.** A stop that lands before its turn starts still drops two kinds of message:
   - a queued message the hub had already dispatched to the agent;
   - a person's own first send that opened the stream.

   Each must be kept the way ticket 14 keeps a drawn steer: stored as a stopped turn with no answer, nothing run after the stop, and the reload showing the message. A message the hub returned to the composer is still dropped, so it is never shown twice. A hub from before keeps the old drop.
2. **A turn never waits on a steer whose agent connection dropped.** Today, when the agent's connection drops after a steer was confirmed delivered, the agent can wait for it until the next message, a stop or the group's end. The waiting turn must start with what it has, or the steer must be delivered again. Either way:
   - nothing waits on a timer (no agent-side timeouts, since they flake under load);
   - each key ends exactly once;
   - no message is answered twice.
3. **A deleted topic is never rewritten.** `KeepUnansweredAsync` must not write history for a conversation that was deleted while a stop was being torn down. It needs the same check the stopped-turn path has. Red first.
4. **A steer refused late is not drawn mid-answer.** A steer the agent refused after the hub drew it together currently has its error written in the middle of the answer. The agent knows about the refusal before the merged turn starts (the gathering step waits for each steer), so the error goes out before the answer begins. That follows the precedent of a steer refused as it arrived (`m1, m2, error(m2), m3, answer`), as closely as the drawn order allows.
5. **The branch ticket 14 only read is run.** The agent picks up an already-received steer after the stop. Pin it with a deterministic test, so both ways a steer can leave (that branch and the end-of-group drain) are run, not read.

**Not in scope:** mixed agent/hub versions. That is handled by deploy order (agent before hub), not code.

**Notes from the implementation:**
- One commit per item: the deleted topic (`683a0e998`, with this ticket), both ways a steer leaves (`5bd90721f`), every drawn message kept (`ddd23f0d5`), a send right behind a stop (`d52193ea5`, found on the way), the late refusal (`f1ceb1737`), the redelivered batch (`35b507a75`); then `channels.md` (`576af3704`: the queue paragraph, still one line, and a bullet of its own for the receive contract) and these notes.
- **Every drawn message survives a stop (item 1).** No wire field and no hub change: the hub never emits a message it later hands back (a queued head is written and emitted in one `InAgentOrderAsync` step, a first send likewise through `StartSendAsync`, both before the stop's cancel), so ticket 14's reading of a cancel that names a list holds for every message, not only steers. The group numbers the turns its pump admits (`AdmittedTurn.Order`) and, at the first cancel naming a list, records how many it had admitted and on which channel (`_drawnBefore`, `_stoppedOn`), replacing ticket 14's `_admittedSteers`/`_drawnAtStop`. A person's message of that channel admitted before it and not named is drawn (`DrawnAtStop`); a fire, Continue's ask (never drawn), a reroll's message (the line holds it already) and another channel's message (the cancel says nothing of it) are not. When the stop came before the group took its first message, nothing was built yet: the group is built to keep it (`EstablishedToKeepAsync`, the warmup it starts on the cancelled turn token only observed). A first send and a queued head carry no turn key, which is why the record is by order, not by key.
- **A batch whose answer died is delivered again (item 2).** The only way a heard steer never reaches a live agent is its poll's answer dying on the wire after the inbox let the batch go: the inbox buffers for a quiet subscriber and puts back a batch whose own poll saw its caller go, but the write itself was open. Fixed at the transport, so it covers every message and cancel, not just steers: `channel_receive` takes an optional `poller` (an id `McpChannelConnection` mints once and keeps across reconnects and tunnel openings, the connection object being reused) and `received` (the last batch number it got, 0 before any), and answers with `ChannelReceiveResult.Batch` (absent when empty or unnamed). `ChannelInbox` keeps the batch drained for a named poller as handed out (`PollerCursor`, `Subscriber.Settle`): that poller's next poll lets it go when it names it, and has it delivered again first when it names an earlier one. Anyone else polling lets it go, as every batch was before: another poller (an agent restarted, a fresh connection) may have taken and answered it, so redelivering there could answer a message twice. No timer: the next poll settles it. The agent numbers a batch received only once every item of it is dispatched. Both arguments optional both ways: a hub from before ignores them (pinned: a tool ignores an argument it does not declare), an agent from before names nothing and every batch is committed on drain.
- **A deleted topic is never rewritten (item 3).** `KeepUnansweredAsync` asks `StillTheLineReadAsync` under the store's lock, as `KeepStoppedAsync` does. For that to mean anything after a turn the session already stored, `_lineRead` is now the line as the session last left it (read, or written by its own append: `Wrote`), and a session that read nothing asks that its topic is still there.

**Still open:**

Moving a fire behind the steers is a change to ticket 13's decided order, and it needs a fire in the very group of the steers within one cut.
- A turn of steers that fails to set up keeps its steers (ticket 14); a non-steer turn that fails to set up still keeps nothing, its message on the page above the error and gone on reload. Not a stop, so outside this ticket; ticket 14 decided it.
- A batch handed to a poller that then went away for good (the agent restarted) is not delivered to the next one: that one cannot tell whether the old one answered it. The group of the old process is gone with it, so no turn waits; the hub's stream does, as for any turn an agent died in.
