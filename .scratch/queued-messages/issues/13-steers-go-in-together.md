# 13: Messages steered into the same reply go in together

**What to build:** A person queues two messages behind a running reply and presses Steer now on both. Today the first steer cuts the reply at its next tool boundary, but the second waits for the first steer's whole answer, as if it had only been queued: the agent's pump signals only the turn running when a steer arrives, and both arrived while the original turn ran. User's decision (2026-11-17): every message steered before the cut goes in together, in the order they were steered, as **one turn with one answer**.

**Blocked by:** 12.

**Status:** done

- [x] Two (or more) steers from the running turn's person that are waiting when the cut turn ends start one turn holding all their messages, in steer order, answered once (agent seam).
- [x] A steer pressed after that merged turn has started cuts it, as a steer cuts any turn of its person's (unchanged; pinned).
- [x] The hub draws every waiting steer's message where the cut turn ended, in order, before anything of the answer; each steer's chip goes; the merged turn is the running turn, and its end is counted once (hub seam).
- [x] Stop before the merged turn starts returns every waiting steer to its sender; Stop after it started returns none of them and keeps the turn stored as stopped, never both (hub + agent seams, `ReturnedTurnKeys`).
- [x] A reload shows the steered messages one after another, then the one answer.
- [x] The steer E2E (or a new one in `WebChatE2E.Queue`) steers two messages into one reply and sees both drawn before a single answer.
- [x] Hub, monitor and client filters green under two concurrent processes; queue E2E collection green.

**Notes from the implementation:**
- One commit per step: the agent (`4423ea0ce`), the hub (`9eff1ee70`), the client pin (`b319e73e8`), the reload pin (`21865c9e5`), `channels.md` (`7fae43c9e`), the E2E (`2762b31d2`).
- **Who decides which steers go together: the hub, at the cut.** The agent cannot tell by itself: it takes its next turn as soon as the cut turn's last `send_reply` is answered, and its pump admits each steer on its own time (an assertion check per message), so a steer the hub drew at the cut may not be pending yet. Merging "whatever is pending" would have the two sides disagree in that window. So the hub decides, under the lock the cut takes (every unanswered waiting steer, in steer order), and says so in its answer to that end: `ReplyReceipt.SteeredTogether` (`{"steeredTogether":[…]}`, beside `returnedTurnKeys`; optional both ways, a receipt with neither is still `ok`). `ReceiptFor` names them only to the reply under the turn key that ended (`RunningQueue.DrawnTogether`). The receipt is the one thing the agent reads before it takes the next turn (ticket 12's ordering).
- **Agent.** `ChatMonitor` records the set on the group (`ConversationGroup.SteeredTogether`, by each of its keys). When the loop takes one of them, `SteeredWithAsync` gathers the rest off the pending turns **before** the turn's `TurnSteering` is made and set running, so none of its own messages can cut it. A steer not admitted yet is waited for; one the pump refused as it arrived is queued as a marker (`AdmittedTurn.Refused`, skipped everywhere else) so the wait ends; anything else at the head stops the gathering and runs after; a key a stop handed back is dropped. The turn is `RunStreamingAsync` with every message, each built as a turn's own message (sender, attachments landed, context, recall and extraction each), the skill preload asked once, for the last message, which is the one `SkillsProvider` takes. The model, config patch and response format are the last message's, as `McpAgent` reads them off the last user message. The `Turn` (targets, metrics, identity) is the first message's.
- **The key, and ending the others exactly once.** The turn answers under the **first** steer's key, which the hub has always drawn (it is the earliest waiting). The hub keeps one pending place per steer it drew, and the agent ends every other key with a `StreamComplete` of its own after the answer (`StreamAgentTurn`'s `joined`). The hub counts that end (giving up its place; the queue goes on once all have ended) and does not write it (`RunningQueue.Joined`), since the answer already ended on the page. This was chosen over giving the other places up at the cut because every interleaving then ends each key once and stalls nothing: an agent from before runs them one by one and each key still ends; a steer refused late (after the hub drew it) ends its own place.
- **Hub.** `StartSteers` now draws every waiting steer, not the first: an unanswered one joins the turn (RunningFor its person), an answered one (refused as it arrived) is drawn with its held refusal in its place and its place given up. So `m1, m2, error(m2), m3, answer(m1+m3)` for a refused steer between two others (pinned).
- **Stop.** Before the cut: every waiting steer is returned, the cancel names each, and the cut heard after it answers with them as returned and draws nothing together, so the agent drops each (pinned on both seams). After the cut: none is returned, and the agent keeps the turn as stopped with every message (`TurnSteering` asks the first key, and the hub returns the together set all or none). Both handed-back rows of the agent theory pin it.
- **Tests.** Red first: the agent-seam test of the user's case (the stored line had the first steer answered alone), and the hub's (only the first steer drawn at the cut). Written after the code and mutation-checked: the late steer waited for (red with the wait removed), the refused marker (red without it: the turn waited until the channel's end), a steer after the merged turn cuts it (red with the signal removed), the stop theory's handed-back row (red with the turn's key left off its handle), the hub-handed-back row (red with the returned check off), the hub's joined end not drawn (red with it drawn) and its place kept until it ends (red with it given up at the cut: `older` dispatched early), the refused steer among the waiting (red with answered steers joined), the receipt's parse and its real wire hop (red with the field dropped). Green on first run and pinned: the client draws two messages written together one after the other, then one answer (red when a user message right after a user message is taken as shown), and the reload projection (`Transcript.Shown` over the line the real store keeps: both messages, each its own entry, then the answer).
- **Read, not run:** a reroll of a merged turn rerolls its last message with the first in history, so both are answered again; a failed merged turn is kept with both messages marked failed, and the page's Retry sends the last message alone, which `FailedTail.RetriedBy` does not take for the failed tail's retry (it compares every message of the tail), so the retry is appended after the failed turn instead of replacing it.

- **E2E** (`SteerNowE2ETests.TwoSteersIntoOneReply_AreDrawnTogether_AndAnsweredOnce`, in the `Queue` collection beside the single steer): a reply held on its tool's approval, two queued messages each asking for a word of its own (`ONE`, `TWO` "in the same reply"), both steered (each chip seen marked steering), then the approval; the page and a fresh load each show the steers one after the other, right after the cut reply, then exactly one answer naming both words. Mutation-checked once: with the agent's gathering switched off (the hub unchanged), on images the fixture rebuilt for the mutant, it failed with `["assistant: ONE…", "assistant: ONE… TWO…"]`, which is how an agent from before shows against this hub.
- **Verified.** The hub, monitor, client, agent, composition, store and thread-state filter passed 1729/1729 in each of two concurrent processes. The queue E2E collection passed 5/5 on images the fixture rebuilt from the committed code, and again 5/5 after the mutation was restored.

**Still open:**
- A stop that lands while the agent gathers (the hub drew the steers, so returned none, but the turn had not started) keeps nothing, so the drawn messages are gone on reload. The same window exists for one steer (a cancel before the steer's turn starts drops it); not closed here.
- A steer the hub drew whose emit nobody heard after it was drawn (`Unsteer` false, `EndUnheardAsync`) never reaches the agent, which then waits for it until the next message, a stop or the group's end.
- A steer the agent refused after the hub drew it together: its error is written under its own key in the middle of the answer.
- Mixed versions: a hub from before answers `ok`, and the agent runs the steers one by one as before. An agent from before with this hub runs them one by one too; each key still ends once, but the second's answer streams after the first's under the drawn messages. Deploy the agent before the hub.
