# 12: A steered, stopped, raced or unshared message is shown once and never lost

**What to build:** Close the open edges tickets 05 to 09 recorded.

**Blocked by:** 10, 11.

**Status:** done

- [x] **Stop just after the agent started a steer.** The steer must be either returned or stored, never both: the stop's cancel tells the agent which turn keys it returned, and the agent keeps no stored turn under a returned key (agent + hub seams).
- [x] **A steer is visible while it waits.** Between Steer now and the running turn's end, the steered message shows as a chip marked as steering, with no Edit or Remove, on every page of the topic, until it is drawn (hub push + client).
- [x] **A send racing a stop is shown once.** A message the page drew as sent that the hub then returns to the composer is taken off the page (and likewise a refused send in a race with a resume: not drawn as sent, its words back in the composer).
- [x] **A person's own first send still being vouched for when Stop lands** is not emitted after the cancel: it is returned to its composer like a queued message.
- [x] **A fire attaching mid-turn** pushes the queue, so no page offers Steer now on a turn that is not the reader's.
- [x] **Unshare (user's decision, 2026-11-16).** Unsharing pulls a member's queued messages out of the queue; those and any returned words the member had not taken go to that member's open page, into whatever composer is on screen, with a toast saying the topic is no longer shared. A member with no page open gets them on their next page load.
- [x] **Attachments are the sender's.** A queued or sent message naming file ids the sender does not hold is refused.
- [x] **A refusal that is not the last message** still offers Retry.
- [x] **The per-chunk steer check** does not take the stream lock on every chunk when no steer waits.
- [x] **The steer E2E proves the cut:** it fails with the `Terminate` line removed (mutation-checked once and recorded).
- [x] Hub, monitor and client filters green under two concurrent processes; the queue E2E collection green.

**Notes from the implementation (part A):**

- **A fire attaching mid-turn** (red first). `GetOrCreateStream` clearing a non-null `RunningFor` now bumps the revision; without the bump the page's reducer drops the push. The push goes out through a new channel, `StreamService.QueueChanges`: a `QueueChange` carries the topic and its `ChannelSession`. The dispatcher reads it beside `Dispatches` and tells it through `QueueNews.TellOrLogAsync(QueueChange)`. So `create_conversation` needs no `QueueNews`, and the stream service still writes but never tells. The test drives the real `CreateConversationTool.McpRun`.
- **The steering chip** (red first; hub and client).
  - On the wire it is `QueueChangedNotification.Steering`, a list beside `Items`. A page from before, which knows only `Items`, never draws Edit or Remove on a message that has left the queue.
  - `QueueSnapshot` carries it, and `QueueOf().Messages` is still the waiting list alone, which `SteerQueued` looks the caller's message up in.
  - Revisions are bumped and told wherever the steers change:
    - `StartSteers` bumps and tells through `QueueChanges` as each steer is drawn.
    - The stop's cleanup bumps when steers were waiting. Before, a stop with only a steer pushed the same revision and the chip stuck (`AStopWithOnlyASteerWaiting_…`).
    - A refused steer is told again, since an `Unsteer` may follow a push that showed it.
  - The client keeps it as `TopicQueue.Steering`, drawn first as `QueueChip.Steering` with no actions and an `Icons.Steer` marker. A success dispatches `QueuedMessageSteered`, which moves the chip into the steering list instead of letting it go and come back.
  - `SteerNowE2ETests` now expects the chip marked steering, with no action buttons, until the approval lets the turn end, and then gone.
- **The per-chunk check** (red first, all four rows).
  - `HeldForSteer` takes `_streamLock` only for a chunk whose key is in `_waitingSteerKeys`. That set is a `ConcurrentDictionary`, written under the lock wherever a steer starts or stops waiting (`Steer`, `StartSteers`, `Unsteer`, the cleanup a stop or a stream's end runs) and read without it. The read is safe because a steer's answer can only arrive after its key was added: the steer is sent after that.
  - `StreamServiceSteerCheckTests` holds the lock with another topic's `Enqueue`, which reads a gated clock under it, and checks that a keyed chunk is written while that lock is still held: with no steer waiting, and after a steer was drawn, put back or stopped. The last three pin the exits, since the steer's own reply is every chunk under its key.
  - The first version of the test passed red: the gate's own 60 s timeout let the lock go inside `Eventually`'s 60 s budget. It now asserts the holder is still blocked and the gate waits 5 minutes.
- **Stop after a steer started** (red first on all three seams; the agent row where nothing was handed back pins existing behaviour).
  - Hub: `StopAsync` hands its cancel callback what it returned, and `CancelTopic` sends every returned id as `ChannelCancelNotification.ReturnedTurnKeys`. Only the steers' ids were ever sent as turn keys; the queued ones are harmless.
  - The field is optional both ways. `McpChannelConnection` maps it onto `ChannelMessage.ReturnedTurnKeys`, and a payload without it, or with a field it does not know, still cancels (pinned).
  - Agent: the group records the keys before `CancelOwnContext()` in a set kept for the group's life. Each turn's `TurnSteering` is built with its message's `TurnKey` and asks that set (`IsReturned`) at keep time, not at cancel time, so a steer dequeued but not yet set as running is covered too. `McpAgent` hands the handle to `RedisChatMessageStore.BeginCollecting`, and `KeepStoppedAsync` keeps nothing for a returned turn (the turn-in-flight mark is still cleared).
  - The row where nothing was handed back passed on its first run. It goes red when `IsReturned` is mutated to ignore the key (true whenever any key came back).
  - The real wire path was read rather than run: `channel_receive` serializes an inbox item whole, and `McpChannelConnection` serializes `item.Cancel` whole before mapping it. Nothing projects fields by hand. The receive, protocol, `Domain.Channels` and `Mcp.Hosting` suites are green (161).
  - Still open: a steer's turn that was stored before the cancel reached the agent. The likely case is one that fails fast and is kept as a failed turn. The hub still hands the steer back, so its sender gets it twice. Whether `send_reply` keeps one conversation's replies in order across turns, which would keep that window small, was not verified.

**Notes from the implementation (part B):**
- One commit per item: attachments (`51ef3856b`), the first send vouched for as Stop lands (`535e84931`), a send shown once (`06e2474b4`), Retry off the last line (`25c8d12e6`), unshare (`51b6d427e`), a steer returned or stored (`065c4a836`), and the chips' height from the screenshot (`ead751868`).
- **Attachments are the sender's** (red first). `ChatHub.AdmissionRefusalAsync` refuses, before the capability guard, a message naming a file the upload store keeps for *another conversation* (`TopicRefusals.NotYourFiles`), for `EnqueueMessage`, a `SendMessage` queued behind a reply and a send opening a turn alike. Upload tickets are per topic and a fork copies files, so no page flow names another conversation's file; the agent fetches whatever a message names (`FetchAttachmentTool` reads any id), which is what the check closes. An id the store holds nothing under passes, as a swept file always did (the agent gets a placeholder): refusing it would also refuse a late retry of a message whose file was swept. "Holds" is by conversation, not by uploader (no uploader is recorded): a member of a shared topic may name a file another member added there, which they can open anyway. `ARemovedMessageNamingAnotherConversationsFile_LeavesThatFileAlone` was deleted, its message now refused; the remove path's conversation filter stays. Hand-built hubs that are not about files get `HubParts.NoUploads()` instead of a null service.
- **The first send vouched for as Stop lands** (red first, both rows). `StreamService.StartSendAsync` writes and emits the send that opened the stream in one `InAgentOrderAsync` step, only while that `StreamKey` still runs; otherwise it is handed back through `HandBackIfStopped` (the stop left `LastStopped` on that stream) and its sender told `OnQueueReturned`. A reroll's message, already on the line, and a Continue's ask are dropped, never put in a composer. `OnStreamStarted` now goes out after the emit, since a stop may take the turn back first.
- **A send shown once** (hub rows red first; the wire marker's hub row was written after the marker and mutation-checked: red without `RefusedSend = true`; client rows red first).
  - Handed back: `ReturnedMessage.CorrelationId` and `QueueReturnedNotification.CorrelationIds` (both optional) name the sending page's id. Every page of the sender takes a drawn copy off on the push (`TakeOffSentMessages`), whichever page takes the words, and again as words are taken. This covers a `SendMessage` the hub queued behind a reply the page had not heard start and a stop then returned (as admitted or later from the queue), and item 2's send.
  - Refused as queued: the hub marks the wire's error `ChatStreamMessage.RefusedSend` (optional; a page from before draws it as before). The page takes the drawn message off, toasts the refusal and gives words and files back through `ReturnToComposer`, on its own wire or off the losing wire of a resume race (ticket 09's edge). Ticket 09's two client rows, which send no marker, still pin a hub from before; the new theory pins both wires with it.
- **Retry off the last line** (red first). `MessageActionsLogic.OffersRetry` keeps Retry on a refusal drawn right under the reader's own message (`RetriedAt`) once other turns follow; never on another member's, never while streaming. `RetryRefused` sends that message again as a new one at the end and takes nothing off: a hub refusal stored nothing, and an agent failure is kept where it was once another turn follows (the store replaces a failed turn only at the tail), so what the page leaves drawn above is what a reload shows for a failed turn; a hub refusal's bubbles vanish on reload as they always did.
- **Unshare** (hub rows red first; the two client rows were written beside the code, then mutation-checked: both red with the push handler and the live trigger removed).
  - `StreamService.Unshare(topic, owner)` takes every non-owner sender's waiting messages, a head of theirs still being vouched for (its place given up, so the queue goes on), and their untaken returned words into `_unshared`, kept by `Account` and dropped with the topic by `Forget`. "Member" is "not the owner", since after an unshare only the owner may continue (`TopicViewer.MayContinue`); a sees-all reader's words move too.
  - The running stream is marked `PrivateTo` the owner, so a member's message still being admitted when the unshare lands is handed over too (`Queueing.Unshared`, `EnqueueMessage` true); `Reshare` clears it. A steer already sent is left to the agent.
  - Told after `OnTopicChanged` (which drops the topic from the member's list) by `OnQueueReturned` with `Unshared` set; a page from before asks `TakeReturned` and is refused, its words staying at the hub. `ChatHub.TakeUnshared` hands them over by person, once; the page asks on the push and every time it becomes live, the first time too.
  - The page puts the **words only** into whatever composer is on screen with a toast (`ReturnedMessagesEffect.UnsharedToast`): the files were added to the unshared conversation, and item 4 would refuse them in any other. The toast does not mention the files. A member reading the topic has it closed by `OnTopicChanged` first (`RemoveTopic` deselects it synchronously, and `ChatInput` keeps its text across the change), so the words land in the composer left; a sees-all reader still reading it, who may no longer send there, has the words wait on the page until another composer is on screen (`UnsharedWhileStillReadingThatTopic_…`, red first; the main-case row passed on its first run and goes red with the client's `RemoveTopic` on an unshare removed).
- **A steer returned or stored, never both** (agent and hub rows written beside the code, then mutation-checked: the hub row red with `ReceiptFor` answering nothing, the agent row red with the receipt not recorded).
  - What the code guarantees: `ChatMonitor.ProcessChatThread` awaits each `DeliverUpdateAsync` before pulling the group's next update, a group runs its turns one after another, `McpChannelConnection.SendReplyAsync` awaits its tool call and `SendReplyTool` awaits `WriteReplyAsync`. So the agent starts turn N+1 only after the hub processed turn N's last reply. The pump's admission refusals are the one path outside that order.
  - Hence the brief's rule ("don't return a steer the hub saw complete") would be wrong. A steer the hub has seen answered while it still waits can only be one the agent refused at admission, which stored nothing (ticket 09 pins it as returned). And the real window is the hub's lock: the stop wins against the steered turn's end, which then finds no stream; the agent starts the steer at once and keeps it if it fails fast before the cancel is pumped.
  - The fix: the turn's end is answered. `SendReplyTool` returns `StreamService.ReceiptFor(p).ToWire()`: for an `IsComplete` reply, the ids the topic's last stop handed back (`{"returnedTurnKeys":[…]}`), else `ok` as before. `IChannelConnection.SendReplyAsync` returns a `ReplyReceipt` (`McpChannelConnection` parses the tool's text; anything unknown is none), `ReplyDispatcher.Delivery` carries it, and `ChatMonitor` records the keys on the group (`TurnsReturned`) before pulling the next update. The group drops a turn whose key is recorded before it starts. Part A's cancel keys and `IsReturned` stay for a cancel that lands mid-steer.
  - The wire hop runs in `McpChannelConnectionReplyReceiptTests`: the hub's real `SendReplyTool` in an in-memory MCP server, read by the agent's real `McpChannelConnection` (green first run; red with the connection answering `None`).
