# 02 — The watches skill travels from the home server to a load

**What to build:** The tracer bullet: one real skill through every layer, with an eval gate. The watches section of the home guide becomes the `home-watches` skill. It is declared in the prompt manifest beside the sections — name, one-line description, description budget, body budget, the home server, its claims — and the manifest's claim set becomes the union of section and skill claims. A declared `skills` section at feature priority carries the advertisement's prose and the trigger claims. The home server publishes the skill as standard resources — one index document and one body with a name-and-description frontmatter — through a hosting helper that builds both from the domain constants, so no server hand-writes a resource. The client manager reads index and bodies at warmup from every dialled server that has them, through the prompt cache, binds each by name (an undeclared one under the default budget with a warning, outposts through the same path) and exposes them on the session. The agent attaches the framework's skills provider with the session's skills inline, the load tool auto-approved and observed by the tool pipeline under its own name, the template cut to the bare list, resources and scripts unadvertised. The prompt fixture renders through the provider so agent snapshots show the advertisement, and the skill gets a body snapshot. Staleness walks skills both ways; the server contract table gains a per-skill row. The stub the home guide keeps says a watch request loads the skill. The watch family cites the trigger claim and requires the load; every watch claim that moved is cited or guarded as before. Ask "warn me when the study window opens" and the model loads the skill and creates the watch as today.
