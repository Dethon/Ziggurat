# Channel Architecture

Transports (WebChat, Telegram, ServiceBus, Voice, Scheduling) are independent MCP channel servers; the agent connects as an MCP client via `ChannelEndpoints`. Wire serialization is centralized in `ChannelProtocol` (shared `JsonSerializerOptions` + typed records — `ChannelMessageNotification`, `ChannelCancelNotification`, `RegisterAgentsParams`, `RequestApprovalParams`). Inbound: `channel/message`, `channel/cancel`. Outbound tools: `send_reply`, `request_approval`, `create_conversation`, `register_agents`. A new transport needs only a new channel server — zero agent changes.

- **Being a channel server is one call.** `Mcp.Hosting`'s `IMcpServerBuilder.AddChannelServer(policy, subscriberId?, errorResult?, noOutboundSurface?)` wires the `ChannelInbox`, the shared `channel_receive` long-poll tool, the call-tool error filter and the sealed `ChannelNotificationEmitter`. It sits beside `AddToolServer`, and the difference between the two kinds of server is exactly what those two calls differ by. A new transport writes only its reply-sending logic.
- **`DeliveryPolicy` is a required argument.** `Broadcast` fans out to every registered subscriber whatever its freshness, so an idle-but-unpruned subscriber still receives; with no subscriber registered at all the item is discarded (SignalR, Voice). `BufferAlways` targets a known subscriber id and creates its queue on demand, for a transport that cannot tell a sender to retry (Telegram). `GateOnLive` enqueues only when someone is actually polling, for callers that settle a durable record on a confirmed delivery — buffering on a failed emit would keep the record *and* leave a duplicate (ServiceBus, Scheduling, Library).
- **Liveness is the return value of emitting**, never a separate property: `EmitAsync`/`EmitCancelAsync` answer "was anyone listening?", with the freshness window internal to `ChannelInbox`. The same stale-subscriber defect was fixed three times across six hand-copied emitters before this. `ChannelReceiveContractTests` drives the channel-capable rows of that table and asserts each declared policy.

- **A conversation group is anchored and built by its first turn.** `ConversationGroup` (internal to `Domain/Monitor`, one per conversation and agent, constructed in production code only by `ChatMonitor`) owns the pending-turn queue, the command dispatch, the delivery anchors, the agent, the restored thread and the warmup, and establishes all of it on the group's **first turn**. A chat command is not a turn, so a group whose messages are all commands builds nothing — a `/clear` on a conversation with no live group costs no agent, no thread read and no MCP connection. The thread context stays eager because disposing it is how a command ends the group; `ChatThreadResolver.ClearAsync` wipes persisted state unconditionally. Whether a turn reuses the anchors is decided by identity against the anchor message, never by a message counter. See `docs/adr/0006-a-group-is-anchored-and-built-by-its-first-turn.md`. The monitor keeps merging the channel streams, grouping the messages, delivering each update and publishing first-reply latency.
- `DeliveryTarget.Minted` means "minted while resolving this turn", so reused anchors carry it cleared and `AnnounceTurnStartAsync` needs no correcting flag: it skips exactly the targets marked minted.
- `create_conversation` doubles as the turn-start announce when given `existingConversationId`: the conversation group calls it channel-agnostically for agent-initiated messages (`Origin` set) into existing conversations, and each channel applies its own semantics — SignalR opens a live stream + `OnStreamStarted` before reply chunks arrive; voice no-ops on a live satellite session, else binds the turn as an announcement.
- **A channel connection runs itself.** `IMcpChannelConnection.RunAsync(endpoint, catalog, ct)` owns connect with retry, register the catalog, watch health, reconnect with retry and re-register; `ChannelConnectionHost` reads the endpoint map and starts one run per endpoint, and knows nothing else about the order. Being **not connected** is five behaviours, one per member, stated on that interface (`docs/adr/0011-not-connected-is-five-behaviours-and-stays-that-way.md`) — `CreateConversationAsync`'s null is load-bearing for `DeliveryTargetResolver`. The far end's tool set is asked for once per **connection generation** and discarded on reconnect (`docs/adr/0012-a-servers-tool-set-is-fixed-for-a-connection-generation.md`).
- On connect and every reconnect the agent registers its `AgentCatalogEntry` list via `register_agents`; channels use this single source instead of duplicated `Agents` config, and SignalR broadcasts `OnAgentsUpdated` so WebChat refreshes live.
- `attachOnly: true` in `ChannelEndpoints` (voice) makes `DeliveryTargetResolver` order that channel last — it attaches to conversations minted elsewhere, never mints the primary target.
- **Dual-role** servers are both a channel and a tool/filesystem server (`mcp-scheduling`, `mcp-library` download alerts); their channel-protocol tools are hidden from the LLM.
- `ChannelMessageNotification.ConfigPatch` (`AgentConfigPatch`: model + reasoning effort) lets a channel override agent config per message; only the SignalR channel populates it. Whitelist: `patchableModels` in `Agent/appsettings.json`, surfaced to clients through the widened `AgentCatalogEntry`.
- **An attachment crosses every boundary as a reference; bytes cross as few as possible.** `ChannelMessageNotification.Attachments` / `ChannelMessage.Attachments` carry `AttachmentReference` (where the file rests, media type, filename, size) and are transport-neutral, so SignalR and Telegram both populate them and nothing above the channel knows which transport a file came from. **Where the bytes rest is the channel's own answer, not something being a channel requires.** SignalR keeps an upload store: bytes go browser → store (HTTP, one file per request, ticket-scoped) → agent. Telegram stores nothing — a `file_id` is a durable per-bot handle, so the reference is `<agentId>/<file_id>` and the fetch is a `getFile` plus a download at the moment the agent asks, with no volume, no sweeper, no retention and no attachment settings on that channel (`docs/adr/0022-a-channel-whose-transport-keeps-files-has-no-upload-store.md`; the named escape hatch if fetching proves slow is a bounded in-memory cache there, deliberately unbuilt). Either way the agent asks by `fetch_attachment`, the sixth channel-protocol tool, hidden from the model like the rest — `ThreadSessionBuilder` strips it. Neither is ever mounted; see `docs/adr/0021-the-upload-store-is-not-a-mount.md`. The persisted `ChatMessage` keeps the reference and never the bytes, and `AttachmentHydration` (`Domain/Agents/`) puts them back on the way to the model only, beside `TurnDecoration` and for the same reason — `docs/adr/0020-an-attachment-is-stored-once-and-hydrated-on-the-way-out.md`.
- **A dictation is not an attachment.** One run of a microphone that ends as words, and the audio is never a message: no playback bubble, no attachment kind, no bytes in any store, nothing in a conversation's history but text. `IAudioTranscriber` (`Domain/Contracts/`) is the one injection point — complete audio plus the container it is in, answered with a transcript and whisper's confidence figures — and `LemonadeTranscriptionClient` (`Infrastructure/Clients/Transcription/`) is its only implementation, shared with the voice hub's streaming `ISpeechToText`, which is otherwise untouched. **whisper as lemonade runs it rejects Opus in any container** (verified against the live instance; the image has no ffmpeg), so WebChat encodes 16 kHz mono s16le WAV in an AudioWorklet and Telegram decodes Ogg/Opus in managed code via Concentus; WAV, MP3, FLAC and Ogg/Vorbis are forwarded untouched, and the container is decided by sniffing the leading bytes, never by a sender-supplied mime type. **WebChat opens the microphone for a recorder, not for a phone call**, which is a mobile constraint rather than a preference: `echoCancellation` and `noiseSuppression` are asked for as false, keeping an Android device off its voice-call audio route, whose processing is tuned for a person listening down a line and reaches whisper as garbled speech. **`autoGainControl` stays on**, and that asymmetry was paid for: asked for as false, an Android phone held in the hand and spoken to normally returned a recording peaking under a tenth of full scale, flat enough to read as a room rather than a person. It works on the level rather than the shape of the sound, which is the one thing a phone microphone cannot supply for itself. A capped, upward-only lift when the WAV is built remains as a floor under it. The graph runs at the device's own sample rate, with the worklet resampling to 16 kHz behind its own anti-aliasing filter, because asking for a 16 kHz `AudioContext` puts a resampler nobody here wrote inside the capture path and it does not treat a phone's microphone as it treats a laptop's. **The chain must still end at `ctx.destination`** (through a gain of zero — nothing is meant to be heard): Chromium renders a graph that reaches no output, Android does not, and every node in it then goes unpulled and records silence. No node in that chain may be left as a leaf, and no desktop test can catch it if one is. WebChat's dictation ticket sits beside the upload and download tickets but is space-scoped and counts no slot, and it carries the recording cap and the mis-tap floor so a dictation obeys the numbers the server holds when it starts rather than what the first render could learn — composer text must not force a conversation into existence or spend an attachment slot — and the transcription endpoint stores nothing. Telegram gates a transcript on the same confidence floors the satellites use and replies rather than staying silent; WebChat deliberately does not, because the person reads the words before sending them. Both record the existing `VoiceMetric` speech-to-text members under a `Channel` dimension, so the dashboard separates satellite, chat and Telegram with no new metric family.

- **Attachment capability is discovered, not configured, and it is refused twice.** `OpenRouterModelCapabilities` asks the provider's model list at startup and hourly; `AgentCatalogBuilder` stamps the accepted kinds onto each catalog entry, and `RunAsync` takes the catalog as a **function** so a refresh reaches channels through the registration that already exists (a connection re-registers a catalog whose wire shape changed). `AttachmentCapability` (`Domain/DTOs/Channel/`) is the one resolution the composer, `ChatHub` and `TelegramBotService` all use, so they cannot disagree about which model is refusing; the agent does not check a third time. Permissive wherever the catalogue is silent — a blip at the provider must not remove the feature. Telegram accepts `register_agents` for this alone (nothing else there consumes the catalogue, and it has no per-message model override), and its refusal is per-turn: no turn is emitted, because an answer that silently ignores what was sent is worse than no answer.
