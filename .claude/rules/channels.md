# Channel Architecture

See also: `.claude/rules/chat-hub.md`, `.claude/rules/chat-queue.md`, `.claude/rules/telegram.md`, `.claude/rules/channel-attachments.md`.

Transports are independent MCP channel servers the agent dials (`ChannelEndpoints`); a new transport is a new channel server and zero agent changes. `ChannelProtocol` is the one spelling of the wire. **One sanctioned exception:** `McpChannelConnection.SendReplyAsync` hand-builds its arguments instead of calling `ChannelProtocol.ToArguments` (per-chunk hot path). Its keys and values must stay byte-identical to what `ToArguments` emits, so a property added to `SendReplyParams` goes into that dictionary in the same change. No other call site may copy this shape.

- **Being a channel server is one call:** `IMcpServerBuilder.AddChannelServer(policy, …)` (`Mcp.Hosting/ChannelServerExtensions.cs`). A transport writes only its reply-sending logic.
- **`DeliveryPolicy` is a required argument**: `Broadcast` (SignalR, Voice), `BufferAlways` (Telegram), `GateOnLive` (Scheduling, Library, Sugary). What each means is on the enum (`Mcp.Hosting/DeliveryPolicy.cs`); `ChannelReceiveContractTests` asserts each server's declared policy.
- **Liveness is the return value of emitting**, never a separate property (`EmitAsync`/`EmitCancelAsync`). The freshness window stays internal to `ChannelInbox`; hand-copied emitters are how the stale-subscriber defect recurred.
- **A batch is handed out until its poller says it arrived.** `channel_receive`'s optional `poller`/`received` and `ChannelReceiveResult.Batch` let `ChannelInbox` redeliver a batch whose answer died on the wire (`PollerCursor`, `Subscriber.Settle`; mechanics in `ChannelInbox.cs` and on `McpChannelConnection._poller`). The batch stays handed out until that poller's next poll: naming it releases it; naming an earlier one redelivers that one first, ahead of anything newer; any **other** poller polling releases it undelivered, since that poller (a restarted agent, a fresh connection) may have taken and answered it. There is no timer: the next poll settles it. Numbers start from the subscriber's clock, so a restarted server never reuses one the agent still names. The agent mints `poller` once per connection, kept across its reconnects and tunnel openings, and names as `received` only a batch it dispatched whole (0 before the first), so nothing is delivered twice; a poller naming nothing has every batch committed as drained. Both arguments stay optional (`ChannelReceive_AnArgumentItDoesNotKnow_IsIgnored`).

- **Which agent answers is configuration, never array order.** `ChatMonitor.RouteToAgentAsync` stamps an agent on a message that named none **before** grouping, so group key, agent, context and memory name the same one. Precedence: a satellite's turn goes to its household's voice agent (`HouseholdAgents.VoiceAgentOf`), the household being the one whose own voice server heard it, else the verified person's (`HouseholdChannels.HouseholdOfTurn`); else the channel's default (`agentDefaults.byChannel`, `Agent/appsettings.json`); else the principal's household's `defaultAgent`, which is how the shared Telegram bot reaches a household's agent. A channel that names an agent keeps it; defaults are fallbacks. `MultiAgentFactory` builds by id or refuses (`AgentNotFoundException`), never the first configured agent. On an attach-only channel that refusal is answered (`ConversationGroup.NoAgentHereAnswer`) so a satellite is not left silent. A voice server names no agent of its own (`VoiceSettings.AgentId`, unset unless an operator pins one); `TopicMintingApi` mints a voice conversation's topic under the same voice agent. Whoever serves a satellite answers under the voice rules: a group keeps its opening channel's prompt sections (`PromptManifest.ForChannel`). Refusal wording is spelled once in `RefusalAnswers`; one added there must be taught to voice's `SpokenRefusals`. `AgentAppSettingsTests` holds every channel default to a real agent.
- **A turn's agents are its household's.** `MultiAgentFactory.CreateAsync` builds from the turn's household (`IAgentDefinitionProvider` over `IHouseholdAgentSource`, `.claude/rules/household-config.md`). A turn acting for nobody runs the home's agents and reaches no household's servers, unless it came through a household's own channel server or a fire its server keeps under a household (`HouseholdChannels.HouseholdOfTurn`, `.claude/rules/own-servers.md`). `ChannelAgentCatalogs` registers the home's catalogue with a dialled channel and a household's with its own channel server.
- **A conversation group is anchored and built by its first turn.** `ConversationGroup` is constructed in production only by `ChatMonitor` (`docs/adr/0006-a-group-is-anchored-and-built-by-its-first-turn.md`). A chat command is not a turn and builds nothing; anchor reuse is decided by identity against the anchor message, never by a message counter.
- **The monitor is supervised, and every ending costs a wait.** `ChatMonitoring` restarts a monitor that returned as well as one that threw, on `MonitorRestartSchedule`; the backoff is forgiven only by a run that lasted (`MonitorRestartPolicy.HealthyRun`), so repeated short deaths are one failure. Each restart is published as an `ErrorEvent` under `MonitorFault.RestartErrorType`; shutdown reports nothing. `MonitorFault.IsFatal` (classified on `MonitorFault.Root`) names only values the code cannot use, never a dependency that is down (Redis, a channel); those end the host instead of retrying.
- `DeliveryTarget.Minted` means "minted while resolving this turn" (reused anchors carry it cleared); `AnnounceTurnStartAsync` skips exactly those targets and needs no correcting flag.
- `create_conversation` with `existingConversationId` doubles as the channel-agnostic turn-start announce for an agent-initiated message (`Origin` set) into an existing conversation (`DeliveryTargetResolver.AnnounceTurnStartAsync`). Each channel applies its own semantics: SignalR opens a live stream and sends `OnStreamStarted` before reply chunks arrive; voice no-ops on a live satellite session, else binds the turn as an announcement.

- **A channel connection runs itself.** `IMcpChannelConnection.RunAsync` owns connect, register, health and reconnect; `ChannelConnectionHost` only starts one run per endpoint. **A dialled server's calls have no HttpClient timeout** (`McpClientManager.DialledHttpClient`, as the tunnel's client): an approval waits on a person, and the 100 s default refused every one unanswered by then. The caller's token bounds each call; the health probe is bounded by its own interval, and a failed probe reconnects, which ends whatever the old client held. A household-server endpoint has a connection per household (`.claude/rules/own-servers.md`, "A household's channel server").
- **The connections are a live set, chosen by household.** Each connection serves a `ChannelHousehold` (`Every` when dialled by URL, `Own` for a household server's tunnel). `LiveConnectionSet` only grows; consumers watch it (`WatchAsync`) rather than read it once. Anything picking a connection by channel id picks it by household too, through `HouseholdChannels.Serving`/`Find`, and never reaches another household's connection. Being **not connected** is five behaviours stated on `IMcpChannelConnection` (`docs/adr/0011-not-connected-is-five-behaviours-and-stays-that-way.md`); `CreateConversationAsync`'s null is load-bearing for `DeliveryTargetResolver`. A server's tool set is fixed per connection generation (`docs/adr/0012-a-servers-tool-set-is-fixed-for-a-connection-generation.md`), and `OffersToolAsync` is also refreshed by every health check's listing.
- **The registered catalogue is never read as a household's list.** `register_agents` sends it on every connect and reconnect, but whatever shows or checks a person's agents asks `HouseholdAgentCatalogue` (`Domain/Agents`): the picker (`ChatHub.GetAgents`; `ValidateAgent` is false for an agent not the household's), the hub's attachment guard, Telegram and Sugary, each on the person's own proof (the session's assertion, the Telegram sender's, the Sugary request's). `OnAgentsUpdated` carries **no list** (`AgentsUpdatedNotification`), so no household is sent the home's names, and the client asks `GetAgents` again; a household's agents save pushes it to that household's connections alone (`HouseholdAgentsAnnouncer`). A household whose agents cannot be read just now is never answered with the registered catalogue: Telegram and Sugary answer no agent, and the hub refuses the call (`ChatHub.HouseholdViewAsync` throws `HubException`). Only the home's paths read the registered catalogue directly, by design: the schedules mount for a call acting for nobody, and a kept file from before files named their agent (`.claude/rules/channel-attachments.md`).
- **`showsReasoning: false` in `ChannelEndpoints` (voice) means the channel is sent no reasoning** (`IChannelConnection.ShowsReasoning`, filtered in `ReplyDispatcher`): every reply is awaited before the next update is pulled, so a delta the channel only drops is a round trip its answer waits behind. A channel's `FirstReply` is then its first words. Omitted means shown.
- `attachOnly: true` in `ChannelEndpoints` (voice) makes `DeliveryTargetResolver` order that channel last; it never mints the primary target. When only an attach-only channel delivers, the agent mints the topic itself (`IConversationFactory`) for the verified principal and hands it over as `existingConversationId`.
- **Dual-role** servers are both a channel and a tool/filesystem server (`mcp-scheduling`, `mcp-library`, `mcp-homeassistant`, `mcp-sugary`, `mcp-timers`). Their channel-protocol tools are hidden from the LLM, and dialling one as a tool server does not make an agent its channel's consumer: `agentDefaults` alone routes the channel (Jonas dials `mcp-sugary` for `/sugary`; the app's estimates still go to `sugary`).
  - `mcp-sugary` is the one with a person waiting on the reply: a turn per estimate under its own `TurnKey`; it continues only conversations it opened (`OpenEstimates`, in memory, within `FollowUpHours`), answering anything else 410 before a turn is sent so the app estimates afresh. A meal's follow-up answers are turns on the first estimate's id carrying no attachments (the first turn's photos hydrate from history). A label refuses before the send when `LabelModel` is not patchable (`LabelEndpoints.NotSwitchable`), and one the model declines returns to the app as 422 with its reason. Clips: `.claude/rules/channel-attachments.md`.

- **An approval can say why it is asked.** `ToolApprovalRequest.Screen` carries codes (`ExecScreenCodes`), not prose, so each channel says them in its own language (`ExecScreenReasons.English` for Telegram and WebChat, Spanish on voice). `Screen` is optional, and every channel skips an unknown code, never showing it raw (`ExecScreenReasons`). `as_person` is not the screen's (`.claude/rules/browsing-as-person.md`).
- **An approval is its asker's, and is answered wherever they are.** `ApprovalRelay` (`Domain/Monitor`) asks on the anchor (`request_approval`) and, for a turn acting for an account, offers it (`offer_approval`) on the deployment's channels and the turn's household's own, never another household's; voice and the dual-role servers advertise none. The chat client gets `OnApprovalOffered` on the account's `account:{userId}` group in any space, a Web Push only when none is open, and `GetOfferedApprovals` to catch up (`ApprovalService`); Telegram, the asker's private chat by the asking agent's bot. The first answer wins: every other channel is told by `settle_approval`, which carries the answer (so an anchor that asked still lets the call through and shows what was approved elsewhere), and only then is its call cancelled, which is how a waiting prompt stops (`McpChannelConnectionApprovalMetaTests`). **The anchor is authoritative:** its answer, its refusal and its time-out all settle every offer. Only an anchor that could show the question to nobody (SignalR with no live session, voice with no satellite) answers `ChannelProtocol.NoAnswer`, which leaves it to the offers for `ApprovalRelay.UnshownWindow` before refusal (ADR 0035: a question nobody can see must not hold the turn); an offer unanswered or closed ends nothing, and a failed (not connected) anchor fails the call unless an offer answers first. `ApprovalAsk` carries the turn's `ConversationContext` as a field, never the call in flight; the asker is `Principal.Of(turn)?.Account`. Whoever sees all is never offered another person's question. `ChannelProtocol.ParseApprovalAnswer` is the one reading of a channel's answer. Known edge: an anchor that answers at once (a dual-role server) still has the offers sent and immediately settled.
- **An alert is its person's, and rings wherever they are.** `AlertRelay` (flow in its header and `.claude/rules/timers.md`) offers a server's alert (`IAlertChannel.Alerts`, never a turn) with `offer_alert` on the deployment's channels and one household's own only (`HouseholdChannels.Serving`: the raising server's household, else the owner's — never another household's server of the same name), signed for nobody and naming the owner. The first `dismissed` (`ChannelProtocol.AlertDismissed`) settles every other channel with `settle_alert`, the raising server included; a stop from the raising server settles every channel showing it; an alert shown nowhere is settled at its origin at once; one nobody dismisses rings out after `AlertRelay.RingWindow`. `IAlertChannel` stays beside `IChannelConnection`, not in it; both tools are hidden from the model (`ThreadSession`).
- **A person's turn carries the accounts service's assertion, and the agent believes only that** (sources: `.claude/rules/person-assertions.md`, "Channels and the agent"). `ChannelMessageNotification.Assertion` is carried untouched; `ConversationGroup.AdmitAsync` verifies it before queueing, and the principal's `Account` is then the assertion's whatever the channel wrote; a turn whose assertion fails is never queued, built or recalled for. A fire acts for its verified delegation's person or for nobody (`.claude/rules/delegations.md`, "Deferred turns").
- **A suspended household starts nothing.** `ConversationGroup` asks for **every message** (`HouseholdStanding`, `Domain/Monitor`, the one rule a built app's read is held to as well), not when the agent is built, since a group outlives its turns, for each household it names — for a fire also `ChannelMessage.HouseholdId`, believed for this alone — and refuses as `HouseholdSuspended`: a person's turn is answered `ConversationGroup.SuspendedAnswer` (an `Error` then `StreamComplete`) so their channel shows why, a fire only on the errors feed; nothing is built, recalled or minted. A fire naming no household and acting for nobody (a download, a home's watch) still runs. **A household that turned Sugary off starts no Sugary turn** (`FeatureRefusalAsync`: `FeatureOff`, answered `RefusalAnswers.SugaryOff`), rather than estimated without the rules the withheld server serves. **A household the agent cannot read just now is refused too** (`StandingUnreadable`, answered `ConversationGroup.UncheckedAnswer`), never let through and never called suspended. Channels refuse earlier where they can (`.claude/rules/channel-identity.md`, "Resolving a channel identity"), but this refusal is what tells an already open chat client.
- **The principal carries the account beside the channel's user id.** `UserId` is the channel's label and nothing decides by it; `Principal.Of` reads the stamped principal alone, never a context's own `UserId`, and on a server that principal is the call token's (`.claude/rules/service-identity.md`). A fire's principal is built from its verified delegation; whatever its server stamped is a label.
- `ChannelMessageNotification.ConfigPatch` overrides model and effort per message, honoured only for `patchableModels` (`Agent/appsettings.json`, surfaced to clients on `AgentCatalogEntry`); off the list `McpAgent` runs its own model, so a channel that must not get that checks `PatchableModels` itself before the send.
- `ChannelMessageNotification.ResponseFormat` asks for that turn's final answer in a strict schema (`docs/adr/0044-a-channel-message-may-ask-for-its-answer-in-a-schema.md`). `McpAgent` reads it off the turn's own user message only, never the history; a worker never inherits it.
- **`ChannelMessageNotification.AppTurn` is a built app's ask** (`Domain/DTOs/Channel/AppTurn.cs`: `AppId`, `Instructions`, `Servers`), believed only from the deployment's `apps` channel endpoint (`AppTurns.IsAppsEndpoint`: channel id `AppChannels.Apps`, a URL endpoint, never a household's server of that name, never a fire); anywhere else it is dropped with a warning and the message is an ordinary turn. That channel starts app turns alone (a message on it without one is refused `TurnAdmission.NotAnAppTurn`), is never routed to a default agent, and an ask is admitted on the viewer's `apps` assertion as a person (the guest is `NotAPerson`), then standing, then `FeatureRefusalAsync`: the household's `apps` feature (`RefusalAnswers.AppsOff`) and the named agent among the household's own (`RefusalAnswers.AgentGone(id)`, asked per ask). Every refusal is answered (`Error` then `StreamComplete` under the ask's `TurnKey`); `RefusalAnswers.CodeOf` gives each its code. An honoured ask loses `ReviewCopy` and `ReplyTo`, so no topic is minted; it is stamped on the turn's user message as `ResponseFormat` is, and `McpAgent` reads it off that message alone: the app's instructions in place of the persona (`PromptComposer`, `PromptContext.AppInstructions`), no tools, no skills, no offline line, and no session dialled (nor a warmup for a group an ask opened). Memory skips it (`.claude/rules/memory-architecture.md`); its usage carries `TokenUsageEvent.Channel` and `AppId`.
