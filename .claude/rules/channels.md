# Channel Architecture

Transports (WebChat, Telegram, Voice, Scheduling) are independent MCP channel servers; the agent connects as an MCP client via `ChannelEndpoints`. Wire serialization is centralized in `ChannelProtocol` — the shared `JsonSerializerOptions` plus the typed records, and the one place the inbound methods and outbound tool names are spelled. A new transport needs only a new channel server — zero agent changes. **One sanctioned exception to the one-spelling claim:** `McpChannelConnection.SendReplyAsync` hand-builds its argument dictionary instead of going through `ChannelProtocol.ToArguments`, because `send_reply` fires once per streamed content chunk (hundreds per response) and the reflective `SerializeToDocument` + per-property `Clone` is measurable there. The divergence is deliberate and carries an obligation: the hand-built keys and values must stay byte-identical to what `ToArguments` would emit (same camelCase keys, enum values spelled as `JsonStringEnumConverter` spells them), so a property added to `SendReplyParams` must be added to the hand-built dictionary in the same change. No other call site may copy this shape.

- **Being a channel server is one call.** `Mcp.Hosting`'s `IMcpServerBuilder.AddChannelServer(policy, subscriberId?, errorResult?, noOutboundSurface?)` wires the `ChannelInbox`, the shared `channel_receive` long-poll tool, the call-tool error filter and the sealed `ChannelNotificationEmitter`. It sits beside `AddToolServer`, and the difference between the two kinds of server is exactly what those two calls differ by. A new transport writes only its reply-sending logic.
- **`DeliveryPolicy` is a required argument.** `Broadcast` fans out to every registered subscriber whatever its freshness, so an idle-but-unpruned subscriber still receives; with no subscriber registered at all the item is discarded (SignalR, Voice). `BufferAlways` targets a known subscriber id and creates its queue on demand, for a transport that cannot tell a sender to retry (Telegram). `GateOnLive` enqueues only when someone is actually polling, for callers that settle a durable record on a confirmed delivery — buffering on a failed emit would keep the record *and* leave a duplicate (Scheduling, Library) — and for a caller waiting on its own request, who is better told at once that nobody is listening (Sugary).
- **Liveness is the return value of emitting**, never a separate property: `EmitAsync`/`EmitCancelAsync` answer "was anyone listening?", with the freshness window internal to `ChannelInbox`. The same stale-subscriber defect was fixed three times across six hand-copied emitters before this. `ChannelReceiveContractTests` drives the channel-capable rows of that table and asserts each declared policy.

- **Which agent answers is configuration, never array order.** `AgentDefaults` (`agentDefaults` in `Agent/appsettings.json` — a per-`ChannelId` map plus a `fallback`) names the agent for a message whose channel named none, and `ChatMonitor` stamps it onto the message **before** the grouping, so the group key, the agent built for it, the context stamped on the turn and the memory written from it all name the same one. `MultiAgentFactory` builds by id or refuses: it never falls back to the first configured agent, which is how a general request used to be answered by the download assistant (`jack` is simply listed first). A default naming an agent nobody configured fails the host at startup rather than one message at a time. A channel that has an agent of its own still sends it — the defaults are what a channel falls back to, not what overrides it.
- **A conversation group is anchored and built by its first turn.** `ConversationGroup` (internal to `Domain/Monitor`, one per conversation and agent, constructed in production code only by `ChatMonitor`) owns the pending-turn queue, the command dispatch, the delivery anchors, the agent, the restored thread and the warmup, and establishes all of it on the group's **first turn**. A chat command is not a turn, so a group whose messages are all commands builds nothing — a `/clear` on a conversation with no live group costs no agent, no thread read and no MCP connection. The thread context stays eager because disposing it is how a command ends the group; `ChatThreadResolver.ClearAsync` wipes persisted state unconditionally. Whether a turn reuses the anchors is decided by identity against the anchor message, never by a message counter. See `docs/adr/0006-a-group-is-anchored-and-built-by-its-first-turn.md`. The monitor keeps merging the channel streams, grouping the messages, delivering each update and publishing first-reply latency.
- **The monitor is supervised, and every ending costs a wait.** `ChatMonitoring` restarts `ChatMonitor` on a doubling, jittered delay (`MonitorRestartSchedule`), and it does so for a monitor that *returned* as well as one that threw — a merge whose channel streams all ended is the same hot loop as a fault, with nothing in the log. The backoff is forgiven only by a run that lasted (`MonitorRestartPolicy.HealthyRun`), because a monitor dying after two seconds ten times running is one failure and not ten first ones. Each restart is published as an `ErrorEvent` under `MonitorFault.RestartErrorType`, so the errors feed an operator already reads is where a flapping agent shows up. Shutdown is neither: cancellation unwinds quietly and reports nothing, which it did not before. `MonitorFault.IsFatal` names the faults no restart can clear — a value the code cannot use, never a dependency that is down — and those end the host instead, on the reasoning that a container crash is visible and an infinite retry is not. It classifies `MonitorFault.Root(ex)` because the merge hands a fault on its own side over wrapped.
- `DeliveryTarget.Minted` means "minted while resolving this turn", so reused anchors carry it cleared and `AnnounceTurnStartAsync` needs no correcting flag: it skips exactly the targets marked minted.
- `create_conversation` doubles as the turn-start announce when given `existingConversationId`: the conversation group calls it channel-agnostically for agent-initiated messages (`Origin` set) into existing conversations, and each channel applies its own semantics — SignalR opens a live stream + `OnStreamStarted` before reply chunks arrive; voice no-ops on a live satellite session, else binds the turn as an announcement.
- **A channel connection runs itself.** `IMcpChannelConnection.RunAsync(endpoint, catalog, ct)` owns connect with retry, register the catalog, watch health, reconnect with retry and re-register; `ChannelConnectionHost` reads the endpoint map and starts one run per endpoint, and knows nothing else about the order. Being **not connected** is five behaviours, one per member, stated on that interface (`docs/adr/0011-not-connected-is-five-behaviours-and-stays-that-way.md`) — `CreateConversationAsync`'s null is load-bearing for `DeliveryTargetResolver`. The far end's tool set is asked for once per **connection generation** and discarded on reconnect (`docs/adr/0012-a-servers-tool-set-is-fixed-for-a-connection-generation.md`).
- On connect and every reconnect the agent registers its `AgentCatalogEntry` list via `register_agents`; channels use this single source instead of duplicated `Agents` config, and SignalR broadcasts `OnAgentsUpdated` so WebChat refreshes live.
- `attachOnly: true` in `ChannelEndpoints` (voice) makes `DeliveryTargetResolver` order that channel last — it attaches to conversations minted elsewhere, never mints the primary target.
- **Dual-role** servers are both a channel and a tool/filesystem server (`mcp-scheduling`, `mcp-library` download alerts, `mcp-homeassistant` watch fires, `mcp-sugary` her app's estimates); their channel-protocol tools are hidden from the LLM, and an agent dialling one as a tool server is not thereby its channel's consumer — `agentDefaults` alone routes the channel (Jonas dials `mcp-sugary` for the `/sugary` mount and the `sugary-log` skill; the app's estimates still go to `sugary`, which dials the same server for its estimating prompt alone, `noTools`). `mcp-sugary` is the one whose channel has a person on the other end of a reply: it opens a turn per estimate under a `TurnKey` of its own, collects the reply chunks for that key, and answers the app's waiting request with the parsed whole or an error. A meal is one conversation: her answers are further turns on the id the first estimate returned, carrying no attachments (the first turn's photos are hydrated from history), and the server continues only a conversation it opened itself within `FollowUpHours` of its last turn (`OpenEstimates`, in memory) — anything else is answered 410 before a turn is sent, and the app then estimates the meal afresh. A nutrition label is a turn of its own conversation, asking for the `nutrition_label` format and carrying a config patch naming `LabelModel` (a stronger model than meals use); its photo's capability is asked about that model, and a label the model declines comes back to the app as 422 with the model's reason. A meal may be filmed: the app posts one `clip` part as the phone recorded it, and before anything is kept the server reads it with ffmpeg (`McpServerSugary/Clips`, the image carries it; Domain has no codec) through the QuickTime/MP4 and Matroska/WebM demuxers alone, refuses one over 20 s (half a second's grace, then cut) or one that is not a clip with a reason the app shows, makes it H.264 in MP4 with its short side at most 540 lines, no sound and no metadata, and takes up to eight stills from the phone's own picture at the app's 1568 px — the sharpest moment of each eighth of the clip by `blurdetect`, a stretch blurred against the clip's sharpest giving none (`StillChoice`). Clip and stills go to the upload store under the meal's conversation, and the turn carries her photos, the clip naming its stills, and the stills (ADR-0045 then picks per model). The request's body limit is raised for that route alone to the clip's ceiling (`MaxClipBytes`) and the photos'.
- **An approval can say why it is asked.** `ToolApprovalRequest.Screen` carries the agent's exec screen codes (`ExecScreenCodes`: `not_requested` with the danger that made it worth asking — `destructive`, `sends_out`, `runs_downloaded` — or `unjudged`) for an exec that would have run unasked and was flagged. The screen asks only about a command that is both not what the person asked for and dangerous, on either machine. One code is not the screen's: `as_person`, on a call carrying `asMe: true`, which is asked by its site whatever the whitelist says (`.claude/rules/web-browsing.md`). Codes rather than prose, so each channel says them in its own language beside the approval text it already has: Telegram and WebChat through the one English line `ExecScreenReasons.English` (a line above the keyboard, a line on the card, drawn as text), voice as a Spanish sentence spoken before the question (`.claude/rules/voice.md`). A request with no `Screen` renders exactly as it always did, and an unknown code is skipped, never shown raw.
- **The chat hub's person is the proxy's, settled as the connection arrives.** Caddy's `forward_auth` asks the accounts service's session check before every request to the hub and its upload and dictation endpoints, and copies its three headers (`ForwardedAccount` in `Domain/Security`: `X-Ziggurat-User`, `-Tenant`, `-Roles`) over anything the client sent. `RegisteredConnectionFilter.OnConnectedAsync` reads them off the connection's request and keeps the `ForwardedAccount` in `Context.Items`; a connection without all three is closed with "not signed in" before it can call anything, and its `InvokeMethodAsync` refuses any call on a connection holding none, so a new hub method is covered by default. There is no registration call: the browser has nothing to say about who it is, and the client asks the hub nothing until it is connected. A user message's `SenderId` and the push subscriptions' key are the account's opaque user id. The hub believes the headers because only the proxy reaches it, so a host run with no proxy in front (`Local: MCP Channel SignalR`) refuses every connection.
- **A chat-client turn acts for the account and goes by its name.** The hub stamps the turn's `ChannelMessageNotification.Principal` itself — `ForwardedAccount.PrincipalOn("signalr")`: channel `signalr`, the account's id as the channel's user id, and the `Account` (tenant, user) beside it — so it needs no resolution call: the headers are the account. Its `Sender` is the account's display name, asked once as the connection arrives (`RegisteredConnectionFilter`, DI-activated, through `IAccountResolver` with this server's own `Mcp:SharedSecret`, `.claude/rules/accounts.md`) and kept in `Context.Items[ChatHub.DisplayNameItem]`; a name the accounts service could not give leaves the turn under the account's id and never refuses the connection. `Sender` is a label and never a key — except that memory still reads it until memory follows the account. What must find the person reads the account instead: `IAgentFactory.Create` takes the turn principal's `Account`, under whose user id a person's custom agents are filed, and the history a topic reads back names a person's own message by the account it acted for (`ChatMessage.GetAuthorId()`: the persisted context's `Principal.Account` on a turn with no `OriginKind`, else the sender), because the client tells its own messages by the account's id.
- **A topic is its owner's unless they share it, and an owner may grant someone every topic of the household.** `TopicMetadata` records `OwnerId`, `TenantId`, `Shared` and `OwnerName` (the name the owner went by when it began — a label for "started by", never a key). `TopicViewer` (`Domain/DTOs/WebChat`, built by `ForwardedAccount.Viewer`) is the one rule, which the hub, the store and the chat client all apply: a viewer **sees** their own topics, every topic nobody owns (a voice guest's, and one from before topics had owners — treated as shared until the migration marks it so), the shared topics of their household, and with the `sees-all` role every topic of their household; they **may change** (continue, rename, delete, stop, upload into, mark read) only their own, shared and unowned ones — seeing every topic is reading, never deciding. `GetTopicPageAsync`/`SearchTopicsAsync` take the viewer and fill a page from below whatever they passed over (`RedisThreadStateStore.FillPageAsync`), the cursor being the entry the page filled on, so another person's private topics never cut a page short; the RediSearch schema is untouched and hits are filtered the same way. Every hub call that names a topic, a session or an approval resolves the stored topic first and refuses one the caller may not see with "No such conversation." — the words for one that does not exist; `StartSession` answers false instead. A conversation **no topic holds** is read by nobody (`GetHistory` answers empty, since Telegram's numeric ids are reachable by naming them) and opened, saved or deleted only when it is the one its own topic id names (`ConversationIdGenerator.CreateFor`), so a saved topic never adopts another channel's or another person's conversation; a session over such a conversation is a fresh topic whose id only its opener knows. A new topic saved from the chat client is the connection's person's, private, whatever the browser sent; `SetTopicShared` is the owner's alone. Approvals: a pending one is shown to whoever sees its topic, and until ticket 13 records the asker it is answered by the topic's owner, on a shared topic also by whoever's turn is running (the stream's current sender), and on an unowned one by anyone who sees it — anyone else is answered false and the prompt stays pending. **Reach:** every connection joins `space:{slug}` and exactly one of `space:{slug}:user:{id}` or, holding `sees-all`, `space:{slug}:sees-all:{tenant}` (`TopicAudience`); a private topic's news (created, deleted, stream started, approval resolved) goes to its owner's group and the sees-all group, which no connection is in both of, any other topic's to the space, and a share change to the whole space so each client adds or drops the row by `TopicViewer`. A private topic's finished-reply push goes to its owner's subscriptions in the space alone (`SendToPersonAsync`). **Review copies** are owned by the turn: the agent hands `create_conversation` the turn's `Principal` (`IChannelConnection.CreateConversationAsync`), and `ConversationFactory` makes a topic over it the principal account's, private, or the household's, shared, for a turn acting for none — the asking channel still never names where the copy goes nor whose it is (ADR 0046). Voice mints its own conversations' topics the same way (`.claude/rules/voice.md`), and Sugary's copies are shared until its turns carry the account.
- **The principal carries the account beside the channel's user id (expand, before each channel moves over).** `Principal(ChannelId, UserId, Account?)`: `UserId` keeps its meaning — the channel's own name for the person (a Telegram username, a voice profile, the chat client's account id) — which the identity map, the Telegram approval router (`AnswerersOf`), `AsMeGate` and the eval harness still match on, and `Account` is the accounts service's (tenant id, user id), set where the channel knows it. The chat client sets it, and so does voice for a recognised speaker (`.claude/rules/voice.md`; the voice guest stamps a principal with none); Telegram turns carry none and read exactly as before, through `BuildConversationContext`'s fallback `Principal(channel, sender)`. It rides wherever the principal does with no code of its own — the notification (`ChannelProtocol`), `McpChannelConnection`'s mapping, `ConversationContext` in `_meta` and on the persisted message, a schedule's `CreatedBy` (Redis, default JSON options) and so a fire's principal, and a login wake's — and a record from before it, with no `account`, reads as the channel's user.
- **Telegram admits a number, and an approval is the asker's.** `ChannelSettings.AllowedUserIds` (`ALLOWEDUSERIDS__<n>` in `DockerCompose/.env`) lists numeric Telegram user ids, and a message is admitted only when `From.Id` is on it — never by username, chat name or first name, which their owners can change and Telegram can reassign. The turn's `Sender` stays the username (the id as a string for a person with none), because memory and the identity map are keyed by it. As the bot admits a message it records sender → id on `ApprovalCallbackRouter`; `request_approval` reads the turn's `ConversationContext` off the hop's `_meta`, and a person's turn (`OriginKind` null) is answerable by its principal's recorded id alone, a fire's by any listed id, and a turn with no context or an unrecorded sender by nobody (it times out denied). Any other tap is answered "This approval isn't yours" and the approval stays pending. An approval id is a whole GUID, 32 hex characters, so `tool_always:<id>` is 44 bytes of Telegram's 64.
- `ChannelMessageNotification.ConfigPatch` (`AgentConfigPatch`: model + reasoning effort) lets a channel override agent config per message; SignalR populates it from the person's picker, and Sugary from its `LabelModel` setting on a nutrition label's turn. Whitelist: `patchableModels` in `Agent/appsettings.json`, surfaced to clients through the widened `AgentCatalogEntry`. A model off the list is never honoured: `McpAgent` logs the rejected patch and runs its own model, so a channel that must not be answered by the agent's own model (Sugary's label) checks the registered catalogue's `PatchableModels` itself and refuses before the send.
- `ChannelMessageNotification.ResponseFormat` (`ResponseFormat`: schema name + strict JSON schema) travels beside the patch and asks for that turn's final answer in a schema; Sugary populates it. `McpAgent` reads it off the turn's own user message only — the persisted message keeps it, the next turn never looks back for it — the schema goes out verbatim and strict, a strict schema adds `provider.require_parameters`, tools may still be called first (Sugary's agent has none, so its turns are one answer), and a worker never inherits it. `docs/adr/0044-a-channel-message-may-ask-for-its-answer-in-a-schema.md`.
- **A channel may ask for a review copy, and the review host attaches to the conversation it anchors.** `ChannelMessageNotification.ReviewCopy` (a `Title`) asks for the conversation to be shown on the deployment's one review host (`channelEndpoints[].hostsReviewCopies`, `signalr`; `IChannelConnection.HostsReviewCopies`). `DeliveryTargetResolver` makes it the agent-initiated fan-out with the sending channel first — `[channel on its own conversation, host with none]` — so the channel's conversation stays the delivery identity, and resolves it again on every turn. SignalR's `create_conversation` given an existing id *and* a topic name mints a topic over that very conversation when nothing holds it (so the topic reads the history the agent writes there) and announces the turn on it after; the anchoring channel must therefore spell its ids as a `ConversationIdentity` (Sugary does). The message's files are copied in the background, fetched from the channel and handed to the host by `store_attachment` under the same reference id, which SignalR keeps under its upload rules and never writes over; the shared history's references then download from WebChat as its own do. A clip is copied and its stills are not (`ClipStills.Without`), so the topic shows what a video model was sent: SignalR keeps a review copy's `video/mp4` (`ReviewCopyMediaTypes`) up to `MaxReviewCopyClipBytes` (20 MiB, which fits one call's base64 under Kestrel's 30 MB body limit), while a person's upload still refuses video; the client plays it as `<video controls>` on the ticketed download, which answers byte ranges, and hides the stills a clip names. Sugary asks on every turn it opens: a meal's first estimate, each of her answers on it (under the title the first estimate asked for, which `OpenEstimates` keeps, since an answer carries no words of the meal), and a nutrition label. `docs/adr/0046-a-channel-may-ask-for-a-review-copy-and-webchat-shows-the-conversation-it-anchors.md`.
- **An attachment crosses every boundary as a reference; bytes cross as few as possible.** `ChannelMessageNotification.Attachments` / `ChannelMessage.Attachments` carry `AttachmentReference` (where the file rests, media type, filename, size) and are transport-neutral, so SignalR and Telegram both populate them and nothing above the channel knows which transport a file came from. **Where the bytes rest is the channel's own answer, not something being a channel requires.** SignalR keeps an upload store: bytes go browser → store (HTTP, one file per request, ticket-scoped) → agent. Telegram stores nothing — a `file_id` is a durable per-bot handle, so the reference is `<agentId>/<file_id>` and the fetch is a `getFile` plus a download at the moment the agent asks, with no volume, no sweeper, no retention and no attachment settings on that channel (`docs/adr/0022-a-channel-whose-transport-keeps-files-has-no-upload-store.md`; the named escape hatch if fetching proves slow is a bounded in-memory cache there, deliberately unbuilt). Sugary keeps an upload store of its own (files in its own volume beside the SQLite log, never in it), swept on age alone at the shared `attachmentRetention` because a meal's conversation is a few minutes of turns; it refuses a photo before storing it when the model the turn will run on — the agent its turns are routed to (`SugarySettings.Agent`, pinned equal to `agentDefaults.byChannel.sugary`), or the label model on a label's turn — cannot see one, by the shared `AttachmentCapability` rule over the catalogue the agent registers. Either way the agent asks by `fetch_attachment`, the sixth channel-protocol tool, hidden from the model like the rest — `ThreadSessionBuilder` strips it (and `store_attachment`, the seventh, a review copy's way in). Neither is ever mounted; see `docs/adr/0021-the-upload-store-is-not-a-mount.md`. The persisted `ChatMessage` keeps the reference and never the bytes, and `AttachmentHydration` (`Domain/Agents/`) puts them back on the way to the model only, beside `TurnDecoration` and for the same reason — `docs/adr/0020-an-attachment-is-stored-once-and-hydrated-on-the-way-out.md`.
- **A clip is a video attachment that names its stills, and the send picks one or the other.** `AttachmentKind.Video` covers any `video/` type. A clip's `AttachmentReference.Stills` holds the ids of still frames stored as ordinary image references in the same message's attachment list. `AttachmentHydration` asks `ClipSelection`, given the `ModelInputs` `OpenRouterChatClient` resolves for the model the send resolved to (a patched turn included). A model that takes video gets the clip and none of its stills, as an `input_video` part with a data URL (`VideoInputParts`, since the Responses adapter drops a video `DataContent`). A model that takes only images gets the stills and every other picture. A turn whose model would see nothing of the clip (it takes neither, or takes only images and no stills came) throws `AttachmentRefusedException` before the request leaves. Past the hydration distance, one placeholder names the clip. Telegram keeps refusing a video, and so does a WebChat upload; WebChat holds a clip only as a review copy. `docs/adr/0045-a-clip-or-its-stills-is-chosen-at-the-send.md`.
- **A dictation is not an attachment.** One run of a microphone that ends as words, and the audio is never a message: no playback bubble, no attachment kind, no bytes in any store, nothing in a conversation's history but text. `IAudioTranscriber` (`Domain/Contracts/`) is the one injection point — complete audio plus the container it is in, answered with a transcript and whisper's confidence figures — and `LemonadeTranscriptionClient` (`Infrastructure/Clients/Transcription/`) is its only implementation, shared with the voice hub's streaming `ISpeechToText`, which is otherwise untouched. **whisper as lemonade runs it rejects Opus in any container** (verified against the live instance; the image has no ffmpeg), so WebChat encodes 16 kHz mono s16le WAV in an AudioWorklet and Telegram decodes Ogg/Opus in managed code via Concentus; WAV, MP3, FLAC and Ogg/Vorbis are forwarded untouched, and the container is decided by sniffing the leading bytes, never by a sender-supplied mime type. **WebChat opens the microphone for a recorder, not for a phone call**, which is a mobile constraint rather than a preference: `echoCancellation` and `noiseSuppression` are asked for as false, keeping an Android device off its voice-call audio route, whose processing is tuned for a person listening down a line and reaches whisper as garbled speech. **`autoGainControl` stays on**, and that asymmetry was paid for: asked for as false, an Android phone held in the hand and spoken to normally returned a recording peaking under a tenth of full scale, flat enough to read as a room rather than a person. It works on the level rather than the shape of the sound, which is the one thing a phone microphone cannot supply for itself. A capped, upward-only lift when the WAV is built remains as a floor under it. The graph runs at the device's own sample rate, with the worklet resampling to 16 kHz behind its own anti-aliasing filter, because asking for a 16 kHz `AudioContext` puts a resampler nobody here wrote inside the capture path and it does not treat a phone's microphone as it treats a laptop's. **The chain must still end at `ctx.destination`** (through a gain of zero — nothing is meant to be heard): Chromium renders a graph that reaches no output, Android does not, and every node in it then goes unpulled and records silence. No node in that chain may be left as a leaf, and no desktop test can catch it if one is. WebChat's dictation ticket sits beside the upload and download tickets but is space-scoped and counts no slot, and it carries the recording cap and the mis-tap floor so a dictation obeys the numbers the server holds when it starts rather than what the first render could learn — composer text must not force a conversation into existence or spend an attachment slot — and the transcription endpoint stores nothing. Telegram gates a transcript on the same confidence floors the satellites use and replies rather than staying silent; WebChat deliberately does not, because the person reads the words before sending them. Both record the existing `VoiceMetric` speech-to-text members under a `Channel` dimension, so the dashboard separates satellite, chat and Telegram with no new metric family.

- **Attachment capability is discovered, not configured, and it is refused twice.** `OpenRouterModelCapabilities` asks the provider's model list at startup and hourly; `AgentCatalogBuilder` stamps the accepted kinds onto each catalog entry, and `RunAsync` takes the catalog as a **function** so a refresh reaches channels through the registration that already exists (a connection re-registers a catalog whose wire shape changed). `AttachmentCapability` (`Domain/DTOs/Channel/`) is the one resolution the composer, `ChatHub` and `TelegramBotService` all use, so they cannot disagree about which model is refusing. The agent does not check a third time, except for a clip: the provider's `video` modality is mapped too, `AttachmentCapability` refuses a clip only for a model that takes neither video nor images, and the send refuses a clip its model would not see (ADR-0045). Permissive wherever the catalogue is silent — a blip at the provider must not remove the feature. Telegram accepts `register_agents` for this alone (nothing else there consumes the catalogue, and it has no per-message model override), and its refusal is per-turn: no turn is emitted, because an answer that silently ignores what was sent is worse than no answer.
