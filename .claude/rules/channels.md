# Channel Architecture

See also: `.claude/rules/chat-hub.md`, `.claude/rules/chat-queue.md`, `.claude/rules/telegram.md`, `.claude/rules/channel-attachments.md`.

Transports (WebChat, Telegram, Voice, Scheduling) are independent MCP channel servers; the agent connects as an MCP client via `ChannelEndpoints`. `ChannelProtocol` centralizes wire serialization — the shared `JsonSerializerOptions`, the typed records, and the one spelling of the inbound methods and outbound tool names. A new transport needs only a new channel server — zero agent changes. **One sanctioned exception to the one-spelling claim:** `McpChannelConnection.SendReplyAsync` hand-builds its argument dictionary instead of calling `ChannelProtocol.ToArguments`, because `send_reply` fires once per streamed chunk (hundreds per response) and the reflective `SerializeToDocument` + per-property `Clone` is measurable there. The hand-built keys and values must stay byte-identical to what `ToArguments` would emit (camelCase keys, enums spelled as `JsonStringEnumConverter` spells them), so a property added to `SendReplyParams` must be added to the hand-built dictionary in the same change. No other call site may copy this shape.

- **Being a channel server is one call.** `Mcp.Hosting`'s `IMcpServerBuilder.AddChannelServer(policy, subscriberId?, errorResult?, noOutboundSurface?)` wires the `ChannelInbox`, the shared `channel_receive` long-poll tool, the call-tool error filter and the sealed `ChannelNotificationEmitter`. The two kinds of server differ by exactly what it and `AddToolServer` differ by. A new transport writes only its reply-sending logic.
- **`DeliveryPolicy` is a required argument.** `Broadcast` fans out to every registered subscriber whatever its freshness (an idle-but-unpruned one still receives); with none registered the item is discarded (SignalR, Voice). `BufferAlways` targets a known subscriber id and creates its queue on demand, for a transport that cannot tell a sender to retry (Telegram). `GateOnLive` enqueues only when someone is actually polling — for callers that settle a durable record on confirmed delivery, where buffering on a failed emit would keep the record *and* leave a duplicate (Scheduling, Library), and for a caller waiting on its own request, better told at once that nobody listens (Sugary).
- **Liveness is the return value of emitting**, never a separate property: `EmitAsync`/`EmitCancelAsync` answer "was anyone listening?", with the freshness window internal to `ChannelInbox` (hand-copied emitters let the stale-subscriber defect recur). `ChannelReceiveContractTests` drives the channel-capable rows of the server table and asserts each declared policy.
- **A batch is handed out until its poller says it arrived.** A poll's answer can die on the wire after the inbox let its batch go, invisibly to the server. So `channel_receive` takes optional `poller` (minted once by the agent's `McpChannelConnection`, kept across reconnects and tunnel openings) and `received` (the last batch received, 0 before the first), and answers with the batch's number (`ChannelReceiveResult.Batch`, absent for an empty batch or a poller that named nothing). `ChannelInbox` keeps a batch drained for such a poller as handed out (`PollerCursor`, `Subscriber.Settle`) until that poller's next poll: naming it releases it; naming an earlier one redelivers it first, ahead of what arrived since. Numbers start from the subscriber's clock, so a restarted server never reuses one the agent still names. Anyone else polling releases it undelivered, since another poller (a restarted agent, a fresh connection) may have taken and answered it. A poller that names nothing (an older agent) has every batch committed as drained, and an older hub ignores both arguments, as a tool ignores any it does not declare (`ChannelReceive_AnArgumentItDoesNotKnow_IsIgnored`). No timer: the next poll settles it, and the agent numbers only what it dispatched whole, so nothing is delivered twice.

- **Which agent answers is configuration, never array order.** For a message whose channel named no agent, `ChatMonitor` stamps one **before** grouping, so the group key, the agent built, the turn's context and the memory written all name the same one:
  1. a satellite's turn: the **voice agent** of its household (`HouseholdAgents.VoiceAgent`: the agent its owner marked on the Agents page — any agent, a Jonas as well as a Nabu — else its first agent made from the voice template, else one with that template's id, the home's seeded Nabu; a household with none is routed to the template's id and refused with how to set one up). The household is the one whose own voice server heard it, else the verified person's (`HouseholdChannels.HouseholdOfTurn`; the guest has no account);
  2. else the channel's deployment default (`AgentDefaults`, `agentDefaults.byChannel` in `Agent/appsettings.json` — the Sugary app to `sugary`, for a transport whose messages belong to one agent by nature);
  3. else the default of the household the principal names (its agents section's `defaultAgent`, `IAgentDefinitionProvider.ForHouseholdAsync`; none is the home's) — how the shared Telegram bot reaches a household's agent.

  A channel that sends an agent still has it used — defaults are fallbacks, not overrides. A household the agent cannot read just now routes nothing rather than stopping the monitor. `MultiAgentFactory` builds by id from the turn's household's agents or refuses — it never falls back to the first configured agent (`jack` merely happens to be listed first). A channel default naming an agent the household lacks is refused per message, not at startup (`AgentNotFoundException`; `AgentNotFound` on the errors feed under the household); on an attach-only channel a person's turn is answered `ConversationGroup.NoAgentHereAnswer` (naming the Agents page and the template), so a satellite does not wait out its reply timeout in silence; other channels refuse as before. A voice server names no agent of its own (`VoiceSettings.AgentId`, unset unless an operator pins one); the agent mints a voice conversation's topic under the same voice agent (`TopicMintingApi`). Whichever agent serves a satellite answers under the voice rules: a conversation group reads its opening turn's channel's prompt sections (`audience-channels`, `PromptManifest.ForChannel`) beside its own, for the group's life (`PromptAudience`). The refusals' words are spelled once in `RefusalAnswers` (`Domain/Monitor`) so each channel can say them in its own language: voice speaks each as its own Spanish sentence (`SpokenRefusals`; English in its Spanish voice was noise) and any other error as "Hubo un error: …". `AgentAppSettingsTests` holds every channel default to one of the home's agents, and the Sugary app's to a template's id too.
- **A turn's agents are its household's.** `MultiAgentFactory.CreateAsync` reads the turn's household (`tenantId`, else the account's) through `IAgentDefinitionProvider` over `IHouseholdAgentSource` (in the deployment `HouseholdAgentSource`, kept by the reader for a minute; `.claude/rules/household-config.md`, "The agents a household runs") and builds the definition with the household's zone and the shared servers its features withhold. A turn acting for nobody runs the home's agents and reaches no household's servers — unless it came through a household's own channel server or its fire's server names a household it keeps the object under (`HouseholdChannels.HouseholdOfTurn`, `.claude/rules/own-servers.md`): then it is that household's turn, built for it and reaching its own servers, as nobody. The catalogue registered with a channel the deployment dials is the home's; with a household's own channel server, that household's (`ChannelAgentCatalogs`, read before its connections register and again once a configuration lifetime). A deployment channel showing a person agents asks per household (`agent-names`) — the chat hub, Telegram, the scheduling server's `/schedules`.
- **A conversation group is anchored and built by its first turn.** `ConversationGroup` (internal to `Domain/Monitor`, one per conversation and agent, constructed in production only by `ChatMonitor`) owns the pending-turn queue, command dispatch, delivery anchors, agent, restored thread and warmup, all established on the group's **first turn**. A chat command is not a turn, so a group of only commands builds nothing — a `/clear` with no live group costs no agent, thread read or MCP connection. The thread context stays eager because disposing it is how a command ends the group; `ChatThreadResolver.ClearAsync` wipes persisted state unconditionally. Whether a turn reuses the anchors is decided by identity against the anchor message, never by a message counter (`docs/adr/0006-a-group-is-anchored-and-built-by-its-first-turn.md`). The monitor keeps merging the channel streams, grouping, delivering each update and publishing first-reply latency.
- **The monitor is supervised, and every ending costs a wait.** `ChatMonitoring` restarts `ChatMonitor` on a doubling, jittered delay (`MonitorRestartSchedule`) for a monitor that *returned* as well as one that threw — a merge whose streams all ended is the same hot loop as a fault, silent in the log. The backoff is forgiven only by a run that lasted (`MonitorRestartPolicy.HealthyRun`): ten two-second deaths in a row are one failure, not ten first ones. Each restart is published as an `ErrorEvent` under `MonitorFault.RestartErrorType`, so a flapping agent shows on the errors feed. Shutdown is neither: cancellation unwinds quietly and reports nothing. `MonitorFault.IsFatal` names faults no restart can clear — a value the code cannot use, never a dependency that is down — and those end the host instead (a container crash is visible, an infinite retry is not). It classifies `MonitorFault.Root(ex)` because the merge hands a fault on its own side over wrapped.
- `DeliveryTarget.Minted` means "minted while resolving this turn", so reused anchors carry it cleared and `AnnounceTurnStartAsync` needs no correcting flag: it skips exactly the targets marked minted.
- `create_conversation` doubles as the turn-start announce when given `existingConversationId`: the conversation group calls it channel-agnostically for agent-initiated messages (`Origin` set) into existing conversations, and each channel applies its own semantics — SignalR opens a live stream + `OnStreamStarted` before reply chunks arrive; voice no-ops on a live satellite session, else binds the turn as an announcement.
- **A channel connection runs itself.** `IMcpChannelConnection.RunAsync(endpoint, catalog, ct)` owns connect with retry, register the catalog, watch health, reconnect with retry and re-register; `ChannelConnectionHost` reads the endpoint map, starts one run per endpoint, and knows nothing else about the order. An endpoint naming a household's server instead of a URL has a connection per household, made (`householdConnection`) the first time that household opens its tunnel of that name and run once per opening; a run that returns leaves the connection not connected (`.claude/rules/own-servers.md`, "A household's channel server").
- **The connections are a live set, chosen by household.** Every connection carries the household it serves (`IHouseholdChannel.Household`, a `ChannelHousehold`): a channel dialled by URL serves every household (`Every`), a household server's tunnel that household alone (`Own`, the home's marked `Home`). The agent's `IConnectionSet<IChannelConnection>` (`LiveConnectionSet`; `ConnectionSet.Fixed` in a test) only grows: a connection whose tunnel closed stays, not connected. `ChatMonitor` merges `WatchAsync` and `AlertRelay` listens the same way (`As<IAlertChannel>()`), so a connection made after they started is read like an original; a fixed set's watch ends, so a monitor over one still ends when its channels do. Whatever picks a connection by channel id picks it by household too (`HouseholdChannels.Serving`/`Find`): the turn's own connection's household, else its verified person's (`HouseholdOfTurn`), else the home's — the resolver's targets, the review host and the approval relay's offers never reach another household's connection. Being **not connected** is five behaviours, one per member, stated on that interface (`docs/adr/0011-not-connected-is-five-behaviours-and-stays-that-way.md`) — `CreateConversationAsync`'s null is load-bearing for `DeliveryTargetResolver`. The far end's tool set is asked once per **connection generation** and discarded on reconnect (`docs/adr/0012-a-servers-tool-set-is-fixed-for-a-connection-generation.md`); the channel-protocol probe (`OffersToolAsync`: which tools, such as `create_conversation`, a channel offers) is also refreshed by every health check's listing (`IsHealthyAsync`), because a channel container recreated with a new image keeps the same client, whose pump only retries.
- On connect and every reconnect the agent registers its `AgentCatalogEntry` list via `register_agents`; channels use this single source instead of duplicated `Agents` config. **The registered catalogue is never read as a household's list.** The chat client's picker is `ChatHub.GetAgents`: the connection's household's agents from the accounts service's `agent-names` view (session refresh's assertion, as for spaces), under their names and on their models, with the deployment's model facts — patchable models and efforts, what a model accepts — from the registered catalogue (`AgentCatalogBuilder.ForHousehold`; an id registered on the same model keeps its entry); `ValidateAgent` is false for an agent not the household's. On a registration SignalR pushes `OnAgentsUpdated` with **no list** (`AgentsUpdatedNotification`, so no household is sent the home's names) and the client asks `GetAgents` again; saving a household's agents section pushes the same to that household's connections alone (`HouseholdAgentsAnnouncer` over `IHouseholdConfigSaves`, told after the configuration client dropped its copy; every connection joins `household:{tenant}`, `TopicAudience.Household`). What an agent is and reads for a person is `HouseholdAgentCatalogue` (`Domain/Agents`): their household's agents from `agent-names` on their own proof, each on its household's model, with the registered catalogue's model facts. The picker, the hub's attachment guard on send (`CapabilityRefusalAsync`), Telegram's (the sender's assertion; a shared bot's chat that picked none is the household's default agent) and Sugary's (her request's assertion) all ask it, and a household whose agents cannot be read just now is as silent as a catalogue nothing registered. Only the home's paths read the registered catalogue directly, by design: the schedules mount for a call acting for nobody, and a kept file from before files named their agent (`.claude/rules/channel-attachments.md`).
- `attachOnly: true` in `ChannelEndpoints` (voice) makes `DeliveryTargetResolver` order that channel last — it attaches to conversations minted elsewhere, never mints the primary target. When nothing anchors a fan-out before an attach-only channel (a fire only voice delivers), the agent mints the topic itself through its own `IConversationFactory` (the agent's `ChatMonitor` takes one) for the message's verified principal, and hands the channel that conversation as `existingConversationId`.
- **Dual-role** servers are both a channel and a tool/filesystem server (`mcp-scheduling`, `mcp-library` download alerts, `mcp-homeassistant` watch fires, `mcp-sugary` her app's estimates, `mcp-timers` the alerts of timers with no satellite); their channel-protocol tools are hidden from the LLM, and an agent dialling one as a tool server is not thereby its channel's consumer — `agentDefaults` alone routes the channel (Jonas dials `mcp-sugary` for the `/sugary` mount and the `sugary-log` skill; the app's estimates still go to `sugary`, which dials the same server for its estimating prompt alone, `noTools`).
  - `mcp-sugary` is the one channel with a person waiting on the other end of a reply: it opens a turn per estimate, acting for the person the proxy named (`.claude/rules/sugary.md`), under its own `TurnKey`, collects that key's reply chunks, and answers the app's waiting request with the parsed whole or an error. A meal is one conversation: her answers are further turns on the first estimate's id, carrying no attachments (the first turn's photos hydrate from history); the server continues only a conversation it opened itself within `FollowUpHours` of its last turn (`OpenEstimates`, in memory) — anything else is answered 410 before a turn is sent, and the app estimates afresh. A nutrition label is a turn of its own conversation, asking for the `nutrition_label` format with a config patch naming `LabelModel` (stronger than meals use); its photo's capability is asked of that model, and a label the model declines returns to the app as 422 with the model's reason.
  - A filmed meal's clip is read, cut down and given stills by the server before anything is kept (`.claude/rules/channel-attachments.md`).
- **An approval can say why it is asked.** `ToolApprovalRequest.Screen` carries the exec screen's codes (`ExecScreenCodes`: `not_requested` with the danger that made it worth asking — `destructive`, `sends_out`, `runs_downloaded`, `reaches_lan` (other devices on the local network: a household kit's sandbox sits on that network) — or `unjudged`) for an exec that would have run unasked and was flagged; the screen asks only about a command both not asked for and dangerous, on either machine. `as_person`, on a call carrying `asMe: true`, is not the screen's: its site asks whatever the whitelist says (`.claude/rules/browsing-as-person.md`). Codes, not prose, so each channel says them in its own language: Telegram and WebChat through the one English line `ExecScreenReasons.English`, voice as a Spanish sentence spoken before the question (`.claude/rules/voice.md`). A request with no `Screen` renders exactly as before, and an unknown code is skipped, never shown raw.
- **An approval is its asker's, and is answered wherever they are.** `ApprovalRelay` (`Domain/Monitor`) is the agent's one `IToolApprovalHandler`, built per conversation group around the channel the delivery anchors (`targets[0]`) and every connected channel. `ToolApprovalChatClient` hands it an `ApprovalAsk` — the question's own id (a whole GUID), the conversation, the requests and the turn's `ConversationContext` as a field (never the call in flight); the asker is `Principal.Of(turn)?.Account`, which for a fire is the account its verified delegation names (none for an undelegated fire). The anchor is asked by `request_approval`, carrying `approvalId`; for a turn acting for an account the question is also offered by `offer_approval` (`OfferApprovalParams`) to every other channel advertising it among the deployment's and the turn's household's own (never another household's) — the chat client (`ApprovalService.OfferApprovalAsync`: `OnApprovalOffered` to the account's every connection through its `account:{userId}` group, whatever space, or a Web Push in the default space when `AccountConnections` counts none open; `GetOfferedApprovals` catches a client up whenever it becomes live) and Telegram (the asker's private chat, by the asking agent's bot). Voice and the dual-role servers advertise no `offer_approval`, so are never offered one (a dual-role server's auto-approval stays an anchor's answer). The first answer wins: every other channel is told by `settle_approval` (`SettleApprovalParams`, carrying the answer, so an anchor that asked still lets through and shows what was approved elsewhere) and its call is then cancelled, which is how a waiting prompt stops — the MCP SDK carries a cancelled call to the server's tool token (`McpChannelConnectionApprovalMetaTests`). The chat client's card says "Answered elsewhere" until closed; Telegram edits every copy to it. **The anchor is authoritative about ending the question** — its answer, its refusal and its time-out (Telegram's two minutes, voice's two attempts) all settle every offer — and an offer that is not answered never ends anything. Only an anchor that could not show the question to anyone answers `ChannelProtocol.NoAnswer` (`no_answer`: SignalR with no live session, voice with no satellite or one gone mid-prompt, arbitration taking the answer), which leaves it to the offers for `ApprovalRelay.UnshownWindow` (two minutes) before it is refused, so ADR-0035's "a question nobody can see must not hold the turn" still holds. An anchor that failed (not connected) fails the call unless an offer answers first. A turn acting for nobody — the voice guest, an unstamped fire — is asked on the anchor alone, under that channel's own rule. Whoever sees all is never offered another person's question. `ChannelProtocol.ParseApprovalAnswer` is the one reading of a channel's answer (Telegram's `approved_and_remember` included). Known edge: an anchor that answers by itself at once (a dual-role server, when a fire resolved no target) still has the offers sent and immediately settled.
- **An alert is its person's, and rings wherever they are.** A server may raise an insistent alert for one person instead of a turn — the timers server, for a timer with no satellite to ring on; the raise/offer/settle flow is in `.claude/rules/timers.md` — as the inbox items `ChannelInboxItemKind.Alert` (`ChannelAlertNotification`) and `AlertStopped`. `McpChannelConnection` reads them apart from `Messages`, as `IAlertChannel.Alerts` (`AlertSignal.Ring`/`Stop`); no conversation group sees one and no model is asked. The agent's one `AlertRelay` (`Domain/Monitor`, shaped like `ApprovalRelay`) offers each with `offer_alert` on every other connected channel advertising it among the deployment's and the owner's household's own (`HouseholdChannels.Serving`: the raising server's household, else the owner's — never another household's server of the same name) — the chat client and Telegram; voice and the other dual-role servers advertise none. The first channel answering `dismissed` (`ChannelProtocol.AlertDismissed`) ends it: every other channel, the raising server included, is told by `settle_alert` and its offer is called off. A stop from the raising server settles every channel showing it; an alert shown nowhere is settled at its origin at once; one nobody dismisses rings out after `AlertRelay.RingWindow`. The calls are signed for nobody and name the owner, as an approval offer names its asker. `IAlertChannel` sits beside `IChannelConnection` rather than in it — an alert is no part of a turn — and its not-connected behaviours are an offer's: false, a silent settle, an `Alerts` that yields forever (`IMcpChannelConnection`). Both tools are hidden from the model (`ThreadSession`).
- **A person's turn carries the accounts service's assertion, and the agent believes only that** (each channel's source of it: `.claude/rules/person-assertions.md`, "Channels and the agent"). `ChannelMessageNotification.Assertion` (`ChannelMessage.Assertion` agent-side) is carried untouched. `ConversationGroup` checks it as each message arrives, before queueing (`AssertionVerifier.VerifyTurnAsync`), and the principal's `Account` is then the one it named, whatever the channel wrote; a turn whose assertion fails is never queued, built or recalled for. A chat command is no turn and needs none; a fire (`Origin` set) carries none, and acts for the person its delegation names when the agent's own signature on it holds for that very object, else for nobody (`.claude/rules/delegations.md`, "Deferred turns").
- **A suspended household starts nothing.** Once a message is admitted — a person's or the guest's assertion, or a fire whether its delegation held or not — `ConversationGroup` asks the agent view (`IAgentDefinitionProvider.ForHouseholdAsync`, the reader's copy, dropped on the suspension's announcement) whether the operator suspended each household it names (`HouseholdAgents.Suspended`): the assertion's; for a fire, the one its server keeps the object under (`ChannelMessage.HouseholdId`, a schedule's `TenantId`, believed for this alone) and its delegation's person's. **For every message**, not when the group's agent is built: a group outlives its turns, so one already running is refused from its next message. A person's turn is answered as a refused one ends (`ConversationGroup.SuspendedAnswer`, an `Error` then `StreamComplete`), so the chat client, Telegram, a satellite or Sugary shows why; a fire, with nobody waiting, only on the errors feed. Both are `ErrorType` `HouseholdSuspended` under the household, and nothing is built, recalled or minted. A fire naming no household and acting for nobody (a download, a watch of the home's) runs as before. **A household that turned Sugary off starts no Sugary turn**: its features withhold `mcp-sugary` from every agent, including the estimator whose rules that server serves, so a person's turn on the `sugary` channel (`ChannelIds.Sugary`) is refused the same way (`FeatureOff` on the errors feed, `RefusalAnswers.SugaryOff`) rather than estimated without them. **A household the agent cannot read just now is refused too**, never let through and never told it is suspended: `StandingUnreadable` under the household, answered `ConversationGroup.UncheckedAnswer` ("could not be checked right now"), as for a person's unreadable standing, since the turn could not be built without that view anyway. The channels refuse a suspended household's people before the agent does where they can (`.claude/rules/channel-identity.md`, "Resolving a channel identity"); the hub's per-turn refresh answers for them, so this is what tells an open chat client.
- **The principal carries the account beside the channel's user id.** `Principal(ChannelId, UserId, Account?)`: `UserId` keeps its meaning — the channel's own name for the person (a Telegram username, a voice profile, the chat client's account id), a label nothing decides by; `Principal.Of` reads the stamped principal alone, never a context's own `UserId`, and on a server that principal is the call token's (`.claude/rules/service-identity.md`). `Account` is the accounts service's (tenant id, user id), set where the channel knows it: the chat client, Telegram (whose `UserId` stays the username), and voice for a recognised speaker (`.claude/rules/voice.md`; the voice guest stamps a principal with none). Browsing as a person reads the `Account` alone, from any channel (`.claude/rules/browsing-as-person.md`), so a voice login's link reaches the person's chat client. It rides wherever the principal does with no code of its own — the notification (`ChannelProtocol`), `McpChannelConnection`'s mapping, `ConversationContext` in `_meta` and on the persisted message, a schedule's `CreatedBy` (Redis, default JSON options), a login wake's — and a record from before it, with no `account`, reads as the channel's user. A fire's own principal is the one the agent builds from its verified delegation; whatever its server stamped is a label.
- `ChannelMessageNotification.ConfigPatch` (`AgentConfigPatch`: model + reasoning effort) lets a channel override agent config per message; SignalR populates it from the person's picker, Sugary from its `LabelModel` setting on a nutrition label's turn. Whitelist: `patchableModels` in `Agent/appsettings.json`, surfaced to clients through the widened `AgentCatalogEntry`. A model off the list is never honoured: `McpAgent` logs the rejected patch and runs its own model, so a channel that must not be answered by the agent's own model (Sugary's label) checks the registered catalogue's `PatchableModels` itself and refuses before the send.
- `ChannelMessageNotification.ResponseFormat` (`ResponseFormat`: schema name + strict JSON schema) travels beside the patch and asks for that turn's final answer in a schema; Sugary populates it. `McpAgent` reads it off the turn's own user message only — the persisted message keeps it, the next turn never looks back for it — the schema goes out verbatim and strict, a strict schema adds `provider.require_parameters`, tools may still be called first (Sugary's agent has none, so its turns are one answer), and a worker never inherits it. `docs/adr/0044-a-channel-message-may-ask-for-its-answer-in-a-schema.md`.
