# The accounts service

`Accounts/` is the only owner of households (tenants), people (users), roles, passkeys, invites, recovery links and sessions (`.scratch/accounts/spec.md`). It is a plain ASP.NET Core host, **not an MCP server**: no `Mcp.Hosting`, no Infrastructure; its one project reference is Domain, for the signing piece (`Domain/Security/Signing`, `.claude/rules/service-identity.md`), built `FROM base-sdk` for the SDK band and for Domain, which base-sdk has already built (`BuildProjectReferences=false`). The container is `accounts`, on the compose network only; Caddy routes `handle /accounts/*` on the main host to it, and `handle` passes the path on unstripped, so every route is mapped under `AccountsApp.PathBase` (`/accounts`).

## The store

EF Core on SQLite in `./volumes/accounts` (owned by PUID/PGID through the `accounts-volume` one-shot, as Sugary's is), migrated and the home household seeded by a hosted service before the first request, and by every command before it runs — the operator's first command may come before the service ever started. **Nothing in the model or the migrations names SQLite**, so a hosted database is a provider swap:

- Keys are opaque generated strings (`Tokens.NewId`, 32 lowercase hex: no `:` to break a composite key elsewhere), never a name and never a generated integer, so no `Sqlite:Autoincrement`. Key columns carry a max length, which an indexable key needs on other providers.
- Instants are `DateTimeOffset` converted to UTC `DateTime` (`ConfigureConventions`), enums are strings, no raw SQL, no JSON columns.
- A migration is generated with `dotnet ef migrations add <Name> --project Accounts/Accounts.csproj --output-dir Store/Migrations`, and then **stripped of the provider's store types** — every `type: "TEXT", ` in `Up`/`Down` and every `.HasColumnType(...)` in the designer and the snapshot — so each provider maps a CLR type to its own default. `dotnet ef migrations has-pending-model-changes` must still say nothing changed, and `dotnet ef migrations script` emits the same SQL either way.

Every record carries its tenant even though only the home one exists. A user's channel identities arrive as rows of their own pointing at the user, so `Users` never grows a column per channel: `LinkedIdentity` (`Channel`, `Identity` as the channel spells it — a Telegram id's decimal digits), unique on (`Channel`, `Identity`) so an identity is one person's and on (`UserId`, `Channel`) so a person holds one per channel. A voice profile needs none: it is named after the user id. A group chat bound to a household is a `BoundChat` (`Channel`, `ChatId`, `TenantId`, the owner whose code bound it), unique on (`Channel`, `ChatId`). Both are generic by channel, so another chat transport is rows, not tables.

## Secrets at rest

A link's token and a session cookie's value are bearer secrets: only their SHA-256 hash is stored (`Tokens.Hash`), so the database alone opens nothing. A session and a passkey also have an opaque `Id`, which is what a device list or a revoke names.

## Links

`LinkKind.Recovery` adds a passkey to a person who already exists; the operator's first enrollment is a recovery of an account with no passkey yet. `LinkKind.Invite` names a display name and role and creates the person on redemption, in the inviter's household. `LinkKind.TelegramLink` is the account page's code that links a person's Telegram, redeemed as the bot's start parameter (a 43-character base64url token, inside Telegram's 64 of `[A-Za-z0-9_-]`); `LinkKind.TelegramGroup` is an owner's code from the members page that binds a group, sent to the bot there as `/bind <code>`. Neither opens the enrollment page — `LinkStore.Enrollable` is invite and recovery only — and each Telegram call finds a link by the kinds it redeems alone (the start parameter: invite and link code; `/bind`: the group code), so a recovery link is no start parameter and an invite binds no group. A link is good once for `LinkLifetimeDays` (7). It is checked when its page opens and when its ceremony begins, but **spent** only at the ceremony's finish, by a conditional update inside the transaction that adds the passkey (`LinkStore.SpendAsync`), so two ceremonies racing on one link cannot both write.

An invite's person does not exist until redemption, but the authenticator stores the user handle at the ceremony's start, so the user id is chosen then (`Tokens.NewId()`, held with the ceremony) and the person is created with it. `LinkStore.RedeemInviteAsync(db, linkId, userId)` spends the invite and creates the person **inside the caller's transaction**, and is the seam a redemption without a passkey uses: `TelegramLinks.RedeemStartAsync` spends an invite (creating its person) or a link code (`SpendAsync`) and writes the sender's `LinkedIdentity` in one transaction, so a person never exists without the way in that made them. A Telegram another person holds — or anyone at all, for an invite, which would make the same Telegram two people — is refused (409) before anything is spent, so the code stays open for the Telegram it was meant for; the unique index decides a race the read missed. A person linking a second Telegram replaces their first row.

## Sessions

The cookie is `ziggurat_session`: HttpOnly, Secure (always, since localhost counts as secure in a browser), SameSite=Lax, on `SessionCookie:Domain` (the parent domain; empty for a host-only localhost cookie). A session is valid until revoked; the cookie asks for `Max-Age` 400 days because that is the most a browser keeps one. Last-seen is written at a five-minute grain, because the check runs on every proxied request. A session records the passkey that began it; `PasskeyStore.RevokeAsync` revokes the passkey and those sessions in one transaction, and a session `mint-session` issued has no passkey and survives it. `SessionStore` is the issuing seam, apart from the ceremonies, so a test stack signs a seeded person in without a ceremony. A session's `Device` is the user agent it signed in with. A session or passkey is revoked **named by its owner as well as its id** (`RevokeAsync(userId, id)`): the ids are on the account page, so they are not secrets.

## The account and members pages

`/accounts/account` (anyone signed in) edits the person's own display name and avatar (`POST /account/profile`, held to `People/Profile.Read`: a name of 1–200 characters, and an avatar that is empty — none — or an `http(s)` address or a path on the deployment's hosts starting with one `/`, with no whitespace, control character or `\`, since every app draws it as an image and a browser reads `//host` or `/\host` as somebody else's; `/accounts/me` and the session check read the row, and the chat hub learns the name on its next connection), lists the person's passkeys and devices, each revocable, adds a passkey (a registration for the signed-in person; no new session), mints a Telegram code on a button press rather than per view — only its hash is kept, so it is shown once — shown as `t.me/<Telegram:BotUsername>?start=<code>` or bare when no bot is named, shows `scripts/enroll-voice.sh <user id>`, and names who holds "sees all conversations", which everyone in the household may know. `/accounts/members` (owners; a member gets 403) lists the household with role, operator flag and the permission, mints invites and recovery links (shown in the POST's answer, the only time they exist in clear; an invite also as the bot's deep link, `TelegramSettings.DeepLink`, or as `/start <token>` with no bot named, for somebody who only uses Telegram), mints a group code ("Bind a Telegram group", shown once as `/bind <code>`), changes roles and grants or withdraws the permission. Every read and change is scoped to the viewer's household. The last owner cannot be demoted, checked inside the one `UPDATE` (`MemberStore.ChangeRoleAsync`) so two owners demoting each other cannot both pass. The members page mints no recovery link for the operator: their way back is the container command, and an owner who could mint one could take the dashboard.

`/accounts/*` is not behind the proxy's session check — sign-in and enrollment open signed out — so `PageGuard` reads `ziggurat_session` itself, sending a signed-out page to sign-in and back and a signed-out `/accounts/api` call a 401. Every POST, form or the add-passkey script's JSON, carries an ASP.NET antiforgery token (`RequestVerificationToken` header for the script): the Lax session cookie keeps cross-site forms out, but every host under the parent domain is the same site, and these forms decide who gets in. The antiforgery cookie, `ziggurat_antiforgery`, is host-only on `/accounts` and **not** Secure — TLS ends at the proxy, so no request here is https, and antiforgery throws rather than issue an always-secure cookie on a plain one. Data-protection keys live beside the database (`keys/` in the volume), so a restart leaves open forms valid. A form that changed something answers 303 back to its page. The pages' CSP allows `form-action 'self'`.

## The session check

`GET /accounts/verify?channel=<id>`, for `forward_auth`. A valid session answers 200 with `X-Ziggurat-User`, `X-Ziggurat-Tenant` and `X-Ziggurat-Roles` (`owner`|`member`, plus `operator`, plus `sees-all` for whoever holds "sees all conversations"), and `X-Ziggurat-Assertion`, **always all four** (`ForwardedAccount.Headers`; every `copy_headers` copies all four, conformance-checked). The assertion is those three signed (see Assertions below), with the session's id as `sid`, for the `channel` the block names — `signalr` on the chat client's routes, `sugary` on Sugary's, `dashboard` and `sexytime` on apps that start no turn — because the agent refuses a turn whose assertion names another channel than the one it came on. `channel` is required: a check without it is 400, so a new `forward_auth` block cannot hand an app an assertion naming nothing. Never add a site-level strip of `X-Ziggurat-*`: it runs after `forward_auth` and blanks what `copy_headers` set. The permission rides as a role so the chat hub learns it from the assertion it already verifies (`ForwardedAccount.SeesAll`, spelled again there as `SeesAllRole`); the hub reads them once per connection, so a grant or a withdrawal reaches an open chat client when it reconnects. `?role=<role>` answers a valid session lacking it 403 rather than sending a signed-in person to sign in again. With no session, a **page** — `X-Forwarded-Method` GET, an `X-Forwarded-Uri` whose first segment is not `api` or `hubs`, and an `Accept` naming `text/html` — gets a 302 to `{PublicBaseUrl}/accounts/sign-in?returnUrl=<the original, absolute>`; anything else gets 401, so an app's script can tell a signed-out call from content. The redirect and the return are absolute because the protected page may be on another of the deployment's hosts than the one sign-in is served on; `ReturnUrls.Resolve` follows a return only onto `AllowedOrigins`, else the front page.

## Who can forge the headers

Nobody, any more, for the apps that act for a person: the chat hub, Sugary's API, the dashboard and the agent registration API believe only `X-Ziggurat-Assertion`, verified against this service's JWKS and held to their own channel, and never the plain three (`.claude/rules/service-identity.md`, "Apps behind the proxy"). The sandbox, the one container running what the model writes, is also kept off them by network: it is on a compose network of its own shared with the agent alone (`.claude/rules/sandbox.md`, `DeploymentConformanceTests.TheSandbox_SharesANetworkWithTheAgentAlone`). The chat client's host (`webui`) serves files and reads no header; this service's own pages read their own cookie.

## SexyTime and the agent registration API

SexyTime (the `sexytime` upstream, not in this repo) is behind the same check: `sexy.*`'s catch-all carries the same `forward_auth` as the main host's chat client, and `sexy.*` routes `/accounts/*` too, unchecked, so a page there reads `/accounts/me` same-origin. The session cookie is on the parent domain and `https://sexy.…` is one of `AllowedOrigins`, so a signed-out page there goes to sign-in on the main host and comes back.

`/api/agents*` is **not** behind the check, on either host: its caller is SexyTime's server, which holds the agent API's secret (`AGENTAPI__SHAREDSECRET`) and forwards the `X-Ziggurat-Assertion` the check handed it for `sexytime` (`.scratch/service-identity/sexytime-note.md`). The API wants **both**: the secret says the caller is that server, the assertion — verified against this service's JWKS, for `AppChannels.SexyTime`, a person not the guest — says who it acts for, and without a believable one the call is 401 with the secret. It never reads `X-Ziggurat-User` or a `userId` parameter; a custom agent is listed, used and deleted only under the id it was registered with. Because the proxy does not check this route, nothing strips a header a client wrote, which is why the plain header is no longer believed: a holder of the secret relaying a client's headers could name anyone, but cannot sign. Custom agents stay in memory; making them durable is the Tenants phase.

## Who is signed in

`GET /accounts/me` answers a valid session with JSON `{ userId, tenantId, displayName, avatarUrl, roles }`, `no-store`, and anything else with 401 — never a redirect, since the asker is an app's script. It sits under `/accounts/*`, so it is **not** behind the session check: the chat client reaches it same-origin on the main host, where the proxy routes `/accounts/*`, with the session cookie riding along; another host's app needs that route too, or asks across origins with credentials. The chat client names and draws its person from it, and a 401 is what sends the page to sign in.

## Resolving a channel identity

`POST /accounts/internal/resolve` (`Internal/IdentityResolution`) is how a channel server learns whose account the identity it saw is: `{ channel, identity }` answered `{ tenantId, userId, displayName, assertion }`, or 404 for an identity nobody holds. `voice` identities are the account's own id (a voice profile is named after its user id), `telegram` is a numeric id a `LinkedIdentity` row links, and any other channel is 400 — `signalr` included: the chat hub's person is a live session's, never an account named by its id, which would let the hub's credential mint anybody.

`POST /accounts/internal/session` (`Internal/SessionRefresh`) is the chat hub's: `{ userId, sessionId }` — the session its connection's assertion named (`sid`) and its person — answered like a resolution, `{ tenantId, userId, displayName, assertion }` with a fresh `signalr` assertion naming that session, while the session is live, and 404 once it is revoked, gone, or not that person's (`SessionStore.LiveAsync`). The hub asks it for every turn (`ISessionAccounts`), so revoking a session stops its open chat client's next turn.

The Telegram bot's ways in sit beside it under `/accounts/internal/telegram/` (`Internal/TelegramLinking` over `Links/TelegramLinks`), each answered by a status the bot tells its person apart by: `start` `{ telegramId, code }` → 200 `{ outcome: invited|linked, tenantId, userId, displayName }`, 404 for a code nothing open goes by, 409 for a taken Telegram; `web-link` `{ telegramId }` → 200 `{ url, expiresAt }` (a recovery link the person asked for themselves), 404 for a Telegram nobody linked, **403 for the operator**, whose Telegram must not be a way onto the dashboard (as the members page refuses them a recovery link; their way is the account page or the container command); `bind` `{ chatId, code }` → 200 `{ tenantId }`, 404, or 409 for a group another household holds (one bound to the same household is bound again, idempotently); `group` `{ chatId }` → 200 `{ tenantId }` or 404 for a group bound to none; `of-account` `{ tenantId, userId }` → 200 `{ telegramId }`, the person's linked Telegram and so their private chat with the bot, where an approval their turn asked is offered, or 404 for a person who linked none or a household that does not hold them. The client is `ITelegramAccounts` (`Domain/Contracts`), answered by the same `AccountsResolverClient`, which `AddAccountResolver` registers as both contracts. These are **server to server only**:

- A caller presents `Authorization: Bearer <credential>`, matched against every `Callers` entry (`CALLERS__<host>`), and anything else is 401 before a row is read. The check is one endpoint filter on the `/internal` route group (`Internal/InternalApi`), so an endpoint added there is covered without saying so. The credential is the one the caller already holds for its own `/mcp` — compose feeds `CALLERS__mcp-channel-signalr` the same `${MCP_SECRET_CHANNEL_SIGNALR}` that server's `MCP__SHAREDSECRET` reads, and likewise Telegram and voice — so no secret exists for this alone; `DeploymentConformanceTests` holds each entry to its server's variable. An empty entry admits nobody, and a server that asks nothing here is given no entry (Sugary reads the person off the forwarded assertion and resolves no identity). **Each caller asks about its own channel alone** (`Internal/InternalCallers`, by the `CALLERS__<host>` name): `mcp-channel-signalr` refreshes sessions on `signalr`, `mcp-channel-telegram` resolves `telegram` and is the only caller of `/telegram/*`, `mcp-channel-voice` resolves `voice` and asks for the guest; anything else is 403 before a row is read (a channel no endpoint serves is still 400 first), and a host named with no channel asks about nothing. So one leaked channel credential mints that channel's people and no other's. A credential several entries share — a host run's one local secret — is each of those callers at once. Compose's caller names are held to the table (`DeploymentConformanceTests.EveryChannelCallerOfTheAccountsService_IsOneItKnowsTheChannelOf`).
- The comparison is `Internal/CallerCredential`, `Domain.Security.SharedSecret`'s rule spelled again from before the service referenced Domain; `CallerCredentialTests` holds the two to the same answers.
- Every Caddy host that reaches this service answers `handle /accounts/internal/*` with `respond 404` **before** `/accounts/*` (conformance-checked), so a browser never reaches it; a new host routing `/accounts/*` needs the same block.

`POST /accounts/internal/household-import` is the household migration's one call and the exception to "any listed caller": it can make the operator and mint their passkey link, so it answers only `CALLERS__household-migration` (403 for any other caller), a credential the deployment leaves empty but for the run. It makes the retired identity map's people accounts of the home household all at once or not at all, finding each again by a `LinkedIdentity` on the `identity-map` channel (their map Name), which no resolution answers. `.claude/rules/household-migration.md` has the rest.

Every identity the internal API resolves is answered with an `assertion` of that person on the channel asked about: `resolve` (`ResolvedIdentity.Assertion`) and the Telegram `start` (`TelegramStarted.Assertion`, on `telegram`); `bind`, `group` and `of-account` resolve no person and sign nothing. `POST /accounts/internal/guest` `{ channel }` answers `{ tenantId, assertion }`: the home household's **guest**, signed (`IdentityClaims.Guest`), for a satellite whose speaker no profile matched — `voice` alone, any other channel 400, because only a satellite hears somebody nobody sent. A satellite's own household is the Tenants phase's.

The client every channel server shares is `IAccountResolver` (`Domain/Contracts`), implemented by `AccountsResolverClient` (`Infrastructure/Clients/Accounts`, registered by `AddAccountResolver(config, ownMcpCredential)`, `Accounts:BaseUrl` defaulting to `http://accounts:8080`): null is nobody, and a call the service could not answer throws, so a caller never takes an outage for a stranger. Every person it answers (`ResolvedAccount`, the Telegram start's included) carries the service's `Assertion`, and `GuestAsync(channel)` answers the household guest (`ResolvedGuest`: tenant and assertion); a channel server carries the assertion on the turn it starts, never keeps it past half its life, and never reads it.

## Assertions

`Signing/Assertions` signs `IdentityClaims` as `TokenIssuers.Accounts` for `TokenAudiences.Assertion` — one audience for every consumer, the agent and the apps alike, since the service signs before it knows which the request goes to; the channel is what binds an assertion to a use — for `AssertionLifetime` (10 minutes, appsettings), on `AccountsClock`. The key is `SigningKeyStore` over `Signing` (`SigningKeySettings`): with `Signing:KeyDirectory` empty it is `signing/` beside the database, generated on the first assertion or JWKS request and kept in the volume (beside `keys/`, which is data protection's, not this); `SIGNING__PRIVATEKEY` hands a test stack a fixed key, which nothing writes, rotates or retires. Nothing about it is in `.env`. The public keys are `GET /accounts/internal/jwks` (`InternalApi.JwksPath`), the one internal route **outside** the caller filter — public keys are no secret and their verifiers (the agent, the apps) hold no `CALLERS` entry — kept off the internet by the proxy's `/accounts/internal/*` 404 alone (`DeploymentConformanceTests.TheAccountsJwks_IsRefusedThroughTheProxyOnEveryHost`). Losing the key costs a moment: no assertion is stored, and the next one is signed with the new key.

## Ceremonies

Fido2 (`Fido2`/`Fido2.AspNet`): discoverable credentials (resident key required), user verification preferred, attestation none, the relying party the parent domain (`WebAuthn:RelyingPartyId`) and `AllowedOrigins` the ceremony's accepted origins. Sign-in sends no allowed credentials, and the assertion's user handle — the UTF-8 of the user id — says whose passkey it is. A ceremony's options are held server-side between its two requests (`CeremonyStore`, in memory, five minutes, taken once), because the finish must be checked against the challenge the server issued. The pages are server-rendered with one script (`PasskeyScript`), which converts base64url by hand rather than with `parseCreationOptionsFromJSON`, absent from older phone browsers; they send a strict CSP and `no-referrer`, since the enrollment page's address carries its token.

## Commands

`docker exec accounts dotnet Accounts.dll <verb>`: `mint-link --operator [--name <display name>]` (creates the operator as an owner of the home household the first time, a recovery link for them every later time), `mint-link --user <id>`, `mint-session --user <id>` (prints only the cookie's value), `create-user --name <display name> [--role owner|member]` (a person of the home household with no passkey yet, a member unless named an owner: the operator's way to add someone before the members page exists, and the E2E stack's way to seed the people it then signs in by `mint-session`), `rotate-signing-key` (a new key signs from the running service's next assertion on; the previous stays published) and `retire-signing-keys` (unpublishes all but the signing key; run once the previous key's last assertion has run out, which the rotation prints: the lifetime plus 30 s of skew). The two key verbs touch no database and, with `SIGNING__PRIVATEKEY` set, change nothing and exit 1. As in Sugary, `Program` detects a verb before building and runs it **instead of** the web server, with the verb's arguments kept out of configuration. `mint-link` and `create-user` print the user and household ids in the same words (`user <id>, household <id>`), the only public way to learn them before the members page exists.

## Configuration and time

Per-deployment values are compose environment entries, not secrets: `WEBAUTHN__RELYINGPARTYID`, `ALLOWEDORIGINS__n`, `SESSIONCOOKIE__DOMAIN`, `PUBLICBASEURL` (links and the sign-in redirect are built on it); `DeploymentConformanceTests` checks they describe hosts the Caddyfile serves. Missing ones refuse startup. `Telegram:BotUsername` (`TELEGRAM__BOTUSERNAME`, a compose environment entry of `accounts`) is per-deployment too, but optional and shipped empty: empty shows the bare code, which is safe, while a placeholder name would hand every code to whoever owns that bot. The service has no secret of its own (its signing key is generated, not provisioned); its `CALLERS__<host>` are its callers' existing credentials (above), and a host run takes them from the launch configuration as `local-mcp-secret`. Its clock is `AccountsClock`, a type of its own rather than the container's `TimeProvider`, so a test moves the service's time without moving Kestrel's.

## Tests

`AccountsServer` boots the shipped composition on a real localhost port with its own database, a signing key generated beside it, and a `FakeTimeProvider`; `VerifyAssertionAsync` checks an assertion as a consumer will, with `TokenVerifier` over a `JwksCache` fetching the service's own JWKS; the ceremony suite drives Chromium with CDP's virtual authenticator (ctap2, internal, resident key, user verification). The authenticator belongs to the page, so a sign-in after an enrollment runs on the same page with the cookies cleared. A browser signs in without a ceremony by being handed a `mint-session` cookie (Secure is accepted on localhost). `AccountsServer.SignedIn(session)` is the pages' HTTP client: it carries the session and antiforgery cookies and posts a form with the token its page rendered. The Telegram endpoints are driven raw (`TelegramLinkingTests`) and through the client (`AccountsResolverClientTests`), and the bot itself against a running service by handing `TelegramPollingHarness` a real `AccountsResolverClient` (`TelegramGateTests`); the bot's own rules run against `FakeTelegramAccounts`.
