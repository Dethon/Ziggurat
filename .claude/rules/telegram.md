# Telegram channel

See also: `.claude/rules/channels.md`, `.claude/rules/chat-hub.md`, `.claude/rules/chat-queue.md`, `.claude/rules/channel-attachments.md`.

- **One shared bot serves every household; a household's own bots are its configuration's.** The Telegram channel polls the deployment's shared bot (`Bots:SharedToken`, compose's `BOTS__SHAREDTOKEN` from `.env`'s `TELEGRAM_SHARED_BOT_TOKEN`; empty runs none) and every household's bots, read across households from the accounts service (`IHouseholdConfiguration.TelegramBotsAsync`, `.claude/rules/household-config.md`) at start and every `Bots:Refresh`: `BotRegistry.Replace` keeps a bot whose token is unchanged polling, starts a new one, stops one no longer configured, and polls each token once (the shared bot's included), so a `keys` save takes effect within moments and an accounts outage leaves the bots polling as they were. A `TelegramBot` is keyed by what outlives a poll — `shared`, or `{householdId}.{agentId}` — and that key is what an attachment reference names (`TelegramReference`; an older reference names its agent, and still reads while one bot alone is bound to that agent). **A household's bot** is its agent's: every turn names that agent, and the gate answers anybody of another household "This bot belongs to another household than yours". **On the shared bot** a turn names the agent the chat picked, or none, which the agent answers with the household's default (`ChatMonitor`, `.claude/rules/channels.md`). `/agent` (after the gate, so a stranger is shown only the ways in) lists the person's household's agents (`agent-names`, proven by the person's assertion), and `/agent <id>` switches the chat for everybody in it (`ChatAgents`), kept in Redis per household and chat (`RedisChatAgentChoices`, `telegram:chat-agent@{householdId}:{chatId}`) so it outlives a restart; on a household's bot it says the bot is its agent's. A pick naming an agent the household has since removed is the agent's to refuse. A reply goes back through the bot the chat last wrote through (`BotRegistry.RegisterChat`, in memory): a person's private chat id is their Telegram id on every bot, so one person writing to two bots at once shares a conversation and gets replies through whichever wrote last. Who writes first (an alert, an offered approval) is `BotsPreferring(household, agent)`: the household's bot for the agent, its others, then the shared bot, never another household's. A fire whose author asked for Telegram (a schedule's `deliverTo` naming `telegram`) is delivered the same way: Telegram's `create_conversation` (`CreateConversationTool`) opens the principal's private chat — the conversation `<telegramId>:<telegramId>`, so the fire continues the chat they talk in — by the first of those bots a "typing" can reach, and registers the chat to it for the reply; a principal of nobody, with no Telegram or no bot that can write to them, opens nothing and the fan-out skips the target. With no topic name and an existing conversation it is a later turn's announce, and answers the id unchanged.
- **Telegram admits a linked number, and an approval is the asker's.** Everything in a private chat is addressed to the bot, plain text included (a stranger's is answered with the ways in); in a group only a command or a forum thread is (user's decision, 2026-11-06). A tool the turn ran unasked (`request_approval` in notify mode) is acknowledged and posted nowhere on Telegram (user's decision, 2026-11-06). An approval nobody answered in time edits every copy to say it was not run.
  - A message is admitted only when `From.Id`, the sender's numeric Telegram id, is linked to an account in the accounts service — never by username, chat name or first name, which their owners can change and Telegram can reassign. No allowlist: `TelegramGate` asks through `TelegramAccess`, which resolves `telegram`/`<id>` with `IAccountResolver` and keeps the answer by `TimeProvider` (`LinkCache`: five minutes for a link, five seconds for a refusal, so a stranger costs no request per message and somebody just linked gets in at once). In a group the person must also belong to the household the group is bound to (`ITelegramAccounts.GroupTenantAsync`, cached the same way); a group bound to none admits nobody. Anyone refused is answered with a hint to ask an owner for an invite (or that the group is unbound) and no turn is emitted. An accounts outage throws out of the resolver, is answered "I can't check who you are right now" and is never cached — an outage is not a stranger.
  - **The ways in are answered before anybody is looked up**, since a stranger must be able to use them, and none is a turn: `/start <code>` (a start parameter, `[A-Za-z0-9_-]{1,64}`) redeems an invite, creating the account, or the account page's link code; bare `/web` in a private chat answers a linked person a one-time link that adds a passkey (in a group it sends no link — whoever opens it gets into the account; `/web` with words after it is a turn); `/bind <code>` in a group binds it with an owner's code from the members page (`/bind@bot` too, as a group's command menu sends it). A redemption or bind seeds `TelegramAccess`, so the person or group is let in on the very next message whatever refusal was cached. A bare `/start`, which Telegram sends when someone first opens the bot, is a turn for a linked person and the hint for anyone else.
  - The turn's principal is `Principal("telegram", sender, account)`: `Sender` and `UserId` stay the username (the id as a string for a person with none), because the approval router is keyed by it. The turn carries the assertion the admitting answer came with (the resolution's, or a redemption's for somebody just linked); `TelegramAccess` keeps an answer for `LinkCache:Linked`, which must stay at most half an assertion's lifetime (`DeploymentConformanceTests.TheTelegramBotsKeptAnswer_LeavesItsAssertionHalfItsLifetime`), and a message buffered for an agent away longer than the assertion's remaining life is refused when it finally arrives.
  - `request_approval` reads the turn's `ConversationContext` off the hop's `_meta`: a turn acting for an account — a person's own on any channel, or a fire whose delegation names the schedule's writer — is answered by a tap whose Telegram `TelegramAccess` resolves to that account (`TelegramAccess.AnswersFor`, an `ApprovalAnswerer`); a fire naming nobody by any linked member of the chat's household (a private chat's id is its person's Telegram id, a group's household is its binding, so each tap is resolved as it comes); and any other turn naming nobody — no context, a call the agent signed for nobody whatever user id its `_meta` claims, a chat no household holds — by nobody (it times out denied). Who the turn is comes from the call token alone (`CallTurn`); the sender the bot emitted is a name, never who may answer. Any other tap is answered "This approval isn't yours" and the approval stays pending. Asked in a group for an account, the question is also put in the asker's private chat on the same keyboard (`ApprovalCallbackRouter.ShowInPrivateChatAsync` over `TelegramAccess.PrivateChatOfAsync`, the accounts service's `telegram/of-account` — the one way both an asked and an offered question reach a private chat); every copy is kept on the waiter (`ApprovalCallbackRouter.Shown`) so an answer, here or elsewhere, edits them all. An approval id is a whole GUID, 32 hex characters, so `tool_always:<id>` is 44 bytes of Telegram's 64.
