# Chat queue, stop and steering

See also: `.claude/rules/channels.md`, `.claude/rules/chat-hub.md`, `.claude/rules/telegram.md`, `.claude/rules/channel-attachments.md`.

- **A message sent while a reply runs waits in the topic's queue, the hub's** (`.scratch/queued-messages/spec.md`). `StreamService` keeps it per topic beside the stream (`TopicQueue`), in memory, under the stream's lock: a message is queued only while the topic streams, and the stream ends only once nothing is pending or queued (`GiveUpPlace` is the one release, under `CompleteStream`, `Enqueue` and `Release`: a turn ending, or a place held for a message being admitted, takes the queue's head and keeps the stream open for it).
  - **A turn ends once, on the reply that says `IsComplete`**, never on its kind: the agent ends a refused or failed turn with an `Error` (`IsComplete` false) then a `StreamComplete` under the same turn key, so the error is written and ends nothing; the hub's own errors (`PersonTurns`' refusals and not-live answer, `AnswerRefusedAsync`, the dispatcher's failure) are a turn's last word and carry `IsComplete` true.
  - **Admission.** `EnqueueMessage` keeps its signature (installed pages bind it): it holds a place on the running stream (`StreamService.Hold`, by its `StreamKey`; none means nothing runs, and false is the page's signal to open a stream itself), then admits the message as any send — a file it names that the upload store keeps for another conversation refuses it (`TopicRefusals.NotYourFiles`, `ChatHub.AdmissionRefusalAsync`, also for a send opening a turn, since a page names files by id and the agent fetches whatever is named; an id the store holds nothing under passes, as a swept file always did), then the capability guard, then the accounts service's word for the session — and appends a `QueuedMessage`. Refused, it gives the place up and throws the refusal as a `HubException`, since ending a turn on the stream would end the running one. A `SendMessage` finding a stream already running (`StreamService.OpenOrHold`) is queued the same way (its refusal an error chunk on its own wire), so a page that had not heard the stream start cannot jump the queue.
  - **Dispatch** is `QueueDispatcher`, a hosted service: a turn completes in `send_reply`, with no hub call in hand, so the stream service writes each head it takes to `StreamService.Dispatches` for the dispatcher — which depends on the stream service, never the other way round. It vouches for the head's session afresh, then starts its turn (`StreamService.StartAsync`) whether or not its sender still has a page open (a session signed out meanwhile is written, ended "signed out", and the next runs); a stop while it was being vouched for returns it undrawn. The stream's current prompt and sender become the head's as it is taken.
  - **News.** Every change is pushed whole as `OnQueueChanged` (`QueueChangedNotification`, whose `Revision` the page keeps the later of, since the hub's and the dispatcher's pushes may cross) to the topic's audience by the stream's own rule (`QueueNews`, `TopicAudience`), asked afresh at each push so a share or an unshare mid-reply moves the queue's news as `AudienceChanged` moves the stream's. `GetQueue` answers the same, revision included, to whoever sees the topic (anyone else: "No such conversation."). A page catches up on every topic open and on becoming live again (`ShownTopicCatchUp`, the one trigger it shares with `ReturnedMessagesEffect`) and on resuming a topic not on screen (`StreamResumeService`), all through the one `QueueChanged` reducer, so whichever of a fetched and a pushed queue was read later is shown.
  - **A queued message is withdrawn by its sender alone, by account**: `RemoveQueued(topic, id)` and `TakeBackQueued(topic, id)` (answering a `ReturnedMessage`: words, file references, config patch) resolve the topic under the visibility rule, then take the item out under the stream's lock (`StreamService.Withdraw`) — the same step a turn's end takes the head in, so a withdrawal either wins or is refused `TopicRefusals.AlreadySent`, never both; anyone else is refused `TopicRefusals.NotTheSenders`. Remove deletes the item's files that are this conversation's and that neither the conversation (`ConversationHistory.HeldAttachments`, line and versions) nor the rest of the queue still names; a take-back keeps them for the composer. A withdrawal that won is answered whatever follows: its push is best-effort (`QueueNews.TellOrLogAsync`, as the dispatcher's), and a conversation that cannot be read deletes no file. The push item carries no file references; the take-back's answer does.
  - **Stop returns the queue** (`CancelTopic` → `StreamService.StopAsync`): in one locked step every queued message — and any head taken as the turn ended but not yet started — moves into a per-sender **returned** set for the topic (queue order, in memory, outliving the stream), and the stream is cancelled; only then is the agent told to cancel. **What tells the agent a turn starts or stops goes out in one order** (`StreamService.InAgentOrderAsync`, one semaphore for every topic, each step under it in memory): a stop's step and its cancel, a queued turn's start (claimed, written, emitted) and a send's emit (`SendTurn`) never interleave, so a turn ending as the stop runs starts nothing, a queued turn is either the one cancelled or never sent, and a send that opened a new stream meanwhile reaches the agent after the cancel. Nothing is started after a stop, since a new stream would race the agent's teardown of the cancelled turn. A message still being admitted to the stopped stream (`Hold`, then vouching) goes back to its sender too (`Queueing.Returned`), as does the send that opened the stream if still being vouched for: it is written and emitted in one `InAgentOrderAsync` step only while its stream runs (`StreamService.StartSendAsync`, `SendStart`), else handed back (a reroll's message, already on the line, and a Continue's ask are dropped); other pages hear `OnStreamStarted` only once it has started, and `EnqueueMessage` answers true so the page does not send it behind the cancel. The topic's last stopped stream and the ids it returned are kept (`TopicQueue.LastStopped`, until the topic is deleted), so a Remove or Edit that loses to a stop is refused `TopicRefusals.ReturnedToComposer`, even after a page took them.
  - The stop pushes `OnQueueChanged` and, to each sender's `account:{userId}` group, `OnQueueReturned` (`QueueReturnedNotification`, whose `CorrelationIds` — the sending pages' ids for what it hands back — `ReturnedMessage.CorrelationId` repeats), both best-effort, so a stop never fails on a push and an older page that ignores both still stops. `TakeReturned(topic)` checks the caller still sees the topic, then hands over and forgets their items in one locked step, so only the first of their pages to ask gets them. Deleting the topic drops its returned sets (`StreamService.Forget`); a hub restart loses them, as it loses the queue.
  - **Unsharing hands members their words** (user's decision, 2026-11-16): `SetTopicShared(…, false)` leaves the owner alone writing in the topic, so `StreamService.Unshare` moves every other sender's waiting messages out of the queue — including a head of theirs still being vouched for (its place given up so the queue goes on) and whatever a stop handed back to them there that they had not taken — into a set kept by person (`_unshared`, dropped with the topic by `Forget`), and marks the running stream private to the owner (`RunningQueue.PrivateTo`, cleared by `Reshare`), so a member's message still being admitted goes the same way (`Queueing.Unshared`) and `EnqueueMessage` answers true; a steer already sent is left to the agent. Each member is told after the topic's change, by `OnQueueReturned` marked `Unshared` (an older page asks `TakeReturned` of a topic it may no longer see, and is refused); their page takes the words by person (`ChatHub.TakeUnshared`, also asked whenever it becomes live, so a person with no page open finds them on the next) into whatever composer is on screen, with a toast (`ReturnedMessagesEffect.UnsharedToast`) — the words alone, since the files were added to that conversation and no other takes them.
  - **Taking back on the page.** The page takes on `OnQueueReturned` while it shows that topic, on every topic open and on becoming live again with a topic open (`ReturnedMessagesEffect`), merging through `ReturnToComposer`; an answer landing after the person moved to another topic is kept for that topic's next open, never put in the composer on screen.
  - **The composer always sends** (`ChatInputLogic.CanSend` asks nothing of the stream); Stop sits beside Send or the microphone while the reply runs. A send onto a running stream (`StreamingService.QueueMessageAsync`, decided under its lock) draws nothing and closes no bubble: its correlation id is one the page queued (`IMessagePipeline.QueueUserMessage`), and when the hub writes it on the stream the page draws it there, after the reply it followed, by that id alone — never skipped as "shown" for words the history already holds. Finding nothing running after all, it is drawn and sent as a new message. One the hub refuses, or that could not be sent, is told as a toast and its words go back to the composer (`OfferComposerText`). A send the page drew as sent before it heard a reply start is queued by the hub behind it; if it goes back after all (a stop landing as it was admitted, vouched for, or waited), every page of its sender takes the drawn message off (`TakeOffSentMessages`, by the ids `OnQueueReturned` names, and again by `ReturnedMessage.CorrelationId` as words are taken); refused as it was queued, its wire's error says so (`ChatStreamMessage.RefusedSend`, optional — an older page draws the error as it did), and the page takes it off, toasts the refusal and gives its words and files back through `ReturnToComposer`, read on its own wire or, lost to a resume, off the losing one. A refusal drawn under the reader's own message keeps its Retry after other turns are drawn below it (`MessageActionsLogic.OffersRetry`, `RetryRefused`), which sends that message again as a new one at the end; the last bubble's failure keeps `RetryLastMessage`.
  - The queue shows as chips above the composer (`QueueChips`: the sender's name when not the reader's own); the reader's own offer Edit and Remove (`QueueChip.Actions`), a refusal told as a toast. `ReturnToComposer` (topic, messages) is the one merge for anything given back: words before what is typed, each joined by a blank line (`ComposerState.Handed`, the composer's own slot beside dictation's transcript, `HandedWords.Placement`), files re-added as ready attachments. The config patch a message was queued with is not kept: words handed back go out on whatever the picker shows, never on a model held out of sight (the user's call over keeping it).
  - **Steer now** (`ChatHub.SteerQueued(topic, id)`) sends the caller's own queued message into the running turn, only while that turn is their own person's turn. `StreamService` tracks whose turn runs (`RunningQueue.RunningFor`: set as a person's send opens the stream and as a queued or steer turn starts; cleared for a turn `create_conversation` starts — a fire attaching mid-turn, told to the pages at once through `StreamService.QueueChanges`, which the dispatcher reads beside `Dispatches` and relays (`QueueNews`), so no page goes on offering Steer now — and while a claimed head has not started) and publishes it as `QueueChangedNotification.RunningFor` on every push and `GetQueue`. Anyone else's turn, a fire's, or one about to start is refused `TopicRefusals.NotYourTurn`; another's message `NotTheSenders`; a message gone from the queue as a withdrawal is. It is vouched for afresh first, for the session that queued it (a refusal is the caller's `HubException`; the message keeps its place and the running turn is untouched), then in one `InAgentOrderAsync` step moved into the topic's steers (`StreamService.Steer`, counted as pending, so nothing else dispatches until its turn has started) and emitted with `ChannelMessageNotification.Steer` (mapped onto `ChannelMessage.Steer` by `McpChannelConnection`; inbound only, `send_reply`'s hand-built dictionary is untouched) under its queued id as `ChannelMessageNotification.TurnKey`, which the agent answers every reply of that turn under. An emit nobody hears puts it back at the head (`Unsteer`); one heard is marked (`StreamService.SteerHeard`, `WaitingSteer.Heard`). Until drawn it is published apart from the queue as `QueueChangedNotification.Steering` (beside `Items`, so an older page, knowing `Items` alone, never offers to edit or remove it) and shown first as a steering chip with nothing offered (`QueueChip.Steering`; the steering page turns its own chip at once, `QueuedMessageSteered`); drawing it, a stop's cleanup and a refused steer each bump the revision. The running turn's end writes every waiting steer's message on the stream in the same step, in steer order (`StartSteers`, before anything of their answer), and makes them the running turn, so the reply splits there whether or not the agent cut it short; a stop returns pending steers first.
  - **Only a steer heard is drawn** (ticket 14): a steer is taken from the queue, then sent, and only then is it known whether anybody heard it, so the running turn's end can fall between — drawn there unheard, the agent would wait for a message that never comes. The end draws the heard ones (and one the agent already answered) and stops at one still being sent, the last, since a steer is sent before the next is taken; that one is drawn once heard, or goes back to the head of the queue when nobody hears it, and when the end drew nothing, nothing runs until then (`RunningQueue.EndedUnheard`: `SteerHeard` draws it where the turn ended, `Unsteer` gives its place up so the queue goes on).
  - **Steers waiting at that end go in together** (user's decision, 2026-11-17): those the agent has not answered are one turn, answered once under the first one's key. The hub decides which under the lock that end takes and tells the agent in its answer to that end's `send_reply` (`ReplyReceipt.SteeredTogether`, `{"steeredTogether":[…]}`, optional both ways, beside `returnedTurnKeys`; `StreamService.ReceiptFor` names them only to the reply under the key that ended, `RunningQueue.DrawnTogether`). The agent records them on the group before it takes its next turn (`ReplyDispatcher.Delivery.SteeredTogether`, `ConversationGroup.SteeredTogether`) and, taking one, gathers the rest off its pending turns (`SteeredWithAsync`) before the turn runs, so none of them cuts it. The pump admits on its own time, so a drawn steer not yet pending is waited for; a steer the pump refused as it arrived is queued as a marker (`AdmittedTurn.Refused`) that ends the wait, its refusal sent first, so the page draws it under the steers before their answer (`m1, m2, error(m2), answer`, ticket 15, pinned on all three seams); one whose poll's answer died on the wire is delivered again ("A batch is handed out until its poller says it arrived", `.claude/rules/channels.md`), so the wait ends either way, with no timer. Anything else at the head stops the gathering, and a key the stop handed back is dropped as any is. The turn runs the messages together (`RunStreamingAsync` with each person's message, each built as a turn's own: recall and extraction per message, the skill preload asked once, for the last; the model, config patch and format are the last message's, as `McpAgent` reads them), so the line keeps each as its own entry, then the one answer.
  - **Each steer's key ends once**: the hub keeps one pending place per steer it drew, so the agent ends every key but the first with a `StreamComplete` of its own after the answer (`StreamAgentTurn`'s `joined`); the queue goes on only once all have ended, and the hub counts those ends without writing them (`RunningQueue.Joined`), since the answer already ended on the page. A steer pressed after the steers went in is a steer of their turn, and cuts it. A stop before the end drew them returns them all (and that end's receipt names them as returned, drawing nothing); a stop after returns none, and the agent keeps the turn as stopped with every message.
  - **A message the hub drew always survives a stop** (tickets 14 and 15), however the step before its turn is left. A stop's cancel names what it handed back even when that is nothing (an empty `ReturnedTurnKeys`, never none), and the hub hands back every message it has not drawn and sends nothing after its cancel but a new stream's. So the group keeps a person's message of that channel it admitted before such a cancel (`ConversationGroup._drawnBefore`, by the pump's admission order) and that the cancel does not name — a steer, the send that opened the stream, a queued head — when stopped while its turn gathered or was set up, before it was taken (the loop taking it after the stop, or the group's end draining it, each pinned), or before its run reached the history (the history settles every turn it decides about, `TurnSteering.IsSettled`, so the group keeps only what the history never saw): it is kept as a stopped turn with no answer (`DisposableAgent.KeepUnansweredAsync`, `RedisChatMessageStore.KeepUnansweredAsync`), building the group to keep it when the stop came before its first turn. It is kept only while the conversation is still there (its topic, or a line the session left non-empty), so a conversation deleted during the teardown is never written again, while a line another writer moved since (a fire's, an edit's) still takes it. Nothing runs after the stop. A fire, Continue's ask, a reroll's message and another channel's message are dropped, and a cancel naming nothing (an older hub) drops everything.
  - **A message sent right behind a stop is answered after the stopped turn is kept**: routed to the stopped group before it heard the cancel, it is handed back as that group's grouping completes (`GroupByStreaming`: what a completed group had not read goes to a fresh group of its key, ahead of anything newer), and a context resolved after one was let go of carries that group's end (`ChatThreadContext.Predecessor`, `Ended`), which its first turn and its teardown wait for before keeping anything. So a chain of stops keeps each stopped turn in the order the page drew them, never after the next nor refused as a line moved under it.
  - A turn of steers that fails to set up is answered once under the first key, every other key is ended with a stream end of its own so the queue goes on, and every message is kept marked failed, then what the person was told (`EndUnsetUpAsync`). A failed turn is retried by its last messages (`FailedTail.RetriedBy`, a suffix of what its person said), as the page's Retry sends the last message alone: the retry replaces the failed turn, its earlier messages read by the model again and kept again ahead of it under their own names, so its one answer covers them all.
  - **A stop never leaves a steer both returned and kept**: the agent may have started a steer's turn before the hub heard the turn it cut end, so the stop's cancel names every turn key it handed back (`ChannelCancelNotification.ReturnedTurnKeys`, optional both ways, mapped onto `ChannelMessage.ReturnedTurnKeys`); the group records them before it cancels, for its life, and each turn's `TurnSteering` asks by its own key (`IsReturned`), which `RedisChatMessageStore.KeepStoppedAsync` reads as it keeps a stopped turn (handed the handle by `McpAgent` through `BeginCollecting`): a returned turn keeps nothing, so its words are in the composer alone. The cancel can also reach the agent after a steer's turn already ran and was kept (the stop won the hub's lock against the steered turn's end, and a fast-failing steer finished before the cancel was pumped), so the end is answered too: the agent starts a conversation's next turn only once its last reply's `send_reply` returned (`ChatMonitor` awaits each delivery before pulling the next update; the group runs turns one after another), and the hub answers a reply that says `IsComplete` with the keys the topic's last stop handed back (`StreamService.ReceiptFor`, `ReplyReceipt`: `{"returnedTurnKeys":[…]}`, or the plain `ok` every channel answered, which the agent reads as nothing, as it does anything it does not know). `McpChannelConnection` reads it off the tool's text, `ReplyDispatcher.Delivery` carries it, and the group records the keys (`ConversationGroup.TurnsReturned`) before its next turn, dropping one whose key is among them. So a steer is either drawn (the stop then cancels it as the running turn, kept as stopped) or returned and never run; a steer the hub saw answered before the steered turn's end is one the agent refused as it arrived and stored nothing of, and is still returned.
  - **A reply under a waiting steer's key is that steer's, never the running turn's end** (`StreamService.HeldForSteer`): a steer the agent refuses as it arrives (a member disabled meanwhile) gets an `Error` and a `StreamComplete` while the steered turn still runs; those are held on the steer, not written into the running reply, and the running turn's end draws the steer's message with them where its turn would have run; the steer's turn ends once, on its own `IsComplete` (held or, if the running turn ended between the two, written), and the queue goes on. Every reply chunk asks this, without the stream's lock unless the chunk's key is a waiting steer's (`StreamService._waitingSteerKeys`, written under the lock wherever a steer starts or stops waiting — drawn, put back, stopped — and read without it; a steer's answer can only follow its key's addition, since it is sent after). Nor does a turn an agent started end the steered one: a fire attached mid-turn (`send_reply`'s `agentInitiated`) gives up its own place on completion and starts no steer, which waits for the person's turn to end.
  - **The agent is the authority**: `ConversationGroup` admits and queues a steer as any turn, and just before queueing — when the running turn is a person's turn (`Origin` null) whose verified account is the steer's — signals that turn's `TurnSteering` (`Domain/Agents`), made per turn by the group and handed down as `TurnRunOptions`; `McpAgent` still builds its own options and carries the handle in `ChatOptions.AdditionalProperties` — no ambient state, so a worker, whose run builds its own options, is never cut. While the handle is signalled, `ToolApprovalChatClient` sets `FunctionInvocationContext.Terminate` as each call returns: with concurrency on, every call of the batch keeps its result and the model is not asked again (the sequential path would leave calls without results, so concurrency stays on). A reply that reaches no tool boundary is left whole and the steer just runs next. The cut turn is stored whole, neither interrupted nor failed, and `Transcript.Shown` draws a reply that ended on tool results without a word by its last results, naming its tools (`ChatHistoryMessage.ToolsCalled`).
