# The Sandbox

`McpServerSandbox/` is the deployment's own Linux container where the agent runs commands (`fs_exec`, `bash -lc`). `.claude/rules/virtual-filesystem.md` owns what it is as a mount (workspace, landing target, `Contained` reach). The launcher, unit, daemon and action helper are `sandbox-runtime/CLAUDE.md`'s; core commit and cache rules are `sandbox-runtime/src/vfs/core.rs`'s header.

- **A command gets a minimal environment.** The server's environment holds the deployment's MCP secret, and a child inherits its parent's environment by default — the cheapest exfiltration a prompt injection has. `CommandEnvironment.Minimal` is an **allowlist** (home, path, timezone, locale), so a secret added later is excluded without anyone remembering; `HOME` is the workspace the mount publishes, never the server's own. `BashRunnerOptions.Environment` carries it; null inherits, which only the outpost uses (its command runs on its operator's own machine). Process credentials are not environment: the `render` supplementary group still reaches commands, so GPU access is unchanged.
- **A network of its own.** The sandbox runs in the tenant kit, on the `sandbox` network that no other kit service joins, so a command reaches neither Home Assistant nor the kit's Redis nor another server; it reaches the agent only through its tunnel (the `vfs-bridge` back-call behind `VFSBRIDGEURL`). The servers behind the proxy believe the identity headers it copies on (`.claude/rules/accounts.md`) because only the proxy reaches them, and a command on their network could have sent those headers itself. The network is not `internal`, so commands still reach the internet. `TenantKitConformanceTests.TheSandbox_SharesANetworkWithNoOtherKitService` holds it; a new service the sandbox must reach joins the `sandbox` network by name, and the test then names it.
- **Commands run through a root launcher** (`sandbox-runtime/`, the image's entrypoint): the server runs as a uid of its own, so a command cannot read its environment, trace it or kill it; every command runs as PUID (the home volume's owner) in a private mount namespace with the bounding set dropped, no-new-privs and a syscall filter refusing user namespaces (`sandbox-runtime/CLAUDE.md`, "The launcher"); the per-exec FUSE daemon gives up root once it has mounted ("The daemon"). Compose therefore has no `user:` for the sandbox, grants `SYS_ADMIN` for the namespace, names an AppArmor profile (`DockerCompose/apparmor/ziggurat-sandbox`, installed on the host by hand) allowing exactly the launcher's mounts — `docker-default` denies every mount and prod enforces it — and a syscall filter (`DockerCompose/seccomp/ziggurat-sandbox.json`) so SYS_ADMIN does not also hand root processes `bpf`, `perf_event_open` and `setns`. Every stack starting the image does the same through `SandboxContainer.AsCompose()` (the E2E fixture, the eval's testcontainer). The server uses `LauncherRunner` when `LAUNCHERSOCKET` is set, which only the launcher sets; an in-process host (integration fixtures) keeps `BashRunner`; both resolve the working directory through `CommandCwd` and pass the same minimal environment. The home volume is group-writable with PGID, and what the server's file tools create is handed to PUID before each command — only the paths `SandboxFileSystem` names to the runner (`ICommandRunner.Wrote`) and the launcher adopts, never a walk of the whole home.
- **Every other mount is a filesystem to the shell.** A sandbox exec serves the calling session's other mounts at `/vfs/<name>`, linked at `/<name>`, through one FUSE daemon per exec in that exec's mount namespace (`sandbox-runtime/src/vfs/`). The daemon is a thin kernel adapter; meaning lives agent-side in the **bridge** (`Domain/Tools/FileSystem/Bridge/`, served by `Agent/App/VfsBridgeApi.cs` at `/api/vfs-bridge`, never routed by the public proxy — `VfsBridgeApiTests` reads the Caddyfile). One HTTP request per kernel operation, allowed only where the equivalent `domain__filesystem__*` call would run unasked and the session offers that tool (`VfsCall.Unasked`, the one gate; a built app's reads pass it too, through `VfsCall.ToolAsync`) (a read is `file_read`, a listing `glob`, an attribute `info`), so a command never does through the shell what a tool call would ask a person about; otherwise `EACCES`, never a wait. Served: every mount but an outpost and the sandbox itself — `VfsCall.IsServed`, the one rule the prompt's shell section, the screen's reach and the exec tool's rerouting all ask. Each operation reaches its mount as the conversation the command serves: the bridge's request has no turn in flight, so the caller is carried from mint (`ToolApprovalChatClient` puts it on the exec call's arguments beside `ToolPermission`) and the agent's proxy answers `ICallerBoundBackend.As(caller)` — else a shell write to `/watchers` reaches Home Assistant as nobody. Sessions are kept apart by the mount namespace and the daemon refusing any caller not of its own exec (closing `/proc/<pid>/root`). Commands of two sessions still share the home volume and can see and signal each other's processes; by design, and a PID namespace per exec is the step that would end it.
- **The call token is the bridge's only credential.** `VfsExecTool` mints one per exec on the host's `IVfsBridge` (`VfsBridge` in `Infrastructure/Agents`, since the registry is state; what a call means is `VfsCall`'s, in Domain), bound to the session's registry, the live approval view (`ToolPermission`, so an approval remembered mid-command counts) and the offered tools, and completes it in a `finally` however the exec ends; its change log becomes `FsExecResult.VfsChanges`, null and off the wire where exec has no bridge (an outpost, an in-process host). Minting, revoking, lookup and completion are explicit calls; there is no ambient "current call". The token rides the exec call's `_meta` beside the conversation context (`VfsBridgeGrant`), so neither `IFileSystemBackend.ExecAsync` nor the `fs_exec` schema changed: the agent's proxy implements `IBridgedExecBackend`, the server's registrar hands it to the mount as `FileSystemCaller.Bridge`, the sandbox's view passes it to `LauncherRunner`, which forwards it with `VFSBRIDGEURL` to the launcher, which gives it to the daemon over a pipe — **never argv or environment**. `SandboxMountsE2ETests` hunts for it in everything a command can read.
- **Placement.** One FUSE filesystem at `/vfs` (`ServedMount.Root` agent-side, `MOUNTPOINT` in the launcher, **kept in step by hand** across the two builds) with a link per mount, never bind mounts: a rename between two mounts must arrive as one rename. Links live in the shared root and dangle (ENOENT) where an exec does not serve them. A mount named like a path the image already has, or `sandbox`, is served only at `/vfs/<name>`; the image removes its empty `/media` so the media library can link. A daemon that cannot mount costs the command its view of the mounts, never the command: it runs, and its stderr says why.
- **Sizes.** A mount that reports a size is believed; one it cannot size is served with direct I/O (a zero size without it reads as empty, silently). **Every file crosses the bridge whole, so a call has a ceiling** (`vfsBridge:maxFileBytes`, 64 MiB, `VfsBridgeSettings`): a read is refused `EFBIG` the moment it passes it, a write on its declared length, so the agent never holds what it will refuse; the file tools, whose copy streams, are the way to a film. The daemon's own bound above that (`MAX_FILE`, 1 GiB) covers every size a command names, because it allocates what it is told.
- **Writes are the equivalent tool call, committed when the command means them.** The bridge's `write` takes the whole file: text (UTF-8, no NUL) is `CreateAsync` with overwrite and directories (the text tool, so the mount's own text rules apply), gated on `text_create`; anything else — including text on a mount whose operations hold no text create (read off `FileSystemMount.Capabilities`) — is the blob write a copy streams through, gated on `copy`, where the mount offers one. Commit points are the daemon's (`core.rs`): an existing file on the **last release** of its write handles, only if written or truncated — **never on flush**; a **new** file held until renamed onto a path, an action runs, or the command ends (so `sed -i`'s temp never reaches the mount); a new directory only when a file lands under it. Mode, owner and time changes are accepted and change nothing. Every outcome — applied, refused with the mount's envelope, or dropped — goes to the call's change log, returned as `vfsChanges`: bash swallows a refusal at close, so that list is the agent's only reliable record.
- **Deletes are held like creates, and a rename is one operation.** `unlink`/`rmdir` hide the path and commit at the same points, deletes first; an `rmdir` subsumes the held deletes beneath it — which is what makes `rm -r /timers/<id>` the remove tool's one delete, the cancel. `mv` between mounts arrives as one rename, which the bridge makes the move tool's call (`VfsCall.RenameAsync`: the mount's own move, or a `Transfer` with move intent across two, move-out asked before anything is copied); onto something already there it is judged as a write. A rename commits at once, with the command's earlier deletes first. Between the home and a mount the kernel makes `mv` a copy and an unlink, so mount-to-home cannot ask the move-out question; accepted.
- **A killed command commits nothing.** On a timeout the unit tells the daemon to `revoke` and waits for the bridge to have it **before** killing the tree (the kill's releases would otherwise commit first). The token keeps answering after a revocation so what the kill flushes is logged as `dropped`; only the exec returning completes it. A cancelled call is the same, and the exec tool revokes the token itself the moment its own cancellation fires. **A revocation that fails still commits nothing**: the revoke request has its own bound (`HttpBridge`, 10 s), a daemon the bridge did not hear seals itself and sends nothing more (`Vfs::revoke`; the one kind of drop the change log does not list), and a daemon silent within the unit's wait is killed ahead of the command, leaving the mount answering nothing. Operations already past the gate finish and are logged as they ended.
- **Big trees stay practical, and say when they were cut short.** The daemon caches every answer per call (`core.rs`; `tests/vfs_walks.rs` holds `grep -r` to one listing per directory) and answers a name a cached listing lacks ENOENT without a round trip — **except under a listing the mount cut short**, where the name is asked for, since a command told otherwise would create over a file still there: the bridge must keep flagging a cut listing (`BridgeListing.Truncated`). A listing is the mount's glob `*`, so the mounts' own walk budgets bound it; a directory whose listing stopped early is named in the exec result's `vfsTruncated`, so the agent knows what a recursive command did not see.
- **Action files run from any script.** Every action file under /vfs is the same static ELF, `vfs-action`, mode 0111 — never a shebang script, whose interpreter would need read; nothing depends on the kernel's exec-open flag. The helper runs as PUID and holds no token: it hands its path, arguments and cwd to the call's daemon over `/run/vfs/action.sock` (a tmpfs of the exec's own namespace), and the daemon answers only a process descended from the exec's unit (`sandbox-runtime/CLAUDE.md`, "The action helper"). The daemon first commits everything the script holds (the barrier, so an action sees what the script prepared), then the bridge runs the exec tool's call on the action's directory, `./<name>` with the arguments quoted back into words (`BareAction.Render`), gated on `exec`; the action's real output and exit code come back, and it is listed in `vfsChanges`.
- **exec runs where the files are.** `exec` on a served mount with no shell of its own (`VfsCall.IsServed`: timers, schedules, Home Assistant, the vault) runs in the session's sandbox with `/vfs/<name>/…` as working directory, when the session has a sandbox and the host a bridge — `ExecReach.SandboxFor`, the one rule the exec tool routes by and the screen judges by. Otherwise the mount answers itself: its catalog runs the command (so catalogs accept `./<action>`), and a mount with no exec answers tool-missing. The prompt's shell section names only rerouted mounts that offer `exec`. The result echoes the caller's own path as `cwd`. Such an exec is screened at the sandbox's `Contained` reach (`ExecReach.Over(registry, reroutes: true)`) — except one bare action file run by itself (`./name args`, nothing that chains, pipes, redirects, backgrounds, substitutes or spans a line), which is not screened (a served mount's only executables are its action files, each still gated by the bridge; screening `./turn_on` asked a person to approve their own AC). **That one bare action skips the sandbox** when the mount publishes an exec of its own: the action file would only hand its words back to that exec through the bridge, so `VfsExecTool` hands the mount the line itself (`BareAction.Command`, the bridge's own rendering), with null `vfsChanges`. `BareAction.Parse` is the one rule for screen and route, accepting only a line bash would split into exactly the words it reads; `BareActionTests` holds it to bash with a seeded fuzz, so widening it needs only a green run. An outpost keeps its own exec and its `Host` reach. A rerouted working directory containing `..` runs nowhere (climbing out would run a command the screen judged as the mount's elsewhere). Whether a working directory exists is decided by the launcher inside the exec's namespace and answered not-found from there. The sandbox publishes the names its image holds at its root (`FileSystemBackendBase.OccupiedNames`, `occupiedNames` in its `filesystem://` resource, minus the launcher's links into /vfs), so the per-session mounts section and exec tool description (`FileSystemToolFeature.ShellSection`, `VfsExecTool.BridgedDescription`) name each served mount at its path or only under `/vfs`.
