# The Sandbox

`McpServerSandbox/` is the deployment's own Linux container where the agent runs commands (`fs_exec`, `bash -lc`). `.claude/rules/virtual-filesystem.md` owns what it is as a mount (workspace, landing target, `Contained` reach).

- **A command gets a minimal environment.** The server's environment holds the deployment's MCP secret (and once held its whole secrets file, `env_file: .env`, which compose no longer hands this container), and a child process inherits its parent's environment by default, so a command could otherwise print it — the cheapest exfiltration a prompt injection has. `CommandEnvironment.Minimal` is an **allowlist** (home, path, timezone, locale), so a secret added to the file later is excluded without anyone remembering to exclude it; `HOME` is the workspace the mount publishes, never the server's own. `BashRunnerOptions.Environment` carries it; null inherits, which only the outpost uses, because there the command runs on its operator's own machine in the environment they started it with. Process credentials are not environment: the `render` supplementary group still reaches commands, so GPU access is unchanged.
- **Commands run through a root launcher.** The image's entrypoint is `sandbox-runtime/`'s launcher (read its `CLAUDE.md`): it starts the server as a uid of its own, so a command cannot read the server's environment, trace it or kill it, and runs every command as PUID — the home volume's owner — in a private mount namespace with the bounding set dropped and no-new-privs. Compose therefore has no `user:` for the sandbox and grants `SYS_ADMIN` for the namespace; every stack that starts the image does the same through `SandboxContainer.AsCompose()` (the E2E fixture and the eval's testcontainer). The server reaches the launcher through `LauncherRunner` when `LAUNCHERSOCKET` is set, which only the launcher sets; an in-process host (the integration fixtures) keeps `BashRunner`, and both resolve the working directory through the same `CommandCwd` and hand the command the same minimal environment. Two uids share the home volume: it is kept group-writable with PGID, and what the server's file tools create is handed to PUID before each command.
- **Every other mount is a filesystem to the shell.** A sandbox exec serves the calling session's other mounts at `/vfs/<name>`, linked at `/<name>`, through one FUSE daemon per exec in that exec's mount namespace (`sandbox-runtime/src/vfs/`). The daemon is a thin kernel adapter: meaning lives agent-side, in the **bridge** (`Domain/Tools/FileSystem/Bridge/`, served by `Agent/App/VfsBridgeApi.cs` at `/api/vfs-bridge`, never routed by the public proxy — `VfsBridgeApiTests` reads the Caddyfile to keep it so). One HTTP request per kernel operation, each resolved through the calling session's registry and allowed only where the equivalent `domain__filesystem__*` call would run unasked — a read is a `file_read`, a listing a `glob`, an attribute an `info`, and the tool must also be one the session offers — so a command can never do through the shell what a tool call would have asked a person about; such an operation is refused `EACCES` rather than waiting on anyone. Served: every mount but an outpost (a separate machine) and the sandbox itself (`VfsBridge.Served`).
- **The call token is the bridge's only credential.** `VfsExecTool` mints one per exec on the singleton `VfsBridge` — bound to the session's registry, the approval view `ToolApprovalChatClient` puts on each call's arguments (`ToolPermission`, read live, so an approval remembered mid-command counts) and the tools the session offers — and completes it in a `finally`, however the exec ends; its change log becomes `FsExecResult.VfsChanges`, null and off the wire where exec has no bridge (an outpost, an in-process host). Minting, revoking, lookup and completion are explicit calls on the bridge; there is no ambient "current call". The token rides the exec call's `_meta` beside the conversation context (`VfsBridgeGrant`), so neither `IFileSystemBackend.ExecAsync` nor the `fs_exec` schema changed: the agent's proxy implements `IBridgedExecBackend`, the server's registrar hands it to the mount as `FileSystemCaller.Bridge`, and the sandbox's view passes it to `LauncherRunner`, which forwards it with `VFSBRIDGEURL` (compose: the agent by name) to the launcher. The launcher gives it to the daemon over a pipe, never argv or environment; `SandboxMountsE2ETests` hunts for it in everything a command can read.
- **Placement.** One FUSE filesystem at `/vfs` with a link per mount, never bind mounts: a rename between two mounts must arrive as one rename (spike). The links live in the shared root and dangle — ENOENT — where an exec does not serve them. A mount named like a path the image already has, or `sandbox`, is served only at `/vfs/<name>`; the image removes its empty `/media` so the media library can link. A daemon that cannot mount costs the command its view of the mounts, never the command: it runs, and its stderr says why.
- **Sizes.** A mount that reports a size is believed; a rendered file it cannot size is served with direct I/O and read whole, and stats as its length once read. A guessed size of zero without direct I/O reads as empty, silently (spike).
