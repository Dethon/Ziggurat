# Chat hub: people, topics, streams and spaces

See also: `.claude/rules/channels.md`, `.claude/rules/chat-queue.md`, `.claude/rules/telegram.md`, `.claude/rules/channel-attachments.md`.

- **The chat hub's person is the proxy's, settled as the connection arrives.** Caddy's `forward_auth` runs the accounts service's session check before every request to the hub and its upload and dictation endpoints, copying its four headers (`ForwardedAccount` in `Domain/Security`) over anything the client sent. `SignedInConnectionFilter.OnConnectedAsync` verifies the signed one, `X-Ziggurat-Assertion`, against the accounts JWKS for channel `signalr` (`AssertionVerifier`, `.claude/rules/person-assertions.md`), never reading the plain three, and keeps the `ForwardedAccount` in `Context.Items`. A connection without a believable assertion is closed "not signed in" before it can call anything, and `InvokeMethodAsync` refuses any call on a connection holding none, so a new hub method is covered by default. There is no registration call; the client asks the hub nothing until connected. A user message's `SenderId` and the push subscriptions' key are the account's opaque user id. The connection's assertion is verified once, on arrival, and never again as its ten minutes run out.
  - **A turn needs the accounts service's word of its own**, since the agent believes nothing else and a connection outlives its assertion by hours: every turn asks for a fresh one as it is sent (a queued message also as it is queued) — for the **session** the connection's assertion named (`sid`, `ForwardedAccount.SessionId`; `ISessionAccounts`, `/accounts/internal/session`), never for the account by its id — carried as the notification's `Assertion`. Every send path (`SendMessage`, `SendRerun`, `SendContinue`, `EnqueueMessage`) takes a `SenderSnapshot` as it accepts the message and vouches, writes and emits through `PersonTurns` from that snapshot alone, so a turn sent later with no hub call in hand (a dispatched queued message) carries exactly what a live send does and is vouched for again as it leaves. A session revoked since (or none named) ends the turn on the stream "This device was signed out…" (`TopicRefusals.SignedOut`) and sends nothing; an unreachable service ends it "could not be checked right now"; either way as a capability refusal does — except at queueing, where the refusal is its sender's alone (`.claude/rules/chat-queue.md`). A turn already running finishes.
  - **And its connection is closed at once**, since reads and pushes ask nothing: every way sessions end (a device signed out, a passkey revoked, the person disabled) is announced as `SessionsEnded { tenantId, userId }` on `SessionsEnded.EndedChannel` (`accounts:sessions:ended`); the hub's `EndedSessionsListener` has `SessionConnections` ask about each session of that person it holds and abort those no longer vouched for (an unreachable service closes nothing); the page reconnects through the session check, which sends it to sign-in. The display name is asked of the same session on arrival. A host with no proxy in front (`Local: MCP Channel SignalR`) has no session check, so it refuses every connection.
- **A chat-client turn acts for the account and goes by its name.** The hub stamps `ChannelMessageNotification.Principal` itself (`ForwardedAccount.PrincipalOn("signalr")`: the account's id as the channel's user id, and the `Account` beside it) — the verified assertion is the account, so no resolution call. `Sender` is the account's display name, asked once on arrival (`SignedInConnectionFilter`, DI-activated, through `IAccountResolver` with this server's own `Mcp:SharedSecret`, `.claude/rules/channel-identity.md`) and kept in `Context.Items[ChatHub.DisplayNameItem]`; a name it could not get leaves the turn under the account's id and never refuses the connection. `Sender` is a label, never a key: whatever must find the person reads the `Account` — `IAgentFactory.Create` (a person's custom agents are filed under its user id), memory recall, extraction and forgetting (`.claude/rules/memory-architecture.md`), and a history's authorship (`ChatMessage.GetAuthorId()`: the persisted context's `Principal.Account` on a turn with no `OriginKind`, else the sender), because the client tells its own messages by account id.
- **A topic is its owner's unless they share it, and an owner may grant someone every topic of the household.** `TopicMetadata` records `OwnerId`, `TenantId`, `Shared` and `OwnerName` (the name the owner went by when it began — a label for "started by", never a key). `TopicViewer` (`Domain/DTOs/WebChat`, built by `ForwardedAccount.Viewer`) is the one rule, applied by hub, store and chat client:
  - A viewer **sees** their own topics; every topic nobody owns that records their household (a voice guest's records the guest's household, `CreateConversationParams.GuestTenantId` off the verified identity; a Telegram group's copy the group's bound household; pre-owner topics were marked shared and given an owner by the household migration, `.claude/rules/household-migration.md`); their household's shared topics; and with the `sees-all` role every topic of their household. A topic recording no household (only a turn acting for nobody opens one) is nobody's to see.
  - They **may continue** (send, stop its reply, upload into it) their own, shared and unowned topics they see — seeing every topic is reading, never deciding; marking read is not deciding either, since each person's position is their own. They **may rename or delete** only their own — a member continuing a shared topic does not decide it away — except an unowned topic, which has nobody to defer to, so whoever sees it may (`TopicViewer.MayContinue`, `MayRenameOrDelete`).
  - `GetTopicPageAsync`/`SearchTopicsAsync` take the viewer and fill a page from below whatever they passed over (`RedisThreadStateStore.FillPageAsync`, the cursor being the entry the page filled on), so another's private topics never cut a page short; search hits filter the same way.
  - **A list may be narrowed by whose topics it shows** (`TopicFilter`: `Mine` — what the person would see without sees-all — everyone's, or one person's; `TopicViewer.Lists` = `Sees` and the filter, so a filter only narrows and needs no permission). The hub's `GetTopicPageFiltered`/`SearchTopicsFiltered` pass it to the store; `GetTopicPage`/`SearchTopics` stay for installed apps from before (a hub binds every argument). A sees-all person reads `Mine` by default and picks another from `GetHouseholdPeople` (the accounts service's `member-names` view; empty for anyone else), remembered per device (`TopicFilterEffect`); anyone else lists everything they see. The client's topics store holds every row to the same rule on add and update, whatever dispatched it (`TopicsState.Lists`), so a filtered-out topic's badge never counts; one still seen but filtered out loses its row and stays open if open — only one no longer seen is closed. A conversation started while the list shows another person's is the starter's and moves the list to Mine once saved (`TopicListMoves`; user's decision, 2026-11-15).
  - **Every topic key names its household** (`RedisThreadStateStore`): the record `topic@{tenantId}:{agentId}:{chatId}:{topicId}`, the ordering `topics@{tenantId}:{agentId}:{slug}`, the search document `topicdoc@{tenantId}:...` (tagged `household` in `idx:household-topics`, filtered by the searcher's) — so no page, search, or read, mark or delete by id (`GetTopicAsync(tenantId, …)`, the hub passing the connection's `ForwardedAccount.TenantId`, never a client's word) can answer one household with another's topic. The '@' keeps these apart from the pre-household shapes the household migration's patterns match. The one household-free key is the conversation's pointer `topic-of:{agentId}:{chatId}:{threadId}`, valued `{tenantId}:{topicId}`: the agent appending history knows only the conversation id, so `GetTopicByChatIdAndThreadIdAsync` answers whichever household's topic holds it and its caller applies `TopicViewer`. Hence the hub's save and delete check the conversation before treating a topic its household does not hold as never saved: another household's topic over it fails the rule instead of being overwritten or deleted. A topic recording no household is kept under `none` (`RedisThreadStateStore.NoHousehold`), which no viewer is of. Histories stay keyed by conversation.
  - Every hub call naming a topic, session or approval resolves the stored topic first and refuses one the caller may not see with "No such conversation." — the words for one that does not exist; `StartSession` answers false instead. A conversation **no topic holds** is read by nobody (`GetHistory` answers empty, since Telegram's numeric ids are reachable by naming them) and opened, saved or deleted only when it is the one its own topic id names (`ConversationIdGenerator.CreateFor`), so a saved topic never adopts another channel's or person's conversation; a session over such a conversation is a fresh topic only its opener knows the id of. A new topic saved from the client is the connection's person's and private, whatever the browser sent; `SetTopicShared` is the owner's alone.
  - **Approvals:** a pending one is shown to whoever sees its topic and settled by its asker's account alone (`ApprovalService.AskerOf`, read off the hop's `_meta` by `request_approval`), from any of their connections; one acting for nobody keeps the topic's rule — its owner; on a shared topic also whoever's turn is running (the stream's current sender); on an unowned one anyone who sees it. Anyone else is answered false and the prompt stays pending. Only the asker gets the card's buttons (`ToolApprovalRequestMessage.AskedBy`, `ApprovalCard`); anyone else gets a status line and a Close that answers nothing.
  - **Reach:** every connection joins its household's `space:{tenant}:{slug}` and exactly one of `space:{tenant}:{slug}:user:{id}` or, holding `sees-all`, `space:{tenant}:{slug}:sees-all` (`TopicAudience`); a topic recording no household reaches no group. A private topic's news (created, deleted, stream started, approval resolved) goes to its owner's group and the sees-all group (no connection is in both), any other topic's to the space, and a share change to the whole space so each client adds or drops the row by `TopicViewer`. A person's message announces its stream there too (`ChatHub.SendMessage` sends `OnStreamStarted`, as `create_conversation` does for an agent-initiated turn), so the topic's other viewers follow live; the sending browser ignores it. The message carries the name it was sent under beside the account (`UserMessageInfo.SenderName`, `ChatHistoryMessage.SenderName`), shown for anybody but the reader and the topic's starter.
  - **Push:** a private topic's finished-reply push goes to its owner's subscriptions in the space alone (`SendToPersonAsync`), any other's to its household's space. It carries the reply's last text as one line (`string.Excerpt`, `StreamService.PushExcerptLength`), never its reasoning or tool calls, and names its conversation (`PushNotice.Topic`) beside the space's address, which the worker compares with the page on screen to stay quiet — only while a visible page shows that space, `/` and `/default` being the same page (`spacePage`). A tap opens `/{space}?agent=&topic=`, which `LaunchLink` reads once at app start: the first load opens that conversation over the remembered one, opens nothing if the list lacks it, and strips the query. A question asked in a topic (`RequestApprovalAsync`) is pushed to its asker's devices the same way, whether or not a page is open; an offered approval (asked on another channel) and an alert push to `/` with no conversation, the offer only when the person has no chat client open. A space's phones are kept under its household (`push:space@{tenant}:{slug}`, `RedisPushSubscriptionStore`), a person's under their user id; only its owner moves or removes one. Each carries the session that subscribed it (`PushSubscriptionDto.SessionId`, stamped by the hub from the assertion, never the browser's word): `WebPushNotificationService` asks whether that session lives before each push (`ISessionAccounts`), drops a phone whose session ended, and skips one it could not ask about.
  - **A failed turn is kept**: the person's message and what they were told (`TurnFailure.Answer`), both marked `IsFailedTurn` (`RedisChatMessageStore.InvokedCoreAsync`; a stopped turn is no failure, below), shown as the error with its retry (`ChatHistoryMessage.IsError`), never read back by the model (`ModelView`) nor by memory's extraction, and replaced by a retry sending the same words (`DropTailAsync`, which takes the topic's count back too).
  - **A turn a service started is a line, not a message** (`ServiceNotice`): a service's sender (`ServiceSenders`) or a request asking for a response format (`ChatHistoryMessage.ResponseFormat`, which no typed message carries — the Sugary app's turns carry the person's account) draws as "You finished logging in", "A scheduled task ran", "Sent from the Sugary app", the prompt behind a toggle (a fire's instruction alone, `FireReports.InstructionOf`: the report framed beside it is the model's) and its files shown.
  - A topic an agent opens (`create_conversation`) buffers its prompt with its time and announces `OnStreamStarted` after `OnTopicChanged`, so an open page follows its first turn, badge and preview like any later one. Opening a topic always asks the store to mark it read, since the client's count can be older than the store's.
  - **How far a topic was read is each person's** (`TopicMetadata.ReadBy` by account id, written inside the mark-read script; `ReadFor(userId)` is a person's view, applied by the store to every page and search and by the client to every pushed change; a topic read before keeps its old shared `ReadPosition` for whoever has none of their own): one person's devices share a position — a read is told to the topic's audience as a rename is — and a member reading a shared topic clears nothing for anyone else (user's decision, 2026-11-05).
  - **A turn ended by a rejected approval** has no text of its own, so the transcript draws its tool result (`ApprovalRejection`) as an assistant line, "web_browse was not run: it was turned down." An answer that is one JSON object draws as an outline (`JsonOutline`) and previews its words (`JsonObjectWords`); a named format may add a view of its own over it (`StructuredAnswers`, `meal_estimate`).
  - **Review copies** are owned by the turn: the agent hands `create_conversation` the turn's `Principal` (`IChannelConnection.CreateConversationAsync`), and `ConversationFactory` makes the topic the principal account's and private, or — for the voice guest — the guest's household's and shared; one for a turn acting for nobody records no household and nobody sees it. The asking channel never names where the copy goes nor whose it is (ADR 0046). **A group's copy is shared**: the asking channel states a fact, `ReviewCopy.Group` (the conversation is several people's), never a destination; the resolver hands it to `create_conversation` as `group` beside the principal (voice's tool declares no such parameter, since voice hosts no review copy, and the MCP server ignores an undeclared argument), and the factory makes that topic nobody's and shared with its `TenantId` still recorded (the group's bound household, which the sender's must be to get a turn), read by `TopicViewer` as unowned. The turn itself still acts for its sender's account (memory, logins). Voice's topics are minted by the agent the same way from the speaker's assertion (`.claude/rules/voice.md`), and Sugary's copies are the person's since its turns carry the account.
- **A conversation is rewritten from its page, and keeps what a rewrite replaced** (`.scratch/chat-edits/spec.md`). Every stored message carries an entry id (`ChatMessage.GetEntryId`, stamped by `RedisChatMessageStore`; a retry keeps the replaced message's), which `GetHistory` projects; a message kept before ids is named `legacy:{index}:{hash}` (`HistoryEntries`), a name the first rewrite replaces and nothing ever stores. The agent's list stays the one line the model and every page read; what a rewrite puts aside is a **version** of its slot, kept under `agent-versions:{agentId}:{chatId}:{threadId}` by the entry id the slot follows (`root` before the first), on the list's expiry. Rewrites are Domain's (`HistoryRewrite`: `PutAside`, `PutAsideFrom` (edit and re-run), `PutAsideReply` (reroll), `EditInPlace`, `SwitchVersion`, `CutFrom` — on a reply, its whole turn; in a slot with other versions, the newest shows); a failed turn stays whole (never a version; its mark goes once a real reply follows). `RedisThreadStateStore.RewriteAsync` applies one in a transaction refused when the line moved from what the page saw (its last entry id) or a turn is in flight (`agent-turn:…`, set as a turn reads its history, cleared when it is kept and by the group as the turn's stream ends), then recounts the topic's count, read positions and preview and rebuilds its search text. The hub's rewrite calls (`DeleteFrom`, `PutAsideFrom`, `PutAsideReply`, `EditInPlace`, `SwitchVersion`) are open to whoever may continue the topic, refused while it streams and on a topic another channel goes on showing (`TopicMirrors`: `TopicMetadata.Mirrored`, set for review copies and voice, else told by shape); they delete files nothing holds any more and tell the audience `OnHistoryChanged`, on which every page rereads. A reroll goes by `SendRerun` (`ChannelMessageNotification.RerunOf`): the person's message rides as itself, read once and kept once, and its reply keeps the model it ran on (`ChatMessage.GetModel`). `Fork` is open to whoever sees the topic: a new private topic of the forker's with the line copied (`HistoryFork`) and files copied into its own conversation.
- **A stopped reply is kept** as far as it got, on every channel: the person's message, what streamed before the stop (McpAgent hands the store each update), every tool call with its result (reasoning staying beside it), and the text marked interrupted (`ChatMessage.IsInterrupted`, `ChatHistoryMessage.IsInterrupted`), which the model reads from then on — kept only while the line still ends where the turn read it, so a delete or clear that stopped it is never undone. A reply ended by the output limit is marked interrupted too (`ChatFinishReason.Length`). **Continue** (`SendContinue`, `ChannelMessageNotification.Continuation`) carries on an interrupted last reply: a turn whose message is a fixed ask (`Continuation.Instruction`) marked `IsContinuation`, which the model reads and nothing else shows, counts or remembers (`Transcript.IsShown`, `ExtractionWindow`). `Transcript.StartsPersonsTurn` is the one rule every turn-boundary scan reads, so a continued reply is one reply to every rewrite and fork; the history marks what followed a Continue `ContinuesPrevious` and the client draws it in the bubble it continues; Retry after a failed Continue continues again. The page learns a streamed turn's entry ids from the history read once its stream ends (`EntryIdsLearned`, asked again a few times, since a stopped turn is kept after its stream ended), never reordering or redrawing what it shows, and skips the echo of its own rewrite.
- **One stream, several pages.** A topic's stream is shared by every page on it; a page joining — a send while another person's runs, a resume — is handed what it carried, under the same lock as its subscription (`StreamService.Join`): a joining send everything, a resume what the stream carried since the state the page drew (`ResumeStreamFrom` with `StreamSeen`; `ResumeStream` stays for older pages and is handed the people's messages alone). A person's message on the stream carries the sending page's `UserMessageInfo.CorrelationId`: that page skips it (except one it queued, which it draws there, `.claude/rules/chat-queue.md`); every other page draws it unless already shown (`BufferRebuildUtility.IsShown`: sender and words among its last few) — and one it shows closes nothing, or the reply shown so far would be cut from its rest. A resume draws every person's message the buffer carried, not just the current prompt. A rename is told to the topic's audience as a share change is.
  - **A turn over within milliseconds can end before the page has a wire on it** (the instant fake model shows it; a real provider's latency hides it). A send that lost its topic to a resume keeps what its own wire carried and, once the holder ends, draws whatever of it the holder never finalized, then names it (`StreamingService.ShowWhatTheHolderMissesAsync`). Another person's turn answered before this page's resume could follow it (`TryResumeStreamAsync(toldOfATurn: true)` finding nothing) reaches the page on no wire, so the history read at a stream's end (`EntryIdsLearned`, or `CatchUpWithHistoryAsync` for that resume) inserts it where the history has it, removing and moving nothing (`EntryIdNaming.WithMissedTurns`), and only for a read asked at the messages' `Revision` (nothing taken away since, so a read from before a delete never puts it back).
  - A reply streams to a page only while its person may see the topic: a share change bumps the topic's audience (`StreamService.AudienceChanged`) and each wire re-asks `TopicViewer.Sees`; a page told it may no longer see a topic only stops reading it (`TopicDeleteEffect`), never asks the hub to stop a reply not its own.
- **A topic the hub says does not exist for this person is closed on their page.** After a reconnect — including the renewal `OnAccessChanged` asks for — the open topic's history is asked again, and a `TopicRefusals.NoSuchConversation` answer (shared by hub and client) closes it as a delete does (`ReconnectionEffect`, `TopicRemoved`), e.g. another person's private topic left open when a sees-all grant was withdrawn.
- **Spaces are the household's configuration.** A household's spaces (slug, name, colour, default agent, order) are its `spaces` section (`.claude/rules/household-config.md`), a new household's being the one `default` space; the client's host keeps no list and reads no header. The hub answers `GetSpaces` (in order) and `JoinSpace`, which refuses a slug none of the connection's household's with "No such space." — the words for one that does not exist — each asked of the accounts service's `spaces` view with the session refresh's assertion of the connection's person (`ISessionAccounts.SessionAsync`), never the browser's word nor the arrival assertion, which outlives its ten minutes on a long connection. The client opens the space its slug names, or the household's first; a mid-session switch to a slug none of them goes to the first's page (`SpaceAgent.PathOf`). A space opens on the agent the person last picked **in that space** (localStorage `selectedAgentId:{slug}`; the default space keeps the old shared `selectedAgentId`, which a space never picked in falls back on), else the space's `defaultAgent` when the catalog holds it, else the household's default (its agents section's `defaultAgent`, else its first: `AgentCatalogEntry.IsHouseholdDefault`), else the first agent; what the client chose for them is not remembered as a pick (`SelectAgent.Picked`), so a default the household changes later still reaches them. The manifest (`/manifest.webmanifest?slug=&name=&color=`) is named once the page has heard from the hub (`manifestHelper.setSpace`), each value held to a space's shapes; before that the slug alone keeps the app's start, id and scope. **A removed space's topics are listed in the default space, read side** (`SpaceListing`, 4c): nothing is moved — they stay under `topics@{tenant}:{agent}:{slug}`. As a connection joins its household's default space (`default`, or the first for a household saved without one), `JoinSpace` asks the store which slugs the household's topics are kept under (`SpacesHoldingTopicsAsync`, a scan of `topics@{tenant}:*`, once per join and never per page) and keeps those that are none of its spaces on the connection; that space's `GetTopicPage` and `SearchTopics` pass them as `alsoSpaces`, and the store pages every ordering as one list by last write (merged in a sorted set's own order, so the cursor stays one cursor) and searches `@space:{a | b}`. A share change or delete of such a topic is told to the default space's groups (`HeardIn`), since nobody can join a removed one; streams and pushes already follow the space the session joined. A space added back under the same slug has its topics again.
