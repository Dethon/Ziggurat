# Scheduling Architecture

`McpServerScheduling` is a dual-role MCP server:
- **`filesystem://schedules` resource** (mount `/schedules`) — managed with the standard `domain__filesystem__*` tools. **A schedule is its household's**: `RedisScheduleStore` keeps it under `schedule@{tenantId}:{id}` and the household's set `schedules@{tenantId}`, with one deployment-wide `schedules-due` set of `{tenantId}:{id}` for the one dispatcher, and every read but the dispatcher's and the operator's `ListEveryHouseholdAsync` names the household. The mount's view of a call (`For(caller)`) lists, reads and writes only the household the call's verified identity names (`ConversationContext.Identity.TenantId`, the call token's, `CallTurn`) — so a schedule id is unique within its household only, and one household's `/schedules` can never answer with another's — and a call acting for nobody names none: it sees no schedule and writes none (`permission_denied`). `delegations_replace` refuses an id two households both hold rather than guess which. Layout: `/schedules/<agentId>/<scheduleId>/schedule.json` (`{prompt, cron|runAt, userId?, deliverTo?}` — exactly one of recurring `cron` or one-shot `runAt`), plus `agent_info.json` and read-only `status.json` (`createdAt`/`lastRunAt`/`nextRunAt`). `fs_exec ./run_now` on a schedule directory fires it immediately; `run_now` is an action file (reported executable by info and glob, refused on read and write). The `ScheduleFileSystem` engine (`Domain/Tools/Scheduling/Vfs/`) implements `IFileSystemBackend`, returning typed `FsResult<T>`. **A schedule runs as the person whose turn last wrote it, on the agent's delegation**: every create, edit and move keeps the delegation the agent signed for that write (`FileSystemCaller.Delegation`, read with `call.Delegation`) on `Schedule.Delegation` — a write carrying none, a turn acting for nobody, clears it — and the fire carries it back beside what the schedule does now (`ScheduleFirePlanner`, `ScheduleDelegation.Of`); the agent believes it only if its own signature holds for this schedule doing exactly that (`.claude/rules/service-identity.md`, "Deferred turns"). Each write still records that turn's `Principal` from the call's own context (`For(FileSystemCaller)`, as `HaFileSystem` does) into `Schedule.CreatedBy` — who last wrote it, never what a fire acts as. One written before accounts is stamped with its writer's account by the household migration, or the owner's where its principal names nobody (`HouseholdMigration/Steps/ScheduleCreators.cs`); one written before delegations fires for nobody until the agent's `redelegate` offers it as that writer and the operator says yes. The server also answers the agent's `delegations_list` / `delegations_replace` (`ScheduleDelegationStore`). The JSON's `userId` is the model's to write and is never evidence of who a fire acts for (`.claude/rules/web-browsing.md`, "A user id is only as true as the channel that sent it").
- **Channel** — registered through `AddChannelServer(DeliveryPolicy.GateOnLive)` (`Mcp.Hosting`). `ScheduleDispatcherService` polls `IScheduleStore` for due schedules, `ScheduleFirePlanner` chooses delete-after-fire (one-shot) vs. update-next-run (cron), and the shared `ChannelNotificationEmitter` emits `channel/message`. The notification itself — `deliverTo` parsed and coalesced into reply targets, the agent, the `userId`, the origin, one clock reading for the conversation id and the timestamp — is composed by `Domain/Channels/FirePlanning.cs`, which the Home Assistant server's watch callback uses too, so the two kinds of unprompted fire cannot drift. The default `deliverTo` is the shared policy file `Domain/delivery.json` (`DeliverySettings`), not a scheduling setting. Gate-on-live is load-bearing: the dispatcher deletes or advances a schedule only when the emit reports a live subscriber, and a false return buffers nothing, so a failed delivery leaves no duplicate to fire alongside the retry. The agent runs the prompt; `ChatMonitor` fans the result out to `deliverTo`, minting conversations as needed.

The `scheduling_prompt` (`Domain/Prompts/SchedulingPrompt.cs`) is the standing stub — a schedule is a deferred action of the agent's own, never a human reminder — plus the live agent list the server appends; the `/schedules` idiom itself (layout, which agent, the file's fields in the server's zone, the managing actions) is the `scheduling` skill (`Domain/Prompts/SchedulingSkill.cs`, built per zone and shipped through `AddSkills`). See `docs/adr/0039`.
