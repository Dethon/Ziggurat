# Scheduling Architecture

`McpServerScheduling` is a dual-role MCP server:
- **`filesystem://schedules` resource** (mount `/schedules`) — managed with the standard `domain__filesystem__*` tools. **A schedule is its household's**: `RedisScheduleStore` keeps it under `schedule@{tenantId}:{id}` and the household's set `schedules@{tenantId}`, with one deployment-wide `schedules-due` set of `{tenantId}:{id}` for the one dispatcher, and every read but the dispatcher's and the operator's `ListEveryHouseholdAsync` names the household. The mount's view of a call (`For(caller)`) lists, reads and writes only the household the call's verified identity names (`ConversationContext.Identity.TenantId`, the call token's, `CallTurn`) — so a schedule id is unique within its household only, and one household's `/schedules` can never answer with another's — and a call acting for nobody names none: it sees no schedule and writes none (`permission_denied`). `delegations_replace` refuses an id two households both hold rather than guess which. Layout: `/schedules/<agentId>/<scheduleId>/schedule.json` (`{prompt, cron|runAt, userId?, deliverTo?}` — exactly one of recurring `cron` or one-shot `runAt`), plus `agent_info.json` and read-only `status.json` (`createdAt`/`lastRunAt`/`nextRunAt`). `fs_exec ./run_now` on a schedule directory fires it immediately; `run_now` is an action file (reported executable by info and glob, refused on read and write). The `ScheduleFileSystem` engine (`Domain/Tools/Scheduling/Vfs/`) implements `IFileSystemBackend`, returning typed `FsResult<T>`. **A schedule runs as the person whose turn last wrote it, on the agent's delegation**: every create, edit and move keeps the delegation the agent signed for that write (`FileSystemCaller.Delegation`, read with `call.Delegation`) on `Schedule.Delegation` — a write carrying none, a turn acting for nobody, clears it — and the fire carries it back beside what the schedule does now (`ScheduleFirePlanner`, `ScheduleDelegation.Of`); the agent believes it only if its own signature holds for this schedule doing exactly that (`.claude/rules/service-identity.md`, "Deferred turns"). Each write still records that turn's `Principal` from the call's own context (`For(FileSystemCaller)`, as `HaFileSystem` does) into `Schedule.CreatedBy` — who last wrote it, never what a fire acts as. One written before accounts is stamped with its writer's account by the household migration, or the owner's where its principal names nobody (`HouseholdMigration/Steps/ScheduleCreators.cs`); one written before delegations fires for nobody until the agent's `redelegate` offers it as that writer and the operator says yes. The server also answers the agent's `delegations_list` / `delegations_replace` (`ScheduleDelegationStore`). The JSON's `userId` is the model's to write and is never evidence of who a fire acts for (`.claude/rules/web-browsing.md`, "A user id is only as true as the channel that sent it").
- **A schedule is read in its household's zone** (the household's `settings.timeZone`, `.claude/rules/household-config.md`): on a call, the mount asks it through the call's household (`FileSystemCaller.Household`, `call.Household`) and reads a bare `runAt`, a cron's next run and every time `schedule.json` and `status.json` show in it — the server's own zone (compose's `TZ`, its `TimeProvider`'s) for a call acting for nobody or a zone this host does not know. Glob, delete and `run_now` read no time and ask nothing. A cron's **fire** has no call, so the dispatcher proves the household with the schedule's own delegation (`CallHousehold.OfFire`, which the accounts service takes from this server alone and for a `schedule` only) and advances it in that zone; a schedule that delegates nothing, or whose delegation no longer verifies (logged), advances in the server's zone; and one whose household the accounts service cannot answer is left due for the next tick rather than advanced on a guessed clock. A one-shot needs no zone at its fire: its `runAt` was made UTC by the write. A save reaches the server at once, over its own Redis. The `DescribeMount` text and the `scheduling` skill still name the server's zone: both are served per session, before any call names a household.
- **Channel** — registered through `AddChannelServer(DeliveryPolicy.GateOnLive)` (`Mcp.Hosting`). `ScheduleDispatcherService` polls `IScheduleStore` for due schedules, `ScheduleFirePlanner` chooses delete-after-fire (one-shot) vs. update-next-run (cron), and the shared `ChannelNotificationEmitter` emits `channel/message`. The notification itself — `deliverTo` parsed and coalesced into reply targets, the agent, the `userId`, the origin, one clock reading for the conversation id and the timestamp — is composed by `Domain/Channels/FirePlanning.cs`, which the Home Assistant server's watch callback uses too, so the two kinds of unprompted fire cannot drift. A schedule's fire also names the household it is kept under (`HouseholdId`, from `Schedule.TenantId`), which the agent refuses the fire by while that household is suspended, delegated or not (`.claude/rules/service-identity.md`, "Deferred turns"); the dispatcher still counts a refused fire as delivered. The default `deliverTo` is the shared policy file `Domain/delivery.json` (`DeliverySettings`), not a scheduling setting. Gate-on-live is load-bearing: the dispatcher deletes or advances a schedule only when the emit reports a live subscriber, and a false return buffers nothing, so a failed delivery leaves no duplicate to fire alongside the retry. The agent runs the prompt; `ChatMonitor` fans the result out to `deliverTo`, minting conversations as needed.

**The agents a call sees are its household's.** The directories under `/schedules` (and each `agent_info.json`, and which agent a create or a move may name) are the calling household's own agents, read through the call's household proof (`ICallHousehold.AgentNamesAsync`, the accounts service's `agent-names` view, `HouseholdAgentCatalog`) — never the catalogue the agent registers with every channel, which is the home's: that showed every household the home's agents and refused a schedule for an agent a household added. The registered catalogue is read only on a stack with no accounts service to ask (the eval's `EveryHouseholdIn` answers the shipped agents; a unit's caller carries no household accessor).

The `scheduling_prompt` (`Domain/Prompts/SchedulingPrompt.cs`) is the standing stub — a schedule is a deferred action of the agent's own, never a human reminder — and names no agent: it is fetched for nobody and cached for every household, so the agent list it once appended was the home's, shown to everybody; the `/schedules` idiom itself (layout, which agent, the file's fields in the server's zone, the managing actions) is the `scheduling` skill (`Domain/Prompts/SchedulingSkill.cs`, built per zone and shipped through `AddSkills`). See `docs/adr/0039`.
