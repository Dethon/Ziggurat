# The Outpost

`McpServerOutpost/` is the one server with **no Dockerfile and no compose service**, because it is not part of the deployment: it is a self-contained single-file `linux-x64` binary somebody copies onto their own machine and runs with flags (`--name`, `--dir`, `--jailed`, `--exec`, `--hub`, `--ext`), publishing that machine's filesystem to the agent. It ships no `appsettings.json` either, and it is the one server allowed to add a configuration source of its own — a flag the operator typed has to beat an environment variable of the same name, which the default order does not give you (`OutpostFlags`). "Every server is a container" is otherwise a safe assumption.

**An outpost is a household's own server on the tunnel** (`.claude/rules/tunnel.md`). It opens one outbound tunnel to the relay and the agent never dials it: Kestrel listens on loopback on a port the system picks, and every stream the relay opens becomes a connection to it from the same process. So the machine needs no open port and no address the deployment can reach, and the deployment dials no address a machine supplied. `OutpostSettings.Mcp` is **computed**, never bound — the tunnel's hub, credential and server name from the flags and the environment, its timings from `Domain/tunnel.json` (`mcp:tunnel`, bound in `OutpostFlags`) when the file sits beside the binary, else `TunnelSettings`' identical defaults (`run-outpost.sh` installs the binary alone) — so no deployment variable (`MCP__SHAREDSECRET`, `MCP__TUNNEL__*`) can reach it. From there the hosting library does what it does for every tunnelled server: `/mcp` asks for the tunnel credential the relay presents, and **every tool call's token is checked** against the audience and keys the relay handed over the tunnel (`TunnelTrust`). The outpost no longer opts out of the call-token check.

- **The credential is the one value that is not a flag**: `CREDENTIAL` in the environment, because a command line is visible to every process on the machine. Passing it as a flag (`--credential`, and the retired `--sharedsecret` spellings) is refused with a message; so is starting without one, naming where it goes. The operator mints it per machine (`mint-tunnel-credential --household <id> --server outpost-<NAME>`); revoking it closes that machine's tunnel.
- **`--hub` is the deployment's address** (`https://assistants.<domain>`), and the tunnel is opened on its `/tunnel` route over the matching WebSocket scheme (`OutpostSettings.TunnelHub`); a `ws(s)://` URL is taken as the route itself. It is required: without a tunnel nothing can reach the machine. A deployment on a certificate authority of its own (a local stack's) is trusted when the environment names that CA's PEM file, `MCP__TUNNEL__HUBCERTIFICATEAUTHORITY`, read with the timings like any tunnelled server's (`tunnel.md`, "The server's end").
- **`--advertise` and `--port` are gone**, refused with a message rather than ignored, so an operator upgrading learns it. There is no registration API (`/api/outposts`), no keepalive, no registry store and no outposts shared secret (`OUTPOSTS__SHAREDSECRET`, gone from compose and `.env`; `DeploymentConformanceTests` pins both).

## How an outpost's tunnel is told apart

By the **server name its credential was minted for**: `outpost-<NAME>` (`Domain/Outposts/OutpostServerName.cs`, one spelling for both ends). The relay takes the household and the name from the verified credential, never from the open, and refuses a tunnel claiming a name its credential was not minted for — so a machine is an outpost because the operator minted it as one, and nothing a machine sends can make it one. One `TunnelRegistry` keyed by (household, server name) holds both kinds, and the prefix keeps an outpost called `vault` from replacing the household's own `vault` server. `--name` must therefore make a valid server name (`OutpostServerName.IsValidName`: lowercase letters, digits, inner hyphens), checked at startup with a message; `run-outpost.sh` lowercases the hostname it defaults to. A definition that names `outpost-<NAME>` as an own server gets that machine as a configured endpoint; `OutpostEndpoints.Compose` then leaves it out of the outposts rather than dial it twice.

## The agent's side

`TunnelledOutposts` (`Infrastructure/Tunnels`, registered beside the relay in `TunnelModule.AddTunnelRelay`) is the deployment's `IOutposts`: `Live(tenantId)` is the household's open tunnels whose name is an outpost's, each as `McpServerEndpoint.RelayedOutpost` — through that opening's client, bound to its generation and `Closed` token like any household server's (so a call after it closes fails as the machine going offline), **dynamic** in ADR 0027's sense, so a tunnel that closes between compose and dial costs the session that mount and nothing else. A turn that names no household has none, and another household's machines are never offered. The same class watches `TunnelRegistry.WatchAsync` and publishes an `OutpostEvent` (`Opened`, `Closed` with the relay's reason, the household) for each, because an outpost leaves no other trace of having been there — "was that machine up at two o'clock". The opening is what registering was, the tunnel's keep-alive is what the keepalive was, and its close is what deregistering and expiring were.

**There is no mount verdict any more.** It existed for one collision — two machines answering to one name — whose only channel back to the machine was the keepalive. Both are gone: the relay holds one tunnel per (household, server name), a second opening replaces the first (`Replaced`), and the mount point is spelled from the same `--name` the credential was minted for. A rogue binary publishing another name's mount is still shadowed by discovery and logged at the agent, and nothing tells the machine.

`.claude/rules/virtual-filesystem.md` owns what an outpost is as a filesystem — the jail rule, `ExecutingOutpostFileSystem` being a separate type, the `outpost:<NAME>` address that makes it a separate machine rather than a branch of the agent's tree, and the absence declared for a machine whose tunnel was open and which did not answer. See `docs/adr/0027` and `docs/adr/0028` (both written when outposts registered over HTTP; their decisions — dynamic endpoints are dropped, a subagent inherits outposts only if it also asks — hold unchanged on the tunnel). The tests are `OutpostTunnelTests` (the binary on a real relay: mounts, jails, executes, refuses an unsigned call, gone when its tunnel closes, never another household's), `OutpostConfigurationTests` and `OutpostExecTests`.
