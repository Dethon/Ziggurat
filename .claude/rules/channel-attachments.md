# Channel attachments, clips and dictation

See also: `.claude/rules/channels.md`, `.claude/rules/chat-hub.md`, `.claude/rules/chat-queue.md`, `.claude/rules/telegram.md`.

- **A channel may ask for a review copy, and the review host attaches to the conversation it anchors** (`docs/adr/0046-a-channel-may-ask-for-a-review-copy-and-webchat-shows-the-conversation-it-anchors.md`). `ChannelMessageNotification.ReviewCopy` (a `Title`) asks for the conversation to be shown on the deployment's one review host (`channelEndpoints[].hostsReviewCopies`, `signalr`; `IChannelConnection.HostsReviewCopies`). `DeliveryTargetResolver` makes it the agent-initiated fan-out with the sending channel first — `[channel on its own conversation, host with none]` — so the channel's conversation stays the delivery identity, resolved again on every turn. SignalR's `create_conversation` given an existing id *and* a topic name mints a topic over that very conversation when nothing holds it (so the topic reads the history the agent writes there), then announces the turn on it; the anchoring channel must therefore spell its ids as a `ConversationIdentity` (Sugary does). The title only names the topic the first time; after that the topic holds the conversation. The message's files are copied in the background, fetched from the channel and handed to the host by `store_attachment` under the same reference id, which SignalR keeps under its upload rules and never overwrites, so the shared history's references download from WebChat as its own do. A clip is copied and its stills are not (`ClipStills.Without`), so the topic shows what a video model was sent: SignalR keeps a review copy's `video/mp4` (`ReviewCopyMediaTypes`) up to `MaxReviewCopyClipBytes` (20 MiB, which fits one call's base64 under Kestrel's 30 MB body limit), while a person's upload still refuses video; the client plays it as `<video controls>` on the ticketed download, which answers byte ranges, and hides the stills a clip names. Sugary asks on every turn it opens: a meal's first estimate, each of her answers on it (under the first estimate's title, which `OpenEstimates` keeps, since an answer carries no words of the meal), and a nutrition label. Telegram asks on every turn (`TelegramBotService.ReviewOf`): `Telegram: <the account's display name>` for a private chat, `Telegram: <the group's title>` with `Group` for a group (a forum group's threads are each a conversation of their own under that one title).
- **An attachment crosses every boundary as a reference; bytes cross as few as possible.** `ChannelMessageNotification.Attachments` / `ChannelMessage.Attachments` carry `AttachmentReference` (where the file rests, media type, filename, size) and are transport-neutral, so nothing above the channel knows which transport a file came from. **Where the bytes rest is the channel's own answer, not something being a channel requires.**
  - SignalR keeps an upload store: bytes go browser → store (HTTP, one file per request, ticket-scoped) → agent; a download ticket is minted for the person the hub checked could see the file and opens it for that person alone, as the session check signed them for the chat channel (`AttachmentTickets.DownloaderOf`), so a copied link opens nothing for anyone else.
  - Telegram stores nothing — a `file_id` is a durable per-bot handle, so the reference names the agent whose bot can fetch it, `<conversation directory>/<agentId>.<file_id>` (`TelegramReference`; a file id is base64url and never holds the dot) — and the fetch is a `getFile` plus a download when the agent asks, with no volume, sweeper, retention or attachment settings on that channel (`docs/adr/0022-a-channel-whose-transport-keeps-files-has-no-upload-store.md`; the named escape hatch if fetching proves slow is a bounded in-memory cache there, deliberately unbuilt). `fetch_attachment` still reads the older agent-first `<agentId>/<file_id>` spelling, which persisted histories carry (the directory-first spelling is what lets review copies keep their photos).
  - **Every channel's reference begins with its conversation's directory** (`AttachmentEndpointPaths.ConversationDirectory`): WebChat keeps a review copy's file under the reference's own id and refuses one whose first segment is not the conversation it is kept for, because its store deletes and sweeps by that directory (the sweep asks one conversation's liveness for everything under it). A kept file names the agent whose conversation it was kept for (`AttachmentStore` metadata `agentId`, from the upload ticket's session or `store_attachment`'s), and the sweep's liveness (`AgentConversationLiveness`) and the hub's download check ask that agent's history and topic alone; a file from before names none and was the home's, so the home's registered agents are asked, and the sandbox landing takes the last segment alone for the same reason.
  - Sugary keeps an upload store of its own (files in its own volume beside the SQLite log, never in it), swept on age alone at the shared `attachmentRetention` because a meal's conversation is a few minutes of turns; it refuses a photo before storing it when the model the turn will run on — the agent its turns are routed to (`SugarySettings.Agent`, pinned equal to `agentDefaults.byChannel.sugary`), or the label model on a label's turn — cannot see one, by the shared `AttachmentCapability` rule over the sugary agent as her household runs it (`HouseholdAgentCatalogue`, the `agent-names` view on her assertion).
  - Either way the agent asks by `fetch_attachment`, the sixth channel-protocol tool, hidden from the model like the rest — `ThreadSessionBuilder` strips it (and `store_attachment`, the seventh, a review copy's way in). Neither is ever mounted (`docs/adr/0021-the-upload-store-is-not-a-mount.md`). The turn names the channel that took its files and, for a household's own server, that household (`SetAttachmentChannelId`, `SetAttachmentHouseholdId`), and the hydration asks `IAttachmentSource.FetchAsync(channel, household, id)` — two households' servers of one name each keep their own files, so a reference is never asked of another's. The persisted `ChatMessage` keeps the reference and never the bytes, and `AttachmentHydration` (`Domain/Agents/`) puts them back on the way to the model only, beside `TurnDecoration` and for the same reason (`docs/adr/0020-an-attachment-is-stored-once-and-hydrated-on-the-way-out.md`).
- **A clip is a video attachment that names its stills, and the send picks one or the other.** `AttachmentKind.Video` covers any `video/` type. A clip's `AttachmentReference.Stills` holds the ids of still frames stored as ordinary image references in the same message's attachment list. `AttachmentHydration` asks `ClipSelection`, given the `ModelInputs` `OpenRouterChatClient` resolves for the model the send resolved to (a patched turn included). A model that takes video gets the clip and none of its stills, as an `input_video` part with a data URL (`VideoInputParts`, since the Responses adapter drops a video `DataContent`). A model that takes only images gets the stills and every other picture. A turn whose model would see nothing of the clip (it takes neither, or takes only images and no stills came) throws `AttachmentRefusedException` before the request leaves. Past the hydration distance, one placeholder names the clip. Telegram keeps refusing a video, and so does a WebChat upload; WebChat holds a clip only as a review copy (`docs/adr/0045-a-clip-or-its-stills-is-chosen-at-the-send.md`).
- **A filmed Sugary meal is read before anything is kept** (`mcp-sugary`, "Dual-role" in `.claude/rules/channels.md`). The app posts one `clip` part as recorded. Before keeping anything the server reads it with ffmpeg (`McpServerSugary/Clips`; the image carries it, Domain has no codec) through the QuickTime/MP4 and Matroska/WebM demuxers alone; refuses one over 20 s (half a second's grace, then cut) or one that is not a clip, with a reason the app shows; makes it H.264 in MP4, short side at most 540 lines, no sound, no metadata; and takes up to eight stills from the phone's own picture at the app's 1568 px — the sharpest moment of each eighth by `blurdetect`, a stretch blurred against the clip's sharpest giving none (`StillChoice`). Clip and stills go to the upload store under the meal's conversation; the turn carries her photos, the clip naming its stills, and the stills (ADR-0045 picks per model). That route alone raises the body limit, to the clip's ceiling (`MaxClipBytes`) plus the photos'.
- **A dictation is not an attachment.** One run of a microphone that ends as words; the audio is never a message: no playback bubble, no attachment kind, no bytes in any store, nothing in a conversation's history but text. `IAudioTranscriber` (`Domain/Contracts/`) is the one injection point — complete audio plus its container, answered with a transcript and whisper's confidence figures — and `LemonadeTranscriptionClient` (`Infrastructure/Clients/Transcription/`) its only implementation, shared with the voice hub's streaming `ISpeechToText`, which is otherwise untouched.
  - **whisper as lemonade runs it rejects Opus in any container** (verified against the live instance; the image has no ffmpeg), so WebChat encodes 16 kHz mono s16le WAV in an AudioWorklet and Telegram decodes Ogg/Opus in managed code via Concentus; WAV, MP3, FLAC and Ogg/Vorbis are forwarded untouched, and the container is decided by sniffing the leading bytes, never by a sender-supplied mime type.
  - **WebChat opens the microphone for a recorder, not a phone call** — a mobile constraint, not a preference: `echoCancellation` and `noiseSuppression` are asked for as false, keeping an Android device off its voice-call audio route, whose processing reaches whisper as garbled speech. **`autoGainControl` stays on**: asked off, a hand-held Android phone spoken to normally recorded peaks under a tenth of full scale, reading as a room rather than a person. It works on the level rather than the shape of the sound, the one thing a phone microphone cannot supply for itself. A capped, upward-only lift when the WAV is built remains as a floor under it. The graph runs at the device's own sample rate, with the worklet resampling to 16 kHz behind its own anti-aliasing filter, because a 16 kHz `AudioContext` puts a resampler nobody here wrote inside the capture path, and it treats a phone's microphone differently from a laptop's. **The chain must still end at `ctx.destination`** (through a gain of zero — nothing is meant to be heard): Chromium renders a graph that reaches no output, Android does not, and every node then goes unpulled and records silence. No node in that chain may be left as a leaf, and no desktop test can catch it if one is.
  - WebChat's dictation ticket sits beside the upload and download tickets but is space-scoped and counts no slot — composer text must not force a conversation into existence or spend an attachment slot — and carries the recording cap and the mis-tap floor, so a dictation obeys the numbers the server holds when it starts rather than what the first render could learn; the transcription endpoint stores nothing. Telegram gates a transcript on the same confidence floors the satellites use and replies rather than staying silent; WebChat deliberately does not, because the person reads the words before sending them. Both record the existing `VoiceMetric` speech-to-text members under a `Channel` dimension, so the dashboard separates satellite, chat and Telegram with no new metric family.
- **Attachment capability is discovered, not configured, and it is refused twice.** `OpenRouterModelCapabilities` asks the provider's model list at startup and hourly; `AgentCatalogBuilder` stamps the accepted kinds onto each catalog entry, and `RunAsync` takes the catalog as a **function** so a refresh reaches channels through the existing registration (a connection re-registers a catalog whose wire shape changed). `AttachmentCapability` (`Domain/DTOs/Channel/`) is the one resolution the composer, `ChatHub` and `TelegramBotService` all use, so they cannot disagree about which model is refusing. The agent does not check a third time, except for a clip: the provider's `video` modality is mapped too, `AttachmentCapability` refuses a clip only for a model that takes neither video nor images, and the send refuses a clip its model would not see (ADR-0045). Permissive wherever the catalogue is silent — a blip at the provider must not remove the feature. Telegram accepts `register_agents` for this alone (nothing else there consumes the catalogue, and it has no per-message model override), and its refusal is per-turn: no turn is emitted, because an answer that silently ignores what was sent is worse than no answer.
