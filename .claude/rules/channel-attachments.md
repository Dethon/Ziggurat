# Channel attachments, clips and dictation

See also: `.claude/rules/channels.md`, `.claude/rules/chat-hub.md`, `.claude/rules/chat-queue.md`, `.claude/rules/telegram.md`.

- **A channel may ask for a review copy, and the review host attaches to the conversation it anchors** (`docs/adr/0046-a-channel-may-ask-for-a-review-copy-and-webchat-shows-the-conversation-it-anchors.md`).
  - `ChannelMessageNotification.ReviewCopy` (a `Title`) asks for the conversation on the deployment's one review host (`channelEndpoints[].hostsReviewCopies`, `signalr`; `IChannelConnection.HostsReviewCopies`). `DeliveryTargetResolver` makes it `[channel on its own conversation, host with none]`, so **the channel's conversation stays the delivery identity**, resolved again every turn.
  - SignalR's `create_conversation` given an existing id *and* a topic name mints a topic over that very conversation when nothing holds it, then announces the turn on it; so **the anchoring channel must spell its ids as a `ConversationIdentity`** (Sugary does). The title names the topic only the first time.
  - Files are copied in the background via `store_attachment` under the same reference id, which SignalR keeps under its upload rules and **never overwrites**. A clip is copied without its stills (`ClipStills.Without`); SignalR keeps a review copy's `video/mp4` (`ReviewCopyMediaTypes`) up to `MaxReviewCopyClipBytes` (20 MiB, fits one call's base64 under Kestrel's 30 MB body limit), while a person's upload still refuses video; the client plays it as `<video controls>` on the ticketed download, which answers byte ranges, and hides the stills a clip names.
  - Sugary asks on every turn it opens (an answer reuses the first estimate's title, kept by `OpenEstimates`); Telegram on every turn (`TelegramBotService.ReviewOf`: `Telegram: <display name>` private, `Telegram: <group title>` with `Group` for a group, each forum thread a conversation of its own under that title).
- **An attachment crosses every boundary as a reference; bytes cross as few as possible.** `ChannelMessageNotification.Attachments` / `ChannelMessage.Attachments` carry `AttachmentReference` (where the file rests, media type, filename, size), transport-neutral, so nothing above the channel knows the transport. **Where the bytes rest is the channel's own answer, not something being a channel requires.**
  - SignalR keeps an upload store (browser → store, one file per request, ticket-scoped → agent). A download ticket opens the file for the person the hub checked, alone (`AttachmentTickets.DownloaderOf`), so a copied link opens nothing for anyone else.
  - Telegram stores nothing: the reference is `<conversation directory>/<agentId>.<file_id>` (`TelegramReference`; a file id never holds the dot) and the fetch is `getFile` plus a download, with no volume, sweeper, retention or attachment settings (`docs/adr/0022-a-channel-whose-transport-keeps-files-has-no-upload-store.md`; a bounded in-memory cache is the named, deliberately unbuilt escape hatch). `fetch_attachment` still reads the older `<agentId>/<file_id>` spelling, which persisted histories carry.
  - **Every channel's reference begins with its conversation's directory** (`AttachmentEndpointPaths.ConversationDirectory`): WebChat refuses a review copy whose first segment is not the conversation it is kept for, because its store deletes and sweeps by that directory. A kept file names the agent whose conversation it was kept for (`AttachmentStore` metadata `agentId`), and the sweep's liveness (`AgentConversationLiveness`) and the hub's download check ask that agent alone; **a file from before files named their agent names none and was the home's**, so the home's registered agents are asked, and the sandbox landing takes the last segment alone for the same reason.
  - Sugary keeps an upload store of its own (its own volume beside the SQLite log, never in it), swept on age alone at the shared `attachmentRetention` (a meal's conversation is a few minutes of turns). It refuses a photo before storing it when the model the turn will run on — the agent its turns go to (`SugarySettings.Agent`, pinned equal to `agentDefaults.byChannel.sugary`), or the label model on a label's turn — cannot see one, by `AttachmentCapability` over the sugary agent as her household runs it (`HouseholdAgentCatalogue`, on her assertion).
  - The apps server keeps an ask's images in the shared upload store (`AddUploadStore`, at `<volume>/.uploads`), **saved for the app's household** (`.claude/rules/apps.md`, "App asks").
  - The agent asks by `fetch_attachment` (the sixth channel-protocol tool) and `store_attachment` (the seventh), both hidden from the model by `ThreadSessionBuilder` and **never mounted** (`docs/adr/0021-the-upload-store-is-not-a-mount.md`). The turn names the channel and, for a household's own server, the household (`SetAttachmentChannelId`, `SetAttachmentHouseholdId`); hydration asks `IAttachmentSource.FetchAsync(channel, household, id, turn)`, so **a reference is never asked of another household's server** of the same name. The persisted `ChatMessage` keeps the reference, **never the bytes**; `AttachmentHydration` puts them back on the way to the model only (`docs/adr/0020-an-attachment-is-stored-once-and-hydrated-on-the-way-out.md`).
  - **Every fetch is signed as the turn it is made for** (`IChannelConnection.FetchAttachmentAsync(id, turn)`: the turn's `ConversationContext` in the call's `_meta`, signed by `SigningClientTransport` as its `Identity`, as any of the turn's calls): hydration as the turn being sent (the request's options, never the stored message's, so a follow-up's earlier files are fetched for whoever asks now), landing as the message's turn, a review copy as the admitted identity. `ChannelAttachmentSource` caches per signed household too. A fetch for no turn is signed as nobody, which a household's file refuses; channels keeping files for none (Sugary, WebChat, Telegram) answer it as before.
- **A clip is a video attachment that names its stills, and the send picks one or the other** (`docs/adr/0045-a-clip-or-its-stills-is-chosen-at-the-send.md`). `AttachmentKind.Video` covers any `video/` type; `AttachmentReference.Stills` holds the ids of image references in the same message. `ClipSelection`, given the `ModelInputs` `OpenRouterChatClient` resolves for the send's model (a patched turn included), sends the clip alone to a video model — as an `input_video` part (`VideoInputParts`, since the Responses adapter drops a video `DataContent`) — and the stills to an image-only model; a model that would see nothing of the clip throws `AttachmentRefusedException` before the request leaves. Telegram and a WebChat upload keep refusing video; WebChat holds a clip only as a review copy.
- **A filmed Sugary meal is read before anything is kept** (`mcp-sugary`, "Dual-role" in `.claude/rules/channels.md`). The app posts one `clip` part; the server reads it with ffmpeg (`McpServerSugary/Clips`; the image carries it, Domain has no codec) through the QuickTime/MP4 and Matroska/WebM demuxers alone, refuses one over 20 s or not a clip with a reason the app shows, cuts it down (`ClipProcessor`: H.264 MP4, no sound, no metadata) and takes up to eight stills at the app's 1568 px (`StillChoice`). Clip and stills go to the upload store under the meal's conversation. That route alone raises the body limit (`MaxClipBytes` plus the photos').
- **A dictation is not an attachment.** The audio is never a message: no playback, no attachment kind, no bytes in any store, nothing in history but text. `IAudioTranscriber` (`Domain/Contracts/`) is the one injection point; `LemonadeTranscriptionClient` (`Infrastructure/Clients/Transcription/`) its only implementation, shared with the voice hub's streaming `ISpeechToText`.
  - **whisper as lemonade runs it rejects Opus in any container**, so WebChat encodes 16 kHz mono s16le WAV in an AudioWorklet and Telegram decodes Ogg/Opus via Concentus; WAV, MP3, FLAC and Ogg/Vorbis pass untouched. **The container is decided by sniffing the leading bytes, never by a sender-supplied mime type.**
  - WebChat's capture constraints are a mobile decision, recorded with their evidence at `dictation.js` `_constraints` (echo cancellation on, noise suppression off, **`autoGainControl` on**). The graph runs at the device's own rate and the worklet resamples to 16 kHz. **The chain must end at `ctx.destination`** (through a gain of zero): Android does not render a graph that reaches no output and records silence. No node may be left as a leaf, and no desktop test can catch it.
  - WebChat's dictation ticket is space-scoped and counts no slot (composer text must not create a conversation or spend an attachment slot), and carries the recording cap and mis-tap floor the server holds; the transcription endpoint stores nothing. Telegram gates a transcript on the satellites' confidence floors and replies rather than staying silent; **WebChat deliberately does not gate**, because the person reads the words before sending. Both record `VoiceMetric` speech-to-text members under a `Channel` dimension — no new metric family.
- **Attachment capability is discovered, not configured, and it is refused twice.** `OpenRouterModelCapabilities` asks the provider's model list at startup and hourly; `AgentCatalogBuilder` stamps accepted kinds onto each catalog entry, and `RunAsync` takes the catalog as a **function** so a refresh reaches channels through registration. `AttachmentCapability` (`Domain/DTOs/Channel/`) is the one resolution the composer, `ChatHub` and `TelegramBotService` all use. The agent does not check a third time, except for a clip: `AttachmentCapability` refuses a clip only for a model that takes neither video nor images (its stills serve an image-only one), the same line `ClipSelection` draws, and the send refuses a clip its model would not see. **Permissive wherever the catalogue is silent** — a provider blip must not remove the feature. Telegram accepts `register_agents` for this alone, and its refusal emits no turn, because an answer that silently ignores what was sent is worse than none.
