# Virtual Filesystem Architecture

Each MCP server can expose a `filesystem://` resource (`vault`, `media`, `ha`, `schedules`, `print-queue`, `timers`). At session start `McpFileSystemDiscovery` detects them and mounts them into `VirtualFileSystemRegistry` with longest-prefix path resolution. `FileSystemToolFeature` provides 10 domain tools (`VfsTextRead`, `VfsTextCreate`, `VfsTextEdit`, `VfsGlobFiles`, `VfsTextSearch`, `VfsMove`, `VfsCopy`, `VfsRemove`, `VfsExec`, `VfsFileInfo`) dispatching through the registry; raw MCP `fs_*` tools are filtered out while domain tools are active. `VfsExec` is filesystem-conditional — backends without `fs_exec` return a "tool missing" envelope.

Each mount is its own backend — **tools cannot reach across mounts**; data needed elsewhere must be copied there first. Backends derive from `FileSystemBackendBase` (`Domain/Contracts/`), which implements twelve of `IFileSystemBackend`'s thirteen operations as unsupported and provides what every backend used to copy: the error envelopes, the glob prologue (base path plus the trailing-slash dirs-only rule), a search regex compiled with a match timeout and guarded against a bad pattern, and the search template. New filesystems need no agent changes.

- **A backend declares its capability by overriding.** `AddFileSystemTools<TBackend>()` (`Infrastructure/Utils/FileSystemServerTools.cs`) reflects over which methods `TBackend` overrides and registers an `fs_*` tool for exactly those, taking each description from the backend's `Describe*` hook. Nothing is declared, so nothing can drift — capability is declared by overriding, so a server cannot advertise an operation its backend has no override for (an override that merely delegates to base still advertises; don't write one). Never hand-write an `fs_*` MCP tool. `Tests/Unit/Infrastructure/FileSystemServerConformanceTests.cs` asserts, per server, that advertised tools, overridden operations and published capabilities are one set.
- **A mount's identity comes from the backend too.** `AddFileSystemResource<TBackend>()` (`Infrastructure/Utils/FileSystemServerResource.cs`) sits beside the tool registrar and publishes the `filesystem://` resource, deriving the address, the published name and the mount point from the backend's one `FilesystemName`, with the prose from its `DescribeMount` hook. They cannot disagree, so there is nothing to keep in sync. Never hand-write a filesystem resource. `DescribeMount` is abstract on the base and satisfied by a constructor argument on the generic disk root, exactly as the name already is — otherwise "Obsidian vault" ends up hardcoded into a reusable type.
- **A mount says where it can be written, and whether a person's files may go there.** `FileSystemBackendBase.Workspace` is the writable, persistent directory under a mount, in the backend's own coordinates, and null for the mounts that have none — which is all but the sandbox. `IsLandingTarget` is the separate claim that attachments may be put into the mount — the sandbox alone, false by default so a new mount receives nothing until it says so. Both travel the same route as the mount's identity: published in the `filesystem://` resource, read by discovery, carried on `FileSystemMount`. One caller reads them — `AttachmentLanding` picks the landing target, then composes the landing directory from its workspace through `FileSystemResolution.ToVirtualPath`, so Domain never joins a mount point itself — and a landing target that declares no workspace lands nothing rather than falling back to the mount root, which is the silent failure the field exists to remove. Don't replace either with a constant or a name check: landing asks the mount, so it cannot know one image's layout. Landing used to ask which mount could execute, which was the same question while the sandbox was the only executing mount; an exec-enabled **outpost** would have started receiving somebody's attachments onto their own machine, so the claims came apart. No landing target and no exec-capable mount is an agent with no sandbox and names nothing as lost; no landing target *beside* an exec-capable mount names every file, because the model can see a filesystem it could have acted on. The sandbox declares its workspace from its own `HomeDir` setting, and its prompt is built from the same two values. See `docs/adr/0025-a-mount-declares-where-it-can-be-written.md`, including the 2026-08-15 refinement.
- **A walk over a disk root is bounded, stoppable and honest.** `DiskWalk` (`Domain/Tools/FileSystem/`) is the one recursive enumeration both disk walks run on — the glob's, in `LocalFileSystemClient`, and the text search's, in `TextSearchTool` — and it owns the two budgets as one definition each: `MaxEntriesScanned` (50,000, both walks) and `MaxFilesRead` (5,000, the search alone). They are constants, not settings; a test lowers them by overriding `ScanBudget`/`ReadBudget`, as the search's match timeout is overridden. Entries carry a directory flag so one pass answers the dirs-only rule, and reparse points are skipped by explicit option — that guard, not the shape of the tree, is what makes a link pointing at its own ancestor unwalkable, and its own test protects it because nothing else fails loudly when it is dropped. The client's glob is a `GlobWalk`: a lazy sequence plus the counters it updates, so `GlobFilesTool` stops pulling one match past `FileResultCap` and still reads how far the walk got. Both results report `budgetReached` (the walk stopped before the tree ended) and `entriesScanned`, spelled identically and distinct from `truncated` (more matched than fit); both are defaulted, because a backend whose entries are a finite in-memory set cannot trip them and is untouched. A glob's `Total` means matches found before stopping, and which entries come back depends on enumeration order — determinism was traded for the early exit. Cancellation propagates as the abort it is. The disk roots match with the shared `GlobRegex`, so one pattern language covers every mount.
- **Capability is per operation, not per path.** A backend may override an operation and still refuse particular paths; the list tells the model which operations exist on a mount, not which will succeed on a given file. Do not refine it into a per-path check the registrar cannot answer.
- **`FileSystemOperations.All` (`Domain/Contracts/`) is the one list.** The registrar, `FsResultContract.ResultTypes`, the discovery capability map, `ThreadSession`'s filter set and `FileSystemToolFeature.AllToolKeys` all derive from it, so a new operation cannot half-exist.
- **Disk roots are `DiskFileSystem`** (glob, info, move, delete, copy, blob read/write — no read, because reading bytes as text needs a rule about which files are text), `TextDiskFileSystem` (adds read, create, edit and text search where a root has allowed extensions), `SandboxFileSystem` (adds exec) and `MediaLibraryDiskFileSystem` (adds the `DownloadsOverlay`: a rendered `downloads/<id>/status.json` per live download, delete that cancels the download, and one refusal rule — `DownloadsOverlay.RefuseAsync(intent, path)` — that every operation on the mount asks before it acts, see `docs/adr/0014-a-live-download-owns-the-path-not-its-spelling.md`; the `MoveOut` intent asks only about downloads that have not finished, so a finished one's files can be filed into the library, see `docs/adr/0023-a-finished-download-no-longer-owns-its-bytes.md`). The generic disk root knows about none of them. Containment is decided once, by `PathJail`.
- **A mount is asked before a path leaves it.** A cross-mount move is a streamed copy plus a delete of the source, so the source's own `MoveAsync` refusals never run. `fs_move_out_check` is the thirteenth operation — transfer machinery like the two blob ones, so no tool key, no capability, invisible to the model — asked once on the source root by `Transfer` under a `Move` intent, before it dispatches to either branch — before the first byte and before the directory listing. It is the one operation whose override means the opposite of the others: the base default *allows*, so overriding declares "I have a rule", and `McpFileSystemBackend` asks the wire tool only of a server that advertised it. Only the media library has a rule. See `docs/adr/0015-a-mount-is-asked-before-a-path-leaves-it.md`.
- **A tool answers in the coordinates it was asked in.** Every path in a response is either the caller's own string echoed back, or a backend entry with its mount point prefixed by `FileSystemResolution.ToVirtualPath` — the one implementation. The backend's own spelling never reaches the model. Echo where the caller named the path (read, info, create, edit, remove's original path): a disk root answers container-absolute, and prefixing a mount point onto that produces nonsense. Translate where the backend produced paths the caller never named (glob entries, search hits, a directory transfer's per-entry paths). Backends keep their own conventions; the invariant holds at the tool boundary. `Tests/Unit/Domain/Tools/FileSystem/VfsVirtualPathConformanceTests.cs` drives every tool against a backend answering in three hostile spellings and fails if any path is not virtual; its tool set comes from the one list, so an operation cannot skip it. One field is exempt, named there with its reason: the raw glob string in a not-under-source transfer diagnostic. The `exec` working directory used to be the other — a backend now answers it relative to its own configured root (the root itself being the empty string, which becomes the mount point with a trailing slash) and the tool translates it like any other path the caller never named. See `docs/adr/0016-a-tool-answers-in-the-coordinates-it-was-asked-in.md`.
- **A transfer is one thing.** `Transfer` (`Domain/Tools/FileSystem/Transfer.cs`) is the copy-or-move machinery: one entry point taking a `TransferRequest` and answering `FsResult<FsTransferResult>`, so errors stay typed until the tool boundary. It owns the file-versus-directory probe, so `VfsCopyTool` and `VfsMoveTool` are resolve, resolve, delegate, serialize — and the only difference between them is the `TransferIntent` they pass. That intent gates three move rules: ask the move-out question, delete the source afterwards, and refuse a directory move that streamed nothing. Its tests drive the two tools, never the module.
- **Resolution is data.** `IVirtualFileSystemRegistry.Resolve` returns `FsResult<FileSystemResolution>`; an unmounted path becomes the error envelope the prompt promises, at every tool site.
- **A mount point is claimed first-come, and an outpost can lose it.** `VirtualFileSystemRegistry.TryMount` answers false where the mount point is already taken; discovery mounts in dial order and logs the loser as *shadowed* — a perfectly valid registration whose mount never happened. This used to be last-write-wins, and **outposts** are why it is not: a machine that named itself after an existing mount would otherwise replace it, so a stranger's laptop could shadow the vault. `OutpostEndpoints.ComposeAsync` puts configured endpoints before dynamic ones for the same reason, so which one loses is decided by mount order rather than by whichever dial finished first. The collision is never checked when a registration is announced, because mount names live inside each server's `filesystem://` resource and are only read at session build.
- **An outpost is a filesystem on a real machine that registered itself.** `OutpostFileSystem` (`Domain/Tools/Files/`) is a text disk root whose mount root is the machine's root `/`; `--jailed` adds a refusal rule every operation asks (the media library's shape, including `MoveOutCheckAsync`, since a transfer off the mount never reaches `MoveAsync`) and roots the glob and search walks at the working directory instead of filtering a walk of `/`. `ExecutingOutpostFileSystem` is a **separate type** rather than a flag, because capability is declared by overriding and the registrar reflects over the type. An outpost is never a landing target, exec or not. Live registrations join an opted-in agent's endpoint list at session build (`AgentDefinition.UsesOutposts`, nothing on by default); a registration or an expiry takes effect at the next session build and never mutates one already there, the same rule ADR-0012 sets for a channel server's tool set. See `.scratch/outposts/spec.md` and `docs/adr/0027`.

Globs support brace expansion (`GlobBraceExpander`): `**/*.{jpg,png}` = union of both patterns (lone/unbalanced `{...}` stay literal). All backends normalize glob entries to full virtual paths.
