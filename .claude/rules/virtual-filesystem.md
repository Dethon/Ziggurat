# Virtual Filesystem Architecture

Each MCP server can expose a `filesystem://` resource; `McpFileSystemDiscovery` mounts each into `VirtualFileSystemRegistry` (longest-prefix resolution), and `FileSystemToolFeature`'s `Vfs*` tools dispatch through it, raw MCP `fs_*` tools filtered out while they are active. `VfsExecTool` on a backend without `fs_exec` answers a "tool missing" envelope, unless the session has a sandbox and the host a bridge: then exec on a mount a command is served runs in the sandbox (`.claude/rules/sandbox.md`, "exec runs where the files are").

Each mount is its own backend — **tools cannot reach across mounts**; data needed elsewhere is copied there first. Backends derive from `FileSystemBackendBase` (`Domain/Contracts/`), where every operation but the move-out check defaults to unsupported. A new filesystem needs no agent changes.

- **A backend declares its capability by overriding.** `AddFileSystemTools<TBackend>()` (`Infrastructure/Utils/FileSystemServerTools.cs`) registers an `fs_*` tool for exactly the methods `TBackend` overrides, described by its `Describe*` hooks. Never hand-write an `fs_*` MCP tool, and never write an override that merely delegates to base (it still advertises). **A server may serve several filesystems**: each backend type registered once, each call dispatched by its `filesystem` argument (`McpFileSystemBackend` sends it on every call); a call naming none goes to the first registered (what an outpost or kit server from before sends — keep that fallback), an unserved name is `invalid_argument` naming the served ones, an operation the named backend lacks is `unsupported_operation`. Each resource publishes its own `operations` and discovery mounts it with that set — the server's whole tool set where a resource publishes none (older outposts and kit servers). `FileSystemServerConformanceTests` holds overridden = published = mounted, per filesystem.
- **A mount's identity comes from the backend too.** `AddFileSystemResource<TBackend>()` (`Infrastructure/Utils/FileSystemServerResource.cs`) derives the address, published name and mount point from the backend's one `FilesystemName`, the prose from `DescribeMount`. Never hand-write a filesystem resource. `DescribeMount` is abstract on the base and a constructor argument on the generic disk root, so "Obsidian vault" is never hardcoded into a reusable type.
- **A mount says where it can be written, and whether a person's files may go there.** `FileSystemBackendBase.Workspace` (the writable persistent directory, backend coordinates; null on all but the sandbox) and `IsLandingTarget` (attachments may land; the sandbox alone, false by default) are two claims, published in the resource, read by discovery, carried on `FileSystemMount`. `AttachmentLanding` reads them and composes the directory through `FileSystemResolution.ToVirtualPath`; a landing target with no workspace lands nothing, never the mount root. Don't replace either with a constant, a name check or "the mount that executes": an exec-enabled outpost would then receive somebody's attachments onto their own machine. No landing target and no exec mount names nothing as lost; no landing target beside an exec mount names every file. The sandbox's workspace and its prompt come from its own `HomeDir`. `docs/adr/0025` (with the 2026-08-15 refinement).
- **A mount says how far its shell reaches.** `FileSystemBackendBase.ShellReach`: `Contained` (the sandbox), `Host` (`ExecutingOutpostFileSystem`, somebody's own computer), null for every other mount; published as `shellReach`, read by `McpFileSystemDiscovery.ReadMount` (absent, null and unknown all null), carried on `FileSystemMount`. The exec screen judges by it (a command headed for a person's machine is asked when no verdict came, the sandbox's runs), as do `VfsCall.IsServed`, `ExecReach.SandboxFor`, the prompt's shell section and the bridged-backend choice. It is not exec capability: `/ha` overrides exec and declares no reach, so its exec alone is never screened, and rerouted into a sandbox it is judged at the sandbox's reach but for one bare action (`.claude/rules/sandbox.md`, "exec runs where the files are"). Don't replace it with a name or mount-point check. `FileSystemServerConformanceTests` pins each server's reach, `OutpostExecTests` the outpost's.
- **A walk over a disk root is bounded, stoppable and honest.** `DiskWalk` (`Domain/Tools/FileSystem/`) is the one recursive enumeration under both the glob (`LocalFileSystemClient`) and the text search (`TextSearchTool`), and owns `MaxEntriesScanned` and `MaxFilesRead` as constants, not settings (tests override `ScanBudget`/`ReadBudget`). Its reparse-point skip is load-bearing and has its own test — keep it. The glob is a lazy `GlobWalk`, so `GlobFilesTool` stops past `FileResultCap`. Results report `budgetReached` and `entriesScanned`, distinct from `truncated` and defaulted so in-memory backends are untouched. A glob's matches come back in enumeration order — determinism was traded for the early exit; don't add a sort. Cancellation propagates as the abort it is. Disk roots match with the shared `GlobRegex`.
- **`file_read` reads text and images, and an image arrives inside its own tool result** (`docs/adr/0029`).
  - Kind is by extension alone (`ImageFileKinds`), never magic bytes.
  - **There is no new operation**: an image's bytes come from `ReadChunksAsync`, transfer machinery with no tool key or capability, so `FileSystemOperations.All`, the capability map and the wire tool set stay untouched and the tool is offered exactly where `fs_read` is. Byte-less mounts (timers, schedules) answer `unsupported_operation` for an image; `/ha` overrides the byte read with `HaFileSystem.RenderAsync`, so an image path there is not found.
  - It answers `FsImageReadResult`, a shape of its own rather than `FsReadResult` repurposed — the send recognises an image read by it. `shown: false` never travels without a `note` reason. The ceiling `readImages.maxInlineBytes` is the agent's own setting, never a compose or shared-policy entry; images are never downscaled or re-encoded.
  - **A refusal never costs the transfer**: the mount is statted first (`InfoAsync`, failures fall through), so every byte-free refusal precedes the first byte; a mount that cannot stat is stopped at the ceiling and the count named "at least".
  - The bytes go to `IReadImageStore` (`RedisReadImageStore`; optional in DI, as `IAttachmentSource` is), keyed by tool call id and the turn context's conversation id — the id the send looks them up under, so a context-less run refuses rather than strands bytes. `AttachmentHydration` rewrites the result into text plus picture on a copy thrown away with the request: nothing new is persisted. The send re-asks the capability for the model the turn resolved to, because the wire rejects a whole request carrying an image that model cannot take: that turn gets a placeholder and the bytes are kept. Past the distance or on a store miss the placeholder names the path and says to read it again. `ForgetOnceReadImageStore` deletes the bytes once, on the send where the image drops out of view. The truncator counts an image part at the flat per-image estimate.
- **An action file runs and is never opened.** `/timers` (`dismiss`), `/schedules` (`<agent>/<id>/run_now`) and `/ha` (each entity's services) expose closed catalogs as extensionless action files run as `./<action>` or the bare name — every executing mount accepts both (`FileSystemBackendBase.WithoutDotSlash`); reading or writing one is refused on every route with `FsError.ExecutableOnly`, whose hint names `exec ./<action>`. `FsInfoResult.Executable` and `FsGlobResult.Executables` mark them, defaulted and off the wire (`executable` only when true, `executables` only when non-null) so every other backend's answer is byte for byte unchanged; `VfsVirtualPathConformanceTests` translates the list like the entries.
- **A mount with tables answers SQL, and its tables are not text.** `query` (`fs_query`, `VfsQueryTool`) runs one DuckDB statement over every table of the mount: a backend overrides `QueryAsync` and hands its tables to `ITableEngine`, whose DuckDB implementation lives only in `McpServerSugary/Tables/` so no other image carries the native library. The statement is the model's and trusted with nothing: a fresh in-memory database per statement, no file access, no extension loading, the mount's clock set and configuration locked before any table loads, a time bound. Every instant column gets a `<column>_local` sibling. The same tables are the mount's Parquet files, written single-threaded so a stat's size is the read's, and every chunk of one read comes from one version (`IReadSnapshots`, `McpServerSugary/Tables/ReadSnapshots.cs`), so a save never tears a read. That rests on the reader's side too: the proxy (`McpFileSystemBackend`) asks each next chunk (256 KiB) at exactly the offset the last one ended, since a version finds its read by that offset; a chunk past the start whose read was quiet for 30 s is refused `transient_dependency`, and the read starts again from the beginning. The byte read serves them (the bridge's read, so a sandbox command opens them with duckdb or polars), info reports their real size, and the text read refuses a table with `FsError.QueryOnly` — the text read stays overridden for the README, because the bridge serves a read only where `file_read` is offered. `/sugary` is the one such mount; whose log it answers, and `people/<folder>/` for a granted reader, is `.claude/rules/sugary.md` ("Everyone's log, for a reader an owner granted it").
- **Capability is per operation, not per path.** A backend may override an operation and still refuse particular paths; do not refine capability into a per-path check the registrar cannot answer.
- **`FileSystemOperations.All` (`Domain/Contracts/`) is the one list.** The registrar, `FsResultContract.ResultTypes`, the discovery capability map, `ThreadSession`'s filter set and `FileSystemToolFeature.AllToolKeys` derive from it, so an operation cannot half-exist.
- **Disk roots are `DiskFileSystem`** (glob, info, move, delete, copy, blob read/write — no text read), `TextDiskFileSystem` (adds read, create, edit, search over allowed extensions), `SandboxFileSystem` (adds exec) and `MediaLibraryDiskFileSystem` (adds the `DownloadsOverlay`: one refusal rule, `DownloadsOverlay.RefuseAsync(intent, path)`, that every operation asks first; `MoveOut` asks only about unfinished downloads — `docs/adr/0014`, `docs/adr/0023`). The generic disk root knows about none of them. Containment is decided once, by `PathJail`.
- **A mount is asked before a path leaves it.** A cross-mount move is copy plus delete, so the source's `MoveAsync` refusals never run; `fs_move_out_check` (transfer machinery, invisible to the model) is asked once on the source root by `Transfer` under a `Move` intent, before any byte or listing. Its base default *allows* — overriding declares "I have a rule" — and `McpFileSystemBackend` asks it only of a server that advertised it. Only the media library has a rule. `docs/adr/0015`.
- **A tool answers in the coordinates it was asked in.** Every response path is the caller's own string echoed (read, info, create, edit, remove's path) or a backend-produced path translated by `FileSystemResolution.ToVirtualPath`, the one implementation (glob entries, search hits, a transfer's per-entry paths, the `exec` working directory — which a backend answers relative to its own configured root, the root itself as the empty string, and the tool translates). The backend's own spelling never reaches the model. `VfsVirtualPathConformanceTests` drives every tool from the one list against hostile spellings, and names the one exempt field. `docs/adr/0016`.
- **A transfer is one thing.** `Transfer` (`Domain/Tools/FileSystem/Transfer.cs`) is copy-or-move behind one `TransferRequest` → `FsResult<FsTransferResult>`; `VfsCopyTool` and `VfsMoveTool` differ only in the `TransferIntent` they pass. Its tests drive the two tools, never the module.
- **Resolution is data.** `IVirtualFileSystemRegistry.Resolve` returns `FsResult<FileSystemResolution>`; an unmounted path is the prompt's error envelope at every tool site.
- **A tool resolves as its caller.** Every file tool resolves through `registry.Resolve(path, arguments)` (`ToolCaller`), binding an `ICallerBoundBackend` (the agent's MCP proxy) to the conversation the call's own arguments carry — `ToolApprovalChatClient` puts it there beside `ToolPermission`. Nothing reads the invocation in flight, so a backend nobody bound acts for nobody: no `_meta` context, no delegation. A transfer binds both ends through one view where they share a backend (`ToolCaller.As`), since `Transfer` tells a same-mount move by backend identity.
- **A registry may be read outside any conversation** (a built app's reads): `AgentReadRegistries.BuildAsync(viewer, agentId)` → `ReadRegistry`, disposed by its user.
  - **For a person** — the identity the agent verified (an assertion's, as `AssertionVerifier.VerifyTurnAsync` admits a turn), never a header; the guest and nobody are refused. The household read is the identity's.
  - **For one of the household's own agents** (`HouseholdAgents.Find`): a person's registered agent is not found, `AgentNotFoundException` naming it.
  - **It mounts what a turn of that agent would**: built by the one build a turn's session goes through (`SessionReach`: the definition's endpoints withheld by features and by own servers not set up or offline, dialled and mounted by `ThreadSession`), so nothing where the agent is offered no filesystem tools. **Never outposts**, whatever `usesOutposts` says: a machine is somebody's own computer, reached for the person at it; an app reads the household's data.
  - Its backends act for nobody until bound to `ReadRegistry.Caller` (the person; conversation `ReadRegistry.NoConversation`), which every call is then signed as. `Offline` names own servers not reached; `IsStaleAsync` asks the household's servers again (a lookup) as a turn's start does. `AgentReadRegistriesTests`.
- **A mount point may be a union of filesystems.** A backend declares `FileSystemBackendBase.Union` (`FileSystemUnion`: `routeBy`, a JSON pointer with `*` for array items, plus `claims` or `fallback`), published as `union`, read onto `FileSystemMount.Union`. Where every mount at a mount point declares one, `VirtualFileSystemRegistry.TryMount` joins them into the generic `UnionFileSystem`; a member declaring workspace, reach or landing, a second fallback, a value claimed twice or a different `routeBy` is refused. A non-union collision keeps first-wins. A top-level entry belongs to the member whose root listing holds it; a new entry goes to the member claiming its content's `routeBy` values (the fallback otherwise; split claims are `invalid_argument`); a move or copy between members is refused. **One id is one entry across the members**: before a new entry goes to a member, the others are asked (`InfoAsync`), and one holding it — even hidden from this caller, which a member answers as `Exists` false with `FsInfoResult.Hidden` (off the wire while false) — makes it `already_exists`, naming no member and nothing of the entry. Glob and search merge every member; one that throws or answers retryable is named in `FsGlobResult.Unavailable` (the bridge treats that listing as cut short), and an entry missing while a member is away is `transient_dependency`, never `not_found`. `As(caller)` binds every member. `VfsVirtualPathConformanceTests` and `VfsBridgeOverTheWireTests` drive a union. `/watchers` is the one shipped: the home's `ha-watches` (fallback) and Sugary's `sugary-watches` (claiming `glucose`, `glucose_trend`, `glucose_forecast`, `sensor` at `/triggers/*/trigger`, answering `Hidden` for a watch the caller may not see), with skills `home-watches` and `glucose-watches` dividing requests by subject (`.claude/rules/sugary.md`).
- **An outpost is a separate machine, addressed `outpost:<NAME>`, and only another outpost can shadow one.** Its mount point is `OutpostMountPoint.For(name)` (`Domain/Outposts/`), declared by `OutpostFileSystem.MountPoint` — the base's one virtual override — not assigned by the agent, since the outpost's own descriptions and jail refusals name it. The hub checks the address against what it knows: a mount from an outpost's endpoint not at a machine address is not mounted (`McpFileSystemDiscovery`), since at `/<name>` it would pass for a deployment mount and be served into sandbox commands. Whether a mount is an outpost is read off the address, by `FileSystemToolFeature.MachinesSection` (listed as somebody's separate computer) and `VfsCall.IsServed` (never served into a sandbox command); `Resolve` never prepends a slash to one. `VirtualFileSystemRegistry.TryMount` answers false for a taken mount point: first-wins in dial order, the loser logged as *shadowed* — never last-write-wins. `OutpostEndpoints.Compose` puts configured endpoints first, then outposts (one tunnel per `outpost-<NAME>`) in name order, leaving out one a definition already names — so a mount a rogue binary claims under another name loses by mount order, never by whichever dial finished first; don't mount in completion order.
- **An outpost is a filesystem on a real machine whose tunnel is open.** `OutpostFileSystem` (`Domain/Tools/Files/`) is a text disk root at the machine's `/`; `--jailed` adds a refusal rule every operation asks (including `MoveOutCheckAsync`, since a transfer off the mount never reaches `MoveAsync`) and roots the walks at the working directory. `ExecutingOutpostFileSystem` is a **separate type**, not a flag, because the registrar reflects over the type. An outpost is never a landing target, exec or not. **It is reached only through its tunnel** (`.claude/rules/outpost.md`, "An outpost is a household's own server on the tunnel": loopback only, the tunnel credential, every call's token checked). The household's open tunnels (`IOutposts`, `TunnelledOutposts`) join an opted-in agent's endpoints at session build (`AgentDefinition.UsesOutposts`, off by default); another household's never do. A **subagent** sees them only where its parent's flag and its own `SubAgentDefinition.UsesOutposts` are *both* true; it inherits the flag and household (via `SpawnContext`), not a set of machines (`docs/adr/0028`). A tunnel opening or closing takes effect at the next session build and never mutates an existing one (ADR-0012's rule). A machine whose tunnel was open and whose dial failed is declared absent (`OutpostEndpoints.DeclareUnreachable`), judged by the server the dial reached (`McpClientManager.DialledServers`, `ServerAddress`), never by mount name. An outpost reports no telemetry; its tunnel's openings and closings are `OutpostEvent`s. `docs/adr/0027`, `docs/adr/0028`.

Globs support brace expansion (`GlobBraceExpander`): `**/*.{jpg,png}` is the union of both patterns; a lone or unbalanced `{...}` stays literal. Every backend's glob entries become full virtual paths.
